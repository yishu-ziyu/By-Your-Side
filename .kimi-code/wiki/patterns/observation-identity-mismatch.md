# Pattern: 诊断读错观测对象——按名字匹配命中别的扩展、共享日志没有时间轴、并发工作区的假回归

## 现象（本轮连踩三处）

1. **按名字匹配 service worker，读到别的扩展的存储。** 清理脚本用 `t.url.includes("background.js")` 找后台；
   Chrome 里同时跑着多个扩展的 `background.js`，命中的不是本项目那个。脚本于是报告
   「history 键 0 个、占用 4,593,372 字节、写入自检成功」—— 数字干净、结论全错，而且已经执行过一次 `remove`
   （删的是别人的键，不是我们的）。按扩展 ID 重跑才读到真实的 10,485,715 字节 / 108 个键。

2. **多进程共用的 stderr 日志没有时间戳。** `~/.sideagent/wrapper-err.log` 由所有宿主进程共用（1,277,164 字节、
   226 次启动记录混在一起），行内无时间；文件末尾是崩溃栈，紧跟其前的却是 50 分钟前的启动块。
   按行序推时间会得出「刚启动就崩」的错结论。带时间戳的是 `~/.sideagent/agent.log`（ISO，UTC）：
   它显示该时段最后一次写入在 14:32:22Z，之后没有新宿主启动。两个文件不一致时，先信有时间的那个。

3. **并发/高负载下的全量检查会造假回归。** 同一工作区另有并行工作与并发构建时，全量测试出现 2–3 项失败，
   失败文件（如 `extension/test/click-integrity.test.ts` 的 B1）都不属于本次改动；单独复跑稳定全绿。

## 根因

下结论前没有把观测对象的**身份**和**时间**钉死：名字匹配被假定唯一、共享文件被假定有序、
测试失败被假定来自本次改动。

## 方法

- **扩展上下文按 ID 过滤**：用 `chrome-extension://<extensionId>/`，ID 由 manifest 的 `key` 推导
  （`scripts/acceptance/constants.mjs` 已有现成函数）；不要用 `background.js`、`sidepanel.html` 这类通用名匹配。
- **读带时间戳的日志**；共用 stderr 只用来取原文（崩溃栈、异常），不用来定序。
- **失败先单独复跑再归因**：记录失败文件与用例名，确认是否落在本次改动范围内，再写结论。
- **写入型探针先干跑**：删除/覆盖前先打印「将要删的键与归属扩展」，确认 ID 后再执行。
- **MV3 后台不在运行时的探针手法**：从扩展页面 `chrome.runtime.connect()` 可以把它唤醒，再按 ID 找 target。

## 适用条件

同一台机器、同一个工作区里同时跑多条工作线时的只读诊断与验证。单扩展、独占工作区时不适用。

## 验证

- 身份过滤：错误脚本读到其他扩展的 4,593,372 字节 / 0 个 history 键；按 ID 重跑读到 10,485,715 字节 / 108 个键。
- 时间轴：`wrapper-err.log` 无时间戳且多进程混写；`agent.log` 带 ISO 时间戳，可判断「崩溃栈属于 22:32 那批进程」而非 23:22 新起的进程。
- 复跑：单独跑全量 3 次均 136 文件 1127 项通过；并发时段出现 2–3 项失败，失败文件不在本轮改动内。
- 并发证据：同一工作区在 23:47–00:13 出现另一条工作线的 8 个设计预览 HTML 与 9 张截图（未跟踪，本轮未提交）。

证据：[本轮验收](../../../docs/evals/20260910-panel-history-quota.md) 与 [STATUS](../../../docs/STATUS.md) 顶部未决项。
