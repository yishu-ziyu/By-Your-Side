# Pattern: 配额受限的存储写满后会静默毁掉功能；按实体分键会被广播状态批量放大

## 现象

2026-09-10 晚真机：侧栏显示「未连接」。表面是连接问题，实际后台一直在刷
`Error: Resource::kQuotaBytes quota exceeded` —— `chrome.storage.local` 已被写满：
**10,485,715 / 10,485,760 字节（99.9996%）**。

写满之后所有写入都失败，而且失败**离现场很远**：用户看到的是「草稿切个会话就没了」「教学模式记不住」
「token 存不进去」，看不到配额错误。键的构成是 `history:<会话 id>`：一个会话一条，108 条合计 9.65 MB，
最大单键 905 KB。

更隐蔽的一层：手工清空后一小时又长出 **119 个键**，内容只有每个会话的 `status` 条目。
落盘触发条件是 `status idle`，而服务端给**每个会话**都推状态 —— 也就是「每个会话一条键」
不是历史慢慢堆积，而是**一次连接批量写出来的**。

## 根因

1. 落盘写的是「内存里的全部历史」（每条 thinking 增量、每次工具返回都在内），没有上界；
2. 键按会话分片且从不清理，会话数增长直接变成键数增长；
3. 写调用被 `void` 掉、没有 `.catch`，失败只以未处理异常出现，不进入任何用户可见路径；
4. 触发落盘的事件是「每个会话都会收到」的广播状态，而不是「这个会话真的有内容」。

## 方法

- **先量再猜**：`chrome.storage.local.getBytesInUse(null)` 对比 `QUOTA_BYTES`；`get(null)` 后按键值大小排序找最大键。
- **落盘要有上界**：按字节从最新往回取到预算为止，并保证非空历史至少留下最新一条。
- **键数要有上界**：按 `updatedAt` 只保留最近 N 个实体的键；旧格式（无时间戳）按最旧处理。
- **无内容不落盘**：只有广播状态、没有实际内容的记录不写盘，从源头掐掉键扇出。
- **清理合并触发**：写入频繁时把清理合并成一次延后动作（本例 5 秒去抖），不要每次写都全量读一遍存储。
- **失败留痕**：写调用带 `.catch` 并打日志。

## 单位陷阱（本次实际踩到并改正）

`JSON.stringify(value).length` 是**字符数**，不是字节数。storage 配额按 UTF-8 字节算，
中文一个字占 3 字节 —— 用字符数当预算会让实际占用达到预算的 3 倍。
计量用 `new TextEncoder().encode(json).length`（Node 与 Service Worker 都可用）。

## 适用条件

「配额受限 + 按实体分键 + 事件驱动落盘」的持久化都适用：`chrome.storage.local`（10 MB）、
按用户或会话分片的 KV、有容量上限的本地缓存。文本以中文为主时，单位陷阱必然触发。

不适用：没有配额上限，或每次落盘整体重写同一份快照的存储。

## 验证

- 修前：10,485,715 / 10,485,760 字节；后台持续 `Resource::kQuotaBytes quota exceeded`。手工清空释放 9.99 MB，
  写自检由失败转成功；清空前把 108 个键原样备份为 9.85 MB 文件（`~/.sideagent/backups/panel-history-2026-09-10T15-46-13.jsonl`）。
- 中间态（只做启动时清理）：连上瞬间键数 8 → **124**、用量到 590,761 字节，5 秒后才回落 —— 证明清理时机不够。
- 修后：连续 40 秒稳定 **8 键 / 60,216 字节**；运行中的 `background.js` 与构建逐字节一致。
- 定向测试 14 项、全量 136 文件 1127 项、`npm run typecheck`、`npm run build` 通过。

证据：[panel-history-quota 验收](../../../docs/evals/20260910-panel-history-quota.md)（含三段对比与中间发现）。
