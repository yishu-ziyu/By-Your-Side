# 文档维护

[文档导航](../README.md) · [项目规则](../../AGENTS.md) · [检查命令](checks.md)

## 写到哪里

项目自有说明统一进入 `docs/`。根 README 只给概览与导航；AGENTS 只放开发约束与入口。工具自动加载的入口、随第三方源码保留的来源说明、锁定评测原件不应为整理而搬走；准确例外清单在[文档策略](../documentation-policy.json)。新增例外应解释真实的路径依赖。

| 内容 | 唯一归属 |
|---|---|
| 现在做到哪里、已知缺口、下一步 | [STATUS](../STATUS.md) |
| 安装步骤与配置 | [源码安装](../guides/getting-started.md) |
| 用户如何操作、数据与权限 | [使用说明](../guides/usage.md) |
| 模块边界与设计理由（精确接口看代码） | [架构](../architecture.md)、[协议](../protocol.md)及对应专题 |
| 方向变化的理由 | [路线](../ROADMAP.md)、[开发日志](../devlog/) |
| 任务施工、标准、失败、验证 | [任务书](../tasks/)、[验收记录](../evals/) |
| 可复用的已验证教训 | [经验库](../knowledge/index.md) |

一个事实只维护在一个权威位置。代码是接口、常量和流程的唯一权威；文档解释理由并链接代码，不手抄第二份。STATUS 引用验收结论，不复制整份日志。

## 渐进式披露

先概览，再按问题链接到细节。新文档应能从对应入口或主题页找到，并给出相关说明或返回入口。已有文档能容纳同一主题时直接更新，避免不断新增相近文件。

篇幅预算以策略文件为准，同时限制字符数和行数；入口比专题更短。超出时按独立问题拆分，原页留下地图和链接，不删约束、不压成长行规避检查。

历史原件保留原始结论和失败，不为了篇幅改写证据。旧 STATUS/NOTES 的原文快照作为文本放入 `history/`，避免里面的旧标题、旧路径和“下一步”继续充当导航；日常只通过短索引访问。新结论写在对应主题，不继续堆进历史快照。

## 每次功能修改

核心原则：代码能还原的别写进文档（来源：[The Death of Documentation](https://prefactor.tech/blog/the-death-of-documentation)、[Docs in the Coding Agent Era](https://nyosegawa.com/en/posts/docs-in-agent-era/)）。判断方法：读代码（含类型、测试、配置）能不能得出这句话？能，就删掉或换成代码链接。

| 不写（以代码为准） | 要写（代码还原不了） |
|---|---|
| 常量与阈值、接口字段、消息清单、函数和文件名、执行步骤 | 为什么这样设计、放弃了哪些方案 |
| 某函数“负责”什么的逐条复述 | 用户能看到的行为和边界 |
| 测试覆盖了哪些情况 | 现在做到哪、已知缺口、下一步 |
| | 实测结论、踩过的坑、外部服务的事实 |

改功能时，只有右栏的事实变了才更新对应文档；左栏随代码走，文档不跟。纯重构通常不必动文档。验证后把施工中得出的长期结论回到归属处，任务记录保留证据并引用它。收尾运行 `npm run check:docs`。

## 写法

当前说明按 [ASD-STE100](https://asd-ste100.org/) 的精简技术写作改写。规则来源是 [hai-simplified-technical](https://github.com/hylarucoder/hai-stack/tree/main/skills/hai-simplified-technical) 的中文规则。该技能不装进项目，也不装进技能目录。

1. 下载技能目录到临时位置，例如 `/tmp/hai-st`。
2. 写或改之前，读 `SKILL.md` 的规则速览；拿不准时读 `references/rules-zh.md`。
3. 用词按[术语表](../glossary.md)。新概念先补术语表，再写正文。
4. 写完运行 `python3 /tmp/hai-st/scripts/check.py --lang zh <文件>`。硬规则全改；软规则不改时，应有理由。

脚本只报出要看的地方，不判断对错。历史记录（`historicalPrefixes`）保留原文，不按本规则改写。

## 检查的能力与边界

检查器复用仓库已有的 Marked 解析 Markdown：检查文档位置、当前说明篇幅、相对文件链接和 HTML 图片路径；不检查代码与文档是否同步。代码块中的示例不当成真实链接。

验收文件以 `docs/evals/YYYYMMDD-<任务名>.md` 的日期为创建日期。`20261004` 及以后应包含二级章节 `## 规则`、`## 技术前提`，未提交、暂存和已提交文件均检查。正文提及、代码块示例或其他层级标题不算章节。旧记录不追补；规则、正反例、未答问题与技术前提的模板见[项目规则](../../AGENTS.md#完成标准格式)。机器只查这两个章节，不证明例子充分或问题已清零。红绿验证见[验收记录](../evals/20261003-eval-format.md)。

历史记录不参与当前篇幅门槛；`--all` 额外扫描其文件链接并输出完整提醒清单，历史缺页只报告，不能据此宣称历史证据完整。本机 `out/` 验收输出与仓库外路径不要求干净 clone 携带。网页链接、`#片段` 锚点、文本是否准确反映实现仍需人工复核。

文件被修改不证明内容真的同步。每个 PR 和里程碑，维护者应从真实用户入口复核以下四项：

- 说明是否仍正确
- 同一事实是否重复
- 历史待办是否混入当前状态
- 任务结论是否回流

复核记录写回本次验收，不再新建一套状态记录。

## 经验库迁移

经验库已由 `.kimi-code/wiki/` 移到 `docs/knowledge/`，现有角色与 hook 只同步资料路径。旧 hook 的项目门控和启用状态保持原样，本轮不激活后台模型复盘。原会话轨迹、锁和本地日志不是项目说明，不因目录整理自动复制或上传；新旧轨迹目录和锁文件都保留在 `.gitignore` 中。
