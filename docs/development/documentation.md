# 文档维护

[文档导航](../README.md) · [项目规则](../../AGENTS.md) · [检查命令](checks.md)

本页是文档规则的唯一归属。AGENTS 只留短规则和本页链接。

## 写到哪里

- 项目说明统一放 `docs/`。根 README 只给概览与导航；AGENTS 只放开发规则与入口。
- 工具自动加载的入口、第三方来源说明、锁定评测原件留在原位。例外清单只在[文档策略](../documentation-policy.json)登记。
- 新增例外时，写明这个例外依赖的真实路径。

| 内容 | 唯一归属 |
|---|---|
| 现在做到哪里、已知缺口、下一步 | [STATUS](../STATUS.md) |
| 续接时容易误判的结论 | [NOTES](../NOTES.md) |
| 安装步骤与配置 | [源码安装](../guides/getting-started.md) |
| 用户如何操作、数据与权限 | [使用说明](../guides/usage.md) |
| 模块边界与设计理由 | [架构](../architecture.md)、[协议](../protocol.md)及对应专题 |
| 方向变化的理由 | [路线](../ROADMAP.md)、[开发日志](../devlog/) |
| 任务施工、标准、失败、验证 | [任务书](../tasks/)、[验收记录](../evals/) |
| 可复用的已验证教训 | [经验库](../knowledge/index.md) |

- 一个事实只放一个权威位置。其他文档链接过去，不另抄一份。
- STATUS 是当前进度的唯一入口。STATUS 写当前结论、未决问题、下一步和证据链接。
- 新结论替换 STATUS 里的过期状态。历史内容明确标为历史。
- 验收文件保留原始标准、修订依据和实测证据。STATUS 引用验收结论，不复制整份日志。

## 代码是权威

核心原则：代码能还原的别写进文档。
来源：

- [The Death of Documentation](https://prefactor.tech/blog/the-death-of-documentation)
- [Docs in the Coding Agent Era](https://nyosegawa.com/en/posts/docs-in-agent-era/)

判断方法：读代码（含类型、测试、配置）能得出这句话吗？能，就删掉或换成一个代码链接。

| 不写（以代码为准） | 要写（代码还原不了） |
|---|---|
| 常量与阈值、接口字段、消息清单 | 为什么这样设计、放弃了哪些方案 |
| 函数名、文件清单、执行步骤 | 用户能看到的行为和边界 |
| 脚本头已写的命令参数 | 现在做到哪、已知缺口、下一步 |
| 测试覆盖了哪些情况 | 实测结论、踩过的坑、外部服务的事实 |

- 改功能时，只有右栏的事实变了才更新文档。左栏随代码走，文档不跟。
- 没变就不动文档，不为凑同步改一行。纯重构通常不动文档。
- 发现文档在抄代码，顺手删掉。
- 验证后，把长期结论写回归属处。任务记录保留证据并链接过去。
- 收尾运行 `npm run check:docs`。

## 渐进式披露

- 入口只给概览和链接，细节放对应小文档。
- 新文档要能从入口或主题页找到，并链接回入口。
- 已有文档能容纳同一主题时，更新已有文档，不新增相近文件。
- 篇幅预算以[文档策略](../documentation-policy.json)为准，同时限字符数和行数；入口比专题更短。
- 超预算就按独立问题拆分，原页留下链接。不删约束，不把段落压成长行规避检查。

## 历史记录

- 历史原件保留原始结论和失败。不为篇幅改写证据。
- 旧 STATUS/NOTES 的原文快照放 `history/`，日常只经短索引访问，因为快照里的旧标题、旧路径和旧“下一步”不能再充当导航。
- 新结论写在对应主题，不堆进历史快照。

## 写法

当前说明按 [ASD-STE100](https://asd-ste100.org/) 精简技术写作。目标是消除歧义和含糊，让读者不会误读：

- 一个词只有一个意思，全文一致。用词按[术语表](../glossary.md)。
- 每句只有一种读法：主语明确，指代明确（不写指向不清的“它、这、该”），用具体词代替含糊词。
- 写明谁做什么。事实和推测分开写，结论在前。
- 短句和一句一事只是手段。不能为缩短句子省略词语，也不能删掉“因为、所以、但是、除非、只有…才”这类承载逻辑的连接词。
  一句话保留原因和结果，好过拆成两段让读者自己重新连起来。

规则来源是 [hai-simplified-technical](https://github.com/hylarucoder/hai-stack/tree/main/skills/hai-simplified-technical) 的中文规则。
这个技能用时临时下载，不装进项目，也不装进技能目录。

1. 把技能目录下载到临时位置，例如 `/tmp/hai-st`。
2. 写之前读 `SKILL.md` 的规则速览；拿不准时读 `references/rules-zh.md`。
3. 用词按[术语表](../glossary.md)。新概念先补术语表，再写正文。
4. 写完运行 `python3 /tmp/hai-st/scripts/check.py --lang zh <文件>`。硬规则全改；软规则不改时要有理由。

脚本只指出要看的地方，不判断对错。历史记录（策略文件的 `historicalPrefixes`）保留原文，不按本规则改写。

## 检查的能力与边界

`npm run check:docs`（[脚本](../../scripts/maintenance/check-docs.mjs)）检查文档位置、篇幅、相对文件链接和图片路径，但不检查代码与文档是否同步。

- 验收文件按文件名日期算创建日期。`20261004` 及以后的验收文件必须有二级章节 `## 规则` 和 `## 技术前提`。
  `20261004` 以前的旧验收文件不追补这两个章节。
- 检查脚本只查这两个章节是否存在，不证明例子充分或问题已清零。模板见[项目规则](../../AGENTS.md#完成标准格式)，红绿验证见[验收记录](../evals/20261003-eval-format.md)。
- 历史记录不受篇幅限制。`--all` 另报历史缺页，但不能据此宣称历史证据完整。
- 网页链接、`#片段` 锚点、文字是否反映实现，仍由人复核。

文件被修改不证明内容同步。每个 PR 和里程碑，维护者从真实用户入口复核四项，记录写回本次验收：

- 说明是否仍正确
- 同一事实是否重复
- 历史待办是否混入当前状态
- 任务结论是否回流
