## 写到哪里

| 内容 | 唯一位置 |
|---|---|
| 现在做到哪里、已知缺口、下一步 | [STATUS](../STATUS.md) |
| 安装与使用 | [源码安装](../guides/getting-started.md)、[使用说明](../guides/usage.md) |
| 设计理由与边界 | `docs/` 下的专题文档，入口见[文档导航](../README.md) |
| 新功能、换方向的标准与证据 | `docs/evals/YYYYMMDD-<任务名>.md` |
| 修 bug、改开发环境的标准与证据 | PR 描述 |

- 一个事实只放一处，其他地方链接过去。
- STATUS 只在更新日常扩展或换方向时更新，单个 PR 不改它，因为逐个 PR 改会让它不停变长、不停压缩。
- 截图和录屏留在 `out/`，不提交。要给人看的放进 `assets` 分支，不合并进 main。

## 代码能还原的不写

判断方法：读代码（含类型、测试、配置）能得出这句话吗？能，就删掉。

| 不写 | 要写 |
|---|---|
| 常量、阈值、字段、消息清单 | 为什么这样设计，放弃了什么 |
| 函数名、文件清单、执行步骤 | 用户看到的行为和边界 |
| 命令参数、测试覆盖了什么 | 现在做到哪、缺口、踩过的坑 |
| 哪天改了什么 | 外部服务的事实（如计费通道） |

- 只有右栏的事实变了才改文档。纯重构不动文档。
- 发现文档在抄代码，就删掉。
- 改了文档就跑 `npm run check:docs`。

## 写法

按 [ASD-STE100](https://asd-ste100.org/) 写：

- 一个词一个意思，用词按[术语表](../glossary.md)。
- 每句一种读法：主语明确，不写指向不清的“它、这”。
- 事实和推测分开，结论在前。
- 不为缩短句子删掉“因为、所以、但是、除非、只有…才”。

## 验收文件模板

只给新功能和换方向。规则超过 4 条就拆成几项任务。还有问题没答上，就先不实现。

```markdown
# 任务: <一句话，用户能观察到的结果>

## 规则
- R1 <一句话规则>
  - 例子(正)：在…情况下，当…时，那么… — 谁检查：<命令>/人
  - 例子(反)：… — 谁检查：<命令>/人

## 还没答上的问题
- Q1 …（清零后写“无”）

## 技术前提
- 前提：… 小实验：<≤50 行脚本路径> 结果：通过/失败

## 边界与不做
- <明确的非目标>
```

## 检查管什么

`npm run check:docs` 查文档位置、篇幅、相对链接和图片路径，也查验收文件有没有“规则”“技术前提”两节。它不查文档内容和代码是否一致，这一项由人在每个 PR 复核。
