# 帕累托爬山

一次改一处，目标指标证明变好、其余指标证明没变差，才装进日常扩展；装上的版本就是下一步的起点。用户定的原则：「在不损耗其他指标的情况下，使特定指标得到极致优化」。

「证明」由 `npm run climb -- <登记文件>` 判，不由写代码的代理判。判定规则在 `scripts/maintenance/climb-rules.mts`，下面只写为什么这样定、放弃了什么。

## 一步怎么走

1. **定痛点**：从任务池（用户原话）和 `npm run logs` 里按「出现次数 × 每次损失（秒或误判）」排，先用一句用户体验的话说清（如「搜一下就提示网站已收到」），写下预期收益。
2. **尺子对齐日常**：回放的主模型、快速模型、思考档位和日常扩展一样，否则会造出假痛点（快速模型配错时，「翻译当前页面」被记成做不完，照日常配置 93 秒译完）。
3. **冻结两份构建**：改前、改后都在工作树里用 `SIDEAGENT_BUILD_DIST` 预先构建，跑判定期间改代码不影响它们。
4. **开跑前登记**（`out/hill-climb/steps/<名字>.json`，格式见 `climb.mts` 开头）：场景、目标和最小有意义改进、每个守护允许变差多少、红线用例、样本量 N、预算。登记文件的哈希记进账本，跑后不改。
5. **跑判定**：`npm run climb -- out/hill-climb/steps/<名字>.json`，输出三态之一，追加一行到 `out/hill-climb/ledger.jsonl`。
   - **通过**：目标证明变好、守护全部证明没变差、红线全过 → 合并，更新日常扩展（先备份上一版），这一版成为新起点。
   - **否决**：红线改后失败，或做成显著变少 → 补丁和证据存进 `out/archive/`，写清原因。
   - **证据不足**：其余情况，包括配对不全、模型配置不一致、预算用完。保留当前版。不改名叫「无差别」，不追加样本直到恰好通过，也不拿机制解释替没过的守护签字。

## 判定规则为什么这样定

- **尺子先要对**。「做成」= 跑完、没报错、卡片没写没做成、没换目标、有回答，而且任务池里登记的结果断言（`expect`）也过。只看流程跑完会奖励答错：曾经有一版把「首页没有推荐，就去搜 AI 点第二个」记成完成。用时取发出到最终交付（含核对和续做），只看第一次回答会奖励早交不可靠的回答。往返、核对结论、换目标都按 runId 归回原句，核对晚到落进下一句的记录时也算回原句。
- **固定样本、最后只判一次**。看一眼不过就加样本、过了就停，会抬高误接受率（只在第 10 次判约 5%，在 3、6、10 次都判约 10%）。提前停只因为红线或做成显著变少。
- **精确符号检验，配对单位是场景**。耗时偏态、长尾，小样本下不假设正态。一个场景里的续句共享会话和页面，不拆成独立样本。每对两版紧挨着在同一台机器上跑，先后顺序按 seed 随机。
- **目标要越过登记的最小改进 Δ**，不是只要比 0 好：防止把噪声里的小波动装进日常。
- **守护的界线是产品能容忍的损失，不从噪声推出来**。界线跟着噪声放大，测得越不准越容易通过。噪声只决定要多少对样本，样本不够就是证据不足。
- **「做成」守护要求一次新增失败都没有**；新增失败和修好分开数，不拿总数相抵。N 对里没见到新增失败，只说明新增失败概率的单侧 95% 上界是 1−0.05^(1/N)（10 对约 26%），报告里写出这个数。这是有意接受的弱点：严格要求「证明不会更差」时任何改动都过不了；长期锚点用更多样本补这块。
- **机制目标**：只在部分运行里出现的故障，修好后不可能在大多数配对里都看到变好。这类改动用一个确定能复现的脚本用例当目标：改前每次失败、改后每次通过。它只证明这一处故障不再发生，守护仍然用真模型配对来判。
- **多个守护不按个数拆 α**：所有守护都要过，本身就是更严的要求。真正抬高误接受率的是同一个痛点反复试候选、挑最好的那个；同一轮确认 K 个候选时，α 用 0.05/K。

## 防累计退化和过拟合

- **长期锚点不随新基线清零**：每装 5 步，当前版和锚点同期跑一次；累计变差超出界线时先停止装新版本，再比较相邻构建找原因。
- **新任务确认**：候选是看着任务池调出来的，所以每过一段时间，用 `npm run logs` 里新出现的用户原话做一次确认；看过结果的任务并入任务池。
- **同一个痛点连续 3 步判不出来**：先看是尺子坏了、样本不够，还是做法本身不行，再决定要不要换结构性做法。结构性做法可以同时做 2–3 个原型，各自走同一套判定；互不支配的几个候选列成取舍交给用户，不用噪声排名硬选一个。
- 必须拿一个指标去换另一个指标的改动不装，列成取舍交给用户。

## 容易踩的坑

- 守护用例失败，先在改前的构建上跑同一条：一样失败就是原有问题或检查过时。真实结果对、检查写错时修检查，不改产品。
- 拿不准的取舍派一个代理做反方，辩完再定。替用户做设置层面的决定（默认换模型、绕过服务商审核）不做，列成提议交给用户。
- 宿主有确凿事实时，用宿主规则代替模型判断（按钮点两次没反应、播放器字幕清单为空）；没有确凿事实时，往提示词里加规则或强制续做多半无效，真模型配对会暴露这一点。
- 机器 1 分钟负载 ≥ 20 时不开跑，判定器自己会等。
