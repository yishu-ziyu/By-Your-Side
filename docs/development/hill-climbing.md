# 帕累托爬山

一次改一处、量一次，目标指标变好且其他指标都不变差才装进日常扩展，装上的版本就是下一步的起点。10-24 用户定：「在不损耗其他指标的情况下，使特定指标得到极致优化」。

## 一步怎么走

1. **定痛点**：从用户原话的任务（每晚回放的任务池）和 `npm run logs` 里找耗时、模型往返、工具报错、核对续做集中的地方，先用一句用户体验的话说清（如「搜一下就提示网站已收到」）。
2. **尺子先对齐日常**：回放的主模型、快速模型、思考档位要和日常扩展一样，否则会造出假痛点。10-24 回放的快速模型配成了 MiniMax，「翻译当前页面」被记成做不完；照日常配置 93 秒就译完。
3. **冻结基线**：`npm run check` 之后把 `extension/dist` 复制一份当改前；候选在任务工作树里用 `SIDEAGENT_BUILD_DIST` 构建。
4. **两层证据**：
   - 真实路径用例（脚本模型）证明机制：改后过、改前失败。
   - 真模型对照证明体感：`npx tsx scripts/maintenance/replay-ab.mts --base=<改前> --cand=<改后> --only=<任务> --runs=3`，两边交错，负载低于 20 才开跑。同一份构建单次用时也能差两三倍，单次不算数；差异在噪声里时看机制证据，例如两版交给模型的输入是否逐字相同。
5. **接受**：目标变好，守护指标（准确与完成、等待、往返与用量、界面干扰、停止与隐私边界）没有一项变差。合并后照常更新日常扩展：先备份上一版，核对加载的文件指纹。
6. **否决**：目标没变好或拿别的指标换来的，不合并；补丁、用例和证据存进 `out/archive/`，在 PR 或记录里写清原因。

## 容易踩的坑

- 守护用例失败，先在改前的构建上跑同一条：一样失败就是原有问题或检查过时。真实结果对、检查写错时修检查，不改产品（10-24：「连接被拒绝」「仍显示第 1 页」「留给你的连成一句念」都是检查过时）。
- 拿不准的取舍派一个代理做反方，辩完再定。替用户做设置层面的决定（默认换模型、绕过服务商审核）不做，列成提议交给用户。
- 宿主有确凿事实时，用宿主规则代替模型判断（按钮点两次没反应、播放器字幕清单为空）；没有确凿事实时，往提示词里加规则或强制续做多半无效，真模型对照会暴露这一点。
