# 协作方式

用户与代理怎样一起做事。开工、汇报、分工的规则在 [AGENTS.md](../../AGENTS.md)，本页只补充细节。

## 流程

| 改动 | 开工前 | 做完 |
|---|---|---|
| 新功能、换方向 | 一句话对齐“用户现在遇到什么 → 做完看到什么”；界面类再给一个可上手试的预览。用户认可后开工 | 用户看得到的变化，需要判断时开 cmux 页面 |
| 修 bug、改开发环境 | 不确认，直接做 | 一次相关检查后合并，关 issue，三行以内说结果 |

- 认可之后不再逐步审批。调研只在用户要求、或一线产品的做法会改变方案时做。
- 实现可拆成约 15 分钟一块，各自验收，并行交给子代理；设计和视觉由主会话自己做。
- 每轮排期至少带一项提速或准确，并写清提速对准确的代价。

## 预览的标准

- 看起来就是用户每天用的产品：侧栏用真实侧栏的结构和样式表，网页用真实网页。不另画一套。
- 能上手试：核心交互真的能点、能画、能撤销。
- 产品里会动的地方，预览也动：光标轨迹、笔画、逐字出现。设计本身静止的才做成静止。
- 给用户之前，代理先在浏览器里跑一遍、看截图，确认不比真产品粗糙。
- 只在本机打开，不发布成需要登录才能看的页面。
- 预览是临时的本机文件，不提交进仓库；认可后以实际产品为准。

## 为什么这样做

- 用户看画面比看文字判断得准，所以界面类改动用预览对齐，认可的预览就是规格。
- 每一步都等审批、每次都跑大测试，用户等得比开发还久。所以只有方向性的改动才先确认。

## 给用户看的进展（Linear）

进展只在 Linear 的 [By Your Side 项目](https://linear.app/yishuyuki/project/by-your-side-9d77250909c0)更新。

| 状态 | 含义 |
|---|---|
| In Progress | 正在做 |
| In Review | 已修好并验证，尚未装进日常扩展；或需要用户亲手试 |
| Done | 已装进日常扩展 |
| Todo / Backlog | 排队 |

- 每个任务按「以前 → 现在 → 没验到的」写。用产品语言，不写提交号与测试术语。技术证据给 PR 或验收文件链接。
- 用户要求充分展示：有可见变化时附实际截图或录屏，注明来源与场景。需要用户试的，写清在哪试、怎样算好。
- 阶段变化时，在任务下补一句进展。装进日常扩展后才移到 Done。
- Linear 只做展示。项目事实以 [STATUS](../STATUS.md) 为准。
- GitHub 提案和 Linear 任务不自动同步。需要对应时，手动互相加链接。
- PR 标题写上任务号（如 YIS-85），Linear 会自动挂上这个 PR 并改任务状态。

## 分工与排期（Linear）

任务按标签分执行者。排期按 Linear 每周一个周期。

- 「Claude」：拆任务、写完成标准、查根因、产品判断、设计与最终验收。
- 「Codex 可领」：只给规格清楚、写明文件范围与检查命令的实现任务。
- 「要你来」：需要用户亲手试、拍板或授权的事。

Codex 用本机 CLI（已接 Linear），在单独的 git worktree 和分支里完成。交回后由 Claude 验收，再合入 main。
Codex 不与 Claude 同时改同一文件。浏览器验收由 Claude 错开安排。

只存图的远端分支：`design-refs`（#53 引用）、`ux-walkthrough-1007`（#102–#106 引用）。

- issue 直接引用这两个分支上的图片，所以删分支会让 issue 里的图裂开。
- 这两个分支不合并，不再提交。引用某个分支的 issue 都关闭后，才删这个分支。

## 汇报：BDD 与 OOPSI

按「目标 → 可见结果 → 产生结果的流程 → 具体场景 → 输入与前提」组织。
来源：[OOPSI 原方法](https://jennyjmar.com/2016/04/16/bdd-discovery-and-oopsi/)。短汇报不强制写成长文或讲解术语。

- 先说用户能得到什么，再说现在能看到什么；排期和下一步由代理负责。
- 场景用「假如／当／那么」，同时看正常、失败和边界；通过、失败、未跑分开。
- 写好代码、完成回复、合入规格文档或关闭票，都不能代替真实场景完成。
- 工作包按用户结果计数，子任务与检查不重复算功能。项目队列不自动成为本轮实现范围。
- 预览用于讨论，实际画面用于交付。最新排期在 Linear，事实依据与未决项仍由 STATUS 导航。
