# 协作方式

用户与代理一起做新功能的固定流程（2026-10-07 用户定）。

- 目标：用户看见、试过、认可之后才写代码；做完的东西用户马上能用上。
- 不认为现有做法已经够好。每一轮都找下一处可以改进的地方。

## 流程

1. **意图**：代理用两三句说明要解决什么、用户会看到什么变化。用户回「yes」才过关。
2. **调研**：代理派短调研，可并行。产出一线产品的做法：几条值得学，几条要避开。用户读完要点才过关。
3. **预览**：代理亲手做 `docs/previews/<名>/` 的本机页面，在 cmux 右侧打开。用户上手试过并认可才过关。
4. **排期**：代理在 Linear 建一个总任务，按独立结果拆小任务。每个小任务要有独立验收。
5. **实现**：小任务交给子代理，约 15 分钟一个，交回代码和一个快速检查。另一方核对，`npm run check` 和 `npm test` 都通过后合并。
6. **跟进**：代理在 Linear 按[进展写法](#给用户看的进展linear)更新。做完就关；落后的排期挪走或关掉。
7. **汇报**：代理按 [BDD 与 OOPSI](#汇报bdd-与-oopsi) 从用户结果讲。不用技术日志代替进展；任务编号只帮助定位。

## 预览的标准

- 看起来就是用户每天用的产品：侧栏用真实侧栏的结构和样式表，网页用真实网页。不另画一套。
- 能上手试：核心交互真的能点、能画、能撤销。
- 产品里会动的地方，预览也动：光标轨迹、笔画、逐字出现。设计本身静止的才做成静止。
- 给用户之前，代理先在浏览器里跑一遍、看截图，确认不比真产品粗糙。
- 只在本机打开，不发布成需要登录才能看的页面。
- 认可后，预览连同拼好的 `index.html` 留在仓库里，便于以后对照（10-07 用户定）。
- 例子：[圈给它看与记忆露出来](../previews/circle-and-memory/index.html)，由 `build.py` 拼入真实侧栏。

## 为什么这样做

- 用户看画面比看文字判断得准。文字规格写得再细，也会和用户心里想的不一样。
- 预览就是规格：认可的预览定下要做成什么样，小任务的验收都对照它。
- 大任务交给一个执行者，会一跑半小时没有音讯。拆成小任务并各自验收后，用户每一步都看得到进展。

## 给用户看的进展（Linear）

进展只在 Linear 的 [By Your Side 项目](https://linear.app/yishuyuki/project/by-your-side-9d77250909c0)更新。
10-04 用户决定用 Linear 取代临时本机工作页 `127.0.0.1:8894`；本机工作页的[验收](../evals/20261003-local-workbench.md)保留为历史。

| 状态 | 含义 |
|---|---|
| In Progress | 正在做 |
| In Review | 已修好并验证，尚未装进日常扩展；或需要用户亲手试 |
| Done | 已装进日常扩展 |
| Todo / Backlog | 排队 |

- 每个任务按「以前 → 现在 → 没验到的」写。用产品语言，不写提交号与测试术语。技术证据只给仓库验收文档路径。
- 用户要求充分展示：有可见变化时附实际截图或录屏，注明来源与场景。需要用户试的，写清在哪试、怎样算好。
- 阶段变化时，在任务下补一句进展。装进日常扩展后才移到 Done。
- Linear 只做展示。项目事实仍以 [STATUS](../STATUS.md) 与验收记录为准。
- GitHub 提案和 Linear 任务不自动同步。需要对应时，手动互相加链接。
- PR 标题写上任务号（如 YIS-85），Linear 会自动挂上这个 PR 并改任务状态（10-07 实测）。

## 分工与排期（Linear）

任务按标签分执行者（10-04 用户确认）。排期按 Linear 每周一个周期。

- 「Claude」：主导拆任务、写完成标准、查根因、产品判断与最终验收。
- 「Codex 可领」：只给规格清楚、写明文件范围与检查命令的实现任务。
- 「要你来」：需要用户亲手试、拍板或授权的事。

Codex 用本机 CLI（已接 Linear），在单独的 git worktree 和分支里完成。交回后由 Claude 验收，再合入 main。
Codex 不与 Claude 同时改同一文件。浏览器验收由 Claude 错开安排。

只存图的远端分支：`design-refs`（#53 引用）、`ux-walkthrough-1007`（#102–#106 引用）。

- issue 直接引用这两个分支上的图片，所以删分支会让 issue 里的图裂开。
- 这两个分支不合并，不再提交。引用某个分支的 issue 都关闭后，才删这个分支。
- 10-07 用户确认删掉只被已关闭 issue 引用的 4 个分支。旧 issue 里的图从此裂开。

## 每轮都带一项提速或准确

提速和准确是长期工程。每次排期至少放一项，同样走上面的流程，并写清这项提速对准确的代价。资料见[提速调研](../research/20261007-browser-agent-speed.md)。

## 汇报：BDD 与 OOPSI

2026-10-08 用户指定。按「目标 → 可见结果 → 产生结果的流程 → 具体场景 → 输入与前提」组织。
来源：[OOPSI 原方法](https://jennyjmar.com/2016/04/16/bdd-discovery-and-oopsi/)。短汇报不强制写成长文或讲解术语。

- 先说用户能得到什么，再说现在能看到什么；排期和下一步由代理负责。
- 场景用「假如／当／那么」，同时看正常、失败和边界；通过、失败、未跑分开。
- 写好代码、完成回复、合入规格文档或关闭票，都不能代替真实场景完成。
- 工作包按用户结果计数，子任务与检查不重复算功能。项目队列不自动成为本轮实现范围。
- 预览用于讨论，实际画面用于交付。最新排期在 Linear，事实依据与未决项仍由 STATUS 导航。
