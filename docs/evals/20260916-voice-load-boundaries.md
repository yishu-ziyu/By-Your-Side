## 当前系统实测

[完整结果](20260916-voice-load-boundaries/baseline.json)：6 文件、92 项通过。新增 baseline 用例通过表示复现了当前限制，**不表示多任务体验通过**。

| 场景 | 实际结果 | 判断 |
|---|---|---|
| 原任务运行，连续三个独立请求 | 三次 clarify，三条 rejected 回执；仍只有原会话 | 没有独立要求待办队列；不是容量已满后排队 |
| 12 个不同会话请求同送 dispatcher，执行回调全部阻塞 | 12 个回调均能进入 | dispatcher 没有全局准入上限；不代表真实模型支持12并发 |
| 20 条普通请求积压时提交 abort | 控制通道可先执行；回调重验任务状态后拒绝后续旧请求 | 保留控制优先通道；测试回调的重验不是 dispatcher 自身的取消能力 |
| 生产 Pi/session 连续纠正、预观察中暂停/终止、失败清理 | 既有12项检查通过 | 保留当前版本检查及未消费要求处理 |
| 页面归属与移交 | 8项页面控制、34项控制闸门检查通过 | 已有保护；拒绝冲突并不等于具有自动等待调度 |
| 第二会话结果回到第一会话的语音 | 被过滤；同会话结果可送达 | 不能仅自动新建会话就宣布支持多任务语音 |
| 一次排入40条正式结果 | 只留最后32条，最早8条无丢弃回执 | 超载静默丢结果；不能仅增加数组长度 |

## 修改决定

见[多要求调度设计](../voice-multi-request-design.md)。先落实要求登记和交付归属，再接入有界执行准入。保留现有 TaskDispatcher 的去重、执行回执、控制优先能力，以及浏览器资源归属保护。不能靠放开 running 检查或订阅所有会话来实现。
