# 任务: 解释、翻译、找东西三个即时动作，页面在 2 秒内出现第一块变化

来源：[即时动作基线](20260926-instant-baseline.md)（解释 12.6 s、翻译当前一屏 24.7 s、「价格在哪」5 轮 4 轮页面不动），用户 2026-09-26 定目标为 2 秒内，并选择在设置里加「快速模型」给即时动作用，主模型不变。

## 完成标准

- [x] 1. 设置页有「快速模型」一项，只列已配置凭据的服务商的模型；选了就保存，不选沿用主模型；主模型或所选快速模型是阶跃时提示会很慢；还没填 key 的服务商可在服务商表单里点「用作快速模型」，主模型不变 — 谁检查: `instant-baseline.mts --fast-model=…`（经设置页选择）+ 人看截图
- [ ] 2. 划一句 →「解释」：第一行字出现 p50 ≤ 2 s（扣除无头环境的点击送达延迟）；快速模型失败时改用主模型答完，不把失败留给用户 — 谁检查: `instant-baseline.mts --only=explain`
- [ ] 3. 「把这页翻译成中文」：当前一屏第一段变中文 p50 ≤ 2 s — 谁检查: `instant-baseline.mts --only=translate`
- [ ] 4. 「价格在哪？」：页面在 2 s 内滚到并指出价格，5 轮都有页面变化 — 谁检查: `instant-baseline.mts --only=find`
- [x] 5. 没配快速模型时行为与改前相同（仍用主模型）；本机模式不受影响 — 谁检查: `npm test` + 对应入口
- [ ] 6. 用户在日常 Chrome 里试用后认可「即时」 — 谁检查: 人

## 边界与不做

- 不换主模型，不改阶跃的 Step Plan 计费通道；不做语音入口的即时化（另测）。
- 服务商首字延迟本身不在产品控制内；达不到时如实报告分布，不改目标。

## 修订记录

- **翻译入口改由快速模型判断（2026-09-26，用户裁决）。** 日常扩展里读不到 Jev 凭据，原计划的 Jev 判断不可用。三个备选（按钮 + 固定说法 / 设置里加 Jev 密钥 / 快速模型判断）中用户选快速模型判断，选项说明里已写明「当前一屏变中文大概 3–4 秒，达不到 2 秒」。第 3 条的 2 s 目标保留作记录，实测对照 2 s 与 4 s 两个数。

## 证据

### 第 1、2 条（2026-09-26）

- 快速模型 `zai-coding-cn/glm-5.3-flash`、主模型 `stepfun/step-3.7-flash`。模型接入：`ModelPort.fastModel`（`agent/src/agent-loop.ts`）由扩展按 `inproc_fast_model_config` 提供；阅读回答与翻译批次优先用它，且不开思考。
- 探针（Node，同一提示词，各 15 次）：智谱直连首字 p50 1.8 s、p90 3.0 s、15 次 4 次连接错误；OpenCode 的同一模型 p50 1.4 s、p90 4.9 s。阶跃 step-3.x 官方接口无法关闭思考，首字 2.7–7.5 s。
- 真实扩展 8 轮（设置页选择快速模型后）：第一行字 1.4–2.1 s 共 6 轮，另 2 轮 3.9、6.8 s，p50 2.04 s；从点击送达到发出请求约 0.04 s，其余全是服务商首字。
- 试过「同时发两次、先到者胜」：慢的轮次两路在同一时刻一起卡住（浏览器对同一服务商复用一条连接），压不住长尾，还使编码套餐额度翻倍，已撤回。
- 未加快速模型兜底前的 5 轮里有 1 轮连接在 10 s 后被断开；兜底后改用主模型答完（23 s），用户看到的是慢而不是失败。

### 第 3 条（2026-09-27 凌晨，未达标）

- 改动：`agent/src/translate-intent.ts` 在消息提到翻译或语言时用快速模型判断「是否现在翻译整页」，是则直接调用同一个 `page_translation` 工具并用回执写一句结果，不经主模型；判断超时（8 s）、否定或出错都交回主模型原流程。最先并行的 4 批每批只取 2 段（`PAGE_TRANSLATION_FIRST_BATCH_BLOCKS`），当前一屏分几路先落地。
- 实测（快速模型 `zai-coding-cn/glm-5.3-flash`，每轮全新无头 Chrome）：判断时限 4 s 时 5 轮 2 轮走快捷通道（6.3 s），3 轮判断超时回退主模型（14–22 s）；放宽到 8 s 后 5 轮 4 轮走快捷通道，当前一屏变中文 6.1、8.8、11.0、11.3 s，另 1 轮回退 27.0 s。改前 18.5–31.9 s。
- 瓶颈：快捷通道要先后两次调用快速模型（判断 + 第一批翻译）；这一时段智谱通道单次首字 1.3–7.6 s。结构下限约为两次首字之和。未做「判断与第一批并行」：它要在确认前不写页面，需要改翻译工具的执行与界面事件，暂未动。

### 第 4 条（2026-09-27 凌晨，未达 2 s）

- 改动：`agent/src/find-intent.ts` 在消息像「在哪、找一下」时读一次快照，快速模型一次调用返回 `{locate, ref, answer}`；编号必须出现在快照里才用 `mark` 圈（圈画会把页面滚过去），再把一句回答发给用户。否定、超时（8 s）或出错交回主模型。
- 实测 5 轮：4 轮页面滚到价格并圈出，2.8、3.9、4.9、7.0 s，回答如「Pro 计划价格为每月 $12（按年计费）」；1 轮快速模型 8 s 内没回，交回主模型只回文字。改前 5 轮 4 轮页面不动。耗时几乎全是那一次调用的首字（2.1–6.3 s）。[圈出后的页面](assets/20260926-instant-baseline/find-fast-marked.jpg)

### 第 5 条

- 干净工作树 `npm test`：284 个文件 3089 项通过，性能测试 2 项通过。
- 真实扩展不配快速模型各跑 1 轮：三个动作的模型请求全部发往 `api.stepfun.com`，解释、翻译、找东西都走改前的主模型流程（找东西仍只回文字）。

### 小结

| 动作 | 改前 | 现在（快速模型 = 智谱 GLM-5.3-flash） | 2 s 目标 |
|---|---|---|---|
| 解释出第一行字 | 12.6 s | p50 2.04 s | 未严格达到 |
| 当前一屏变中文 | 24.7 s | 走快捷通道 6.1–11.3 s，判断超时回退约 27 s | 未达到 |
| 页面指出价格 | 5 轮 4 轮不动 | 4/5 轮 2.8–7.0 s | 未达到 |

剩余时间几乎都在快速模型所用通道的首字上（这一时段 1.3–7.6 s，偶发断线）。

### 第 1 条补充（09-27）

- 服务商表单新增「用作快速模型」：只保存这家的 key 并设为快速模型。真实路径（设置页选智谱、填 key 和模型、测试连接、点按钮）：状态「已设为快速模型：智谱 GLM 编程版 · glm-5.3-flash。主模型不变。」，存储里快速模型为 `zai-coding-cn/glm-5.3-flash`、主模型仍为 `stepfun/step-3.7-flash`。
- 同一轮里智谱连接 5 s 后被重置，解释由主模型兜底答完（14 s）；凌晨这一时段该通道明显更慢，设置页测试连接也用了 9.2 s。

### 快速模型选型（09-27）

- 用户资源：阶跃、智谱、Kimi、MiniMax 的 Token Plan（富裕）；OpenCode Go 与 Command Code GOAT（按模型单价扣额度，官方给出每模型可调次数）。先按成本筛：Kimi K2.7 Code HighSpeed 在 Command Code 每月仅约 904 次、单价是 MiMo 的 14–28 倍，但在 Kimi Token Plan 里不受此限。
- 同一时段（09-27 上午）各 4 次，同一解释提示词：Kimi coding highspeed 出正文 1.2–1.7 s、写完 2.4–4.6 s；智谱 GLM-5.3-flash 1.2–1.8 s / 3.6–5.9 s；MiniMax M2.7-highspeed（少思考）2.1–3.7 s / 5.5–6.5 s；DeepSeek V4 Flash（OpenCode）1.3–8.0 s，回答常只有几十字。更早的夜间批次里 MiMo v2.6 flash（OpenCode、Command Code）4.9–5.4 s，DeepSeek V4.1 Flash 偶发 25–30 s，阶跃低思考 4.4 s。
- 选定快速模型为 Kimi coding highspeed（出字与智谱相当，整段写完快 1–1.5 s，翻译与找东西要等整段）。日常扩展已在设置页登录 Kimi 并设为快速模型。
