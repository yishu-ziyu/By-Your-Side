# 任务: 动作后不经模型核对，跑完后代码当裁判（YIS-113）

来由：axstream（桌面自动化工具）的三个做法——一批动作中间夹断言、动作后用「页面出现某段文字」核对、点击目标点时再核对；以及「观测是摄像机、评测是裁判」的分法（视频字幕 2026-10-08 用户提供）。用户 10-08 同意。对准长期的提速与准确工作：少一轮模型往返，失败处说得更准。

## 规则
- R1 browser_run 新增 `check`：等某段文字或唯一目标出现/消失，最多几秒，不叫模型；返回 true/false 和等了多久。
  - 例子(正)：点「提交」后 `check({ text: "已提交", timeoutMs: 3000 })` 在练习站 1 秒内返回 true — 谁检查：定点脚本（练习站）
  - 例子(反)：文字没出现，3 秒后返回 false，不抛错、不叫模型 — 谁检查：同上
- R2 browser_run 新增 `assert`：条件不成立就停下整个程序，返回停在第几步、名字、原因、已完成几步；侧栏那一步的 chip 标失败；后面的动作一个都不执行。
  - 例子(正)：第 2 步 assert 失败后，第 3 步的 click 没有发生，练习站服务器对应请求计数为 0 — 谁检查：定点脚本（服务器计数）
  - 例子(反)：assert 失败后程序继续点了下一步 — 不合格 — 谁检查：同上
- R3 `text=` 目标在点击/填写那一刻重新核对一次：文字不在了就不点，返回 TARGET_GONE，不点别的东西。
  - 例子(正)：定位后页面把按钮文字从「保存」改成「保存中…」，click 不执行，返回 TARGET_GONE — 谁检查：定点脚本
- R4 任务跑完后代码做三条确定性核对，写进回执折叠区一行「核对 n/3」，失败的条目一句话标出，不拦结果、不叫模型：(a) 每个失败的步骤都在回复里提到或已重试；(b) 回执里的数字（文件条数、改动处数）与记录一致；(c) 用户要求「保存」时恰好多出一个文件。
  - 例子(正)：一步 fetch 失败且回复没提，回执行写「核对 2/3 · 有一步失败没说」 — 谁检查：定点脚本（回放一条真实记录）
  - 例子(反)：三条都过，回执行只写「核对 3/3」 — 谁检查：同上
- Improve：日常会动手的任务每任务模型往返次数比 [时间拆分](20261007-time-breakdown.md) 基线下降；记下准确代价（check 误判率）。

## 还没答上的问题
- 无。R4(b) 的「数字」只认文件条数与回执里的改动处数，别的不比。

## 技术前提
- 前提：check 是现有 waitFor（text= 目标、visible 状态）的轮询变体；assert 的中断走程序宿主已有的停止路径（接管/中止会永久停下程序）。都已在代码里，不另做小实验。

## 边界与不做
- 不做 OCR 读屏（网页有 DOM 文字）。
- 不做宏录制与重放（[走老路对照](20261007-route-ab.md) 不到门槛）。
- 不替代模型的目标核对；代码裁判在前，模型裁判在后。
- 回执行只标不拦；拦截仍由现有的结果未知边界决定。

## 本轮结果（2026-10-08）

R1–R3 真实隔离扩展通过；R4 恢复原文件条数范围后，14 个场景通过。第一次只测文件数量的 8 项不能满足原 R4(b)。证据、红绿反例和默认真实模型冒烟见[续接验收](20261008-session-recovery.md)。未重载日常扩展。

保存、数量和失败披露只核对有权威记录的内容。没有改动处数记录时明确说无法核对，不拿工具成功次数代替。浏览器程序的脚本模型每任务仍为 3 次请求；这不是日常真实任务往返次数下降的证明。日常提速与任意文字的误判率尚无结论。
