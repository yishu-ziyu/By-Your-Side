# 任务: 在真实网站上，做成的任务不变少，用时和模型来回次数变少

来源：10-14 用户定的方向，仿 Anthropic 的“自动设计评测 + 爬坡”做法。用户最看重快（先快后准）。10-14 用户同意了分工和测试集规模（R5）；先跑基线，把数字和每轮花费给用户看，再决定开不开爬坡轮。

## 规则

- R1 任务集 = 用户日常记录里的任务类型改写成公开网站任务 + 陌生网站任务（含跨网站），分训练集和独立测试集，两组网站不重叠。分析者只读训练集的运行记录；测试集的成绩每轮都算，但它的过程记录谁也不看。
  - 例子(正)：`npx tsx scripts/probes/compare-real.mts . out/hillclimb-<日期> ext --split=test` 只跑测试集 — 谁检查：脚本按网址、页面内容或回答文字自动判
  - 例子(反)：分析者为了让任务 R5（RFC）通过，往提示词里写“RFC 文档的作者在页面顶部右侧” — 谁检查：主会话审改动，凡是出现具体网站、具体任务内容的改动一律退回
- R2 硬标准：测试集做成的次数不少于基线；基线里两次都做成的任务，改后不能两次都失败。不满足就丢弃这一轮改动，不论快了多少。
  - 例子(正)：基线测试集 15/16，改后 15/16，用时中位数从 30 秒降到 24 秒 — 谁检查：脚本汇总 `result-ext.json`
  - 例子(反)：改后 14/16，即使轮数少了三成，也不采用 — 谁检查：同上
- R3 要提升的指标（满足 R2 之后）：测试集每个任务的模型来回次数（诊断记录里 `model_request` 的条数，受网络影响小，作主指标），其次是用时中位数。两次运行取平均；只有在两项都不变差时才算改进。
  - 例子(正)：总来回次数 42 → 35，用时中位数不变 — 谁检查：同上
  - 例子(反)：来回次数少了，但用时中位数多了 20%（例如每轮回答变长）— 谁检查：同上，判为没改进
- R4 每轮可改的范围（10-14 用户放宽）：提示词、工具说明，以及工具本身和循环，例如工具多带回什么、程序替模型做掉哪些确定的事。不能放松的边界：发送先问、付款由用户自己点、敏感栏不读不填、用户填过的原值不进模型和日志；代码和提示词里都不出现具体网站或具体任务内容。提示词改动每轮一个提交，能整轮回退；代码改动按合并标准走（新用例通过、故意弄坏会失败、审查），进日常扩展前跑全量 npm test。分析时把每一次多余的来回标上该由哪一块来省（提示词 / 工具 / 循环）。
  - 例子(正)：点击后工具顺带带回页面变化的部分，训练集来回次数下降，核心 33 个用例仍全过 — 谁检查：主会话审改动 + 下一轮成绩 + npm test
  - 例子(反)：为了少一轮，跳过发送前的确认 — 谁检查：主会话审改动，退回
- R5 分工：分析者是主会话，跑评测的是另一个会话。分析者只读训练集的过程记录，永远不看测试集的过程记录。测试集的判据由跑的人校验，只向分析者报“过 / 没过 / 判据是否可靠”，不报过程内容。测试集至少 15 个任务：8 个任务 × 2 次时，做成率的波动约 ±25 个百分点，只够当护栏。
  - 例子(正)：跑的人报“R14 两次都没过；判据可靠，回答里给的是别的行”— 谁检查：分析者只收到这三项
  - 例子(反)：跑的人把测试集某条的工具调用顺序发给分析者 — 谁检查：分析者拒收，这一轮的测试集成绩作废重跑

## 技术前提

- 前提：评测用预先构建好的一份扩展（`SIDEAGENT_ACCEPTANCE_DIST`），整轮评测期间改代码不影响它。小实验：用新任务试跑 1 个。结果：见 PR 描述。
- 前提：每个新任务的判据只看用户看得到的结果（网址、页面内容、回答文字），在本机能自动判。小实验：HN 第 n 条的真值解析和 Python 版本号判据的正则，本地核对过。结果：通过。
- 前提：模型用 AGENTS.md 的默认测试模型 `openai-codex/gpt-6-luna`（脚本 `--model=` 可换），思考强度用产品默认（`--think=` 可指定）。10-13 的对比用的是 gpt-6.1-sol，数字不能和本页的基线直接比。
- 前提：Anthropic `claude-api` 技能里确有 `/claude-api build-eval` 和 `/claude-api hillclimb`。它们的方法（先签字确认输入和判法、训练/测试分开、分析者看不到测试集、按实测花费定预算、每轮记录成绩和改动）适用；但它们按“调用 Claude API 的应用、脚本几秒跑完一条”写，我们是 OpenAI 模型 + 真实浏览器里的扩展、一条要几十秒且受网络影响，所以只借方法和记录格式（`results.jsonl`、`_state.json`、报告生成器），运行器仍用 `compare-real.mts`。

## 每轮花费（估算，基线跑完后用实测数替换）

- 一次全量 = 16 个任务 × 2 次 = 32 条，每条约 25–45 秒加约 10 秒起浏览器，约 30 分钟；有窗口的测试浏览器在后台，期间不能跑别的浏览器验收。
- 模型用量：每条约 3–4 次来回，一次全量约 110–130 次 gpt-6-luna 请求，走 ChatGPT 套餐额度，不按 token 另付费。
- 自动爬坡每轮 = 一次全量（训练集 + 测试集都要跑）+ 一次分析（主会话读 16 条训练记录）。

## 边界与不做

- 不登录、不付款、不发消息、不改别人的数据；用户记录里需要登录的任务（邮箱、笔记账号、自己的视频列表）不进任务集。
- 页面上翻译呈现、圈出词语、画板作图这几类在用户记录里有，但从页面外读不到扩展画的结果，判据不可靠，这次不进任务集。
- 用户记录的原话、网址、个人信息不写进仓库，只写“这类任务”的描述（见 PR）。
- 不跑全量；基线等 #374 合并后另定时段。
- 证据：每次运行在 `out/hillclimb-<日期>/`（每条的诊断记录、截图、`result-ext.json`），不进仓库。
