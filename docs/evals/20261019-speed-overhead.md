# 评测：扩展自己在每一步多花的时间

10-18 到 10-19 用户问助手为什么慢。拆开以后，等模型约占一半，等网站打开约占四分之一；这一页记扩展自己那部分还能省多少。结论：在机器不忙时，扩展这一侧每步能省的已经不到 0.1 秒，速度这条线先停。

## 结论

- 保存对话记录改成后台线程原地追加（#566）：同一脚本模型连做 40 步、对话记录涨到 231KB，40 步总耗时改前 21.9 / 13.5 / 14.2 秒，改后 11.6 / 8.2 / 9.7 秒；每步约省 0.1–0.2 秒。之前估的「每步约 1 秒」没有复现，原因见下面的坑。
- 动手前后的停顿（模型回答写完 → 扩展开始动手，动手完 → 发下一次请求）：机器负载约 8 时 0.01–0.05 秒；负载 27–57 时 0.1–5.4 秒，停的时候扩展没有在算东西，只是在等保存记录的后台线程排上处理器。
- 后台标签页没有被限速（#564 关闭）：不装扩展时同一网址后台标签中位 0.58 秒、前台 0.34 秒；装扩展由助手打开 5 次 1.2–5.3 秒。
- 助手开网页比网页自己多花的时间，主要在往忙碌的网页里插读取脚本（crates.io 每次 0.5–1.6 秒，因为网页自己的脚本还在跑）和等页面安静、读页面结构（0.5–2 秒）。

## 规则
- R1 对话变长时，每一步保存对话记录不随文件变大而明显变慢。
  - 例子(正)：对话记录 231KB，40 步每步中位 0.23–0.30 秒。 — 谁检查：`out/opfs-1019/probe-storage.mts`
  - 例子(反)：每次保存都复制整个文件，同条件每步中位 0.34–0.51 秒。 — 谁检查：同上，改前版本
- R2 重载扩展后，任务照常从记录接着做完。
  - 例子(正)：重载后提交只发生一次。 — 谁检查：`scripts/acceptance/real-path/restart-resume.mts`
  - 例子(反)：保存时追加没写进去，重载后任务做不完。 — 谁检查：同上，故意弄坏时 60 秒超时失败

## 技术前提
- 前提：OPFS 原地追加只能在专用 Worker 里用 createSyncAccessHandle；句柄独占文件，所以每次操作完就关。 小实验：#566 的隔离扩展验收与故障注入。 结果：通过

## 放弃了什么

- 降低 Haiku 思考档：「中」「低」各 20 次真实网站任务，中位 26.2 / 27.6 秒，不更快。
- 把相邻几次模型调用合成一次：能合的只占总时间 3–4%，只做了「填写后直接提交」那一类（#563）。

## 踩过的坑

- 机器负载高时量出来的耗时不算数。这台机器 8 核，跑的时候常有一台虚拟机占 3 个多核心，负载到过 182。量速度前先看 `uptime`，前后两版交替跑，不要和别的验收同时跑。
- 侧栏和 offscreen 文档在同一条线程上：CPU 记录里侧栏光球动画（canvas 逐帧画）在机器忙时一次占 1–2 秒。对用户的影响还没验证。
- 同一个读页面动作连做 15 次，助手会判定原地打转并停下；量多步耗时的探针要让每一步有变化。

## 怎么重跑

探针和数据在主目录 `out/bgtab-1019/` 与 `out/opfs-1019/`（`probe-storage.mts` 量保存记录，`zz-gap.mts` 量动手前后停顿并录 offscreen 的 CPU 记录，`gaps.py` 拆分），放进 `scripts/acceptance/real-path/` 后用 `--headless` 运行。
