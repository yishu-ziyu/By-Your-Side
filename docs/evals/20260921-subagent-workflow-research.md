# 子代理协作调研：减少猜测、等待和交接返工

日期：2026-09-21。范围：当前 Pi 开发宿主的派发方式，不改 By Your Side 产品路由，也不安装或修改代理扩展。用户要求先调研，再继续产品实现。

## 结论

提高效率的单位不是「多派一个代理」，而是「交付一个可独立验证的结果」。主代理负责消除产品歧义、划定真实调用边界、整合和日常验收；子代理拿到自包含的任务、可修改文件、确切检查和停止条件。依赖同一接口的实现串行，独立取证才能并行。给能力较弱的模型缩小判断面，不能用更长的背景材料代替主代理决策。

当前扩展不支持后台任务句柄或续发消息。仅调整提示词无法满足「子代理运行时主对话继续讨论」。

## 3. 派发方式

### 哪些工作派，哪些留主代理

- 主代理：用户目标、产品取舍、跨模块接口、实现顺序、真实日常验收。
- 子代理：具体文件内已明确实现；可独立回答的取证问题；明确变更范围的独立核验。
- 不派：一行修改、主代理已经掌握全部上下文的快速检查；依赖正在变化的架构决定的实现。
- 并行条件：结果相互独立，写入文件不相交，依赖接口已确定。共享一个文件或接口未定就串行，不因为工具支持4并发就派4个。
- 默认不递归派发。代理发现额外工作返回主代理分配，不自行扩展任务树。

### 一份任务包需要什么

必要的是决策完整，不是字数多。每包提供以下内容，已知事实与假设分开：

1. **用户结果**：用户在哪个宿主、哪个入口做什么，会看到什么变化。
2. **任务类别**：只读取证 / 实现 / 独立核验；只能一种为主。
3. **已确认事实**：原始症状、复现或日志、已排除项、用户已定的范围。
4. **必读材料**：少量具体文件及相关符号；最重要的用户限制直接写出，不只说「读AGENTS」。不传密钥、整份对话或全仓库材料。
5. **接口与归属**：输入、输出、调用位置；允许修改文件；并发任务在改哪里；不得动的接口。
6. **成功与反例**：真实路径检查、一个能抓住原问题的失败例、必要的取消/错误分支。尚未决定的产品行为不是实现者自由发挥的范围。
7. **命令与预算**：允许的定点命令，明确禁止全量/构建/重载/模型调用（按任务适用）；扩展检查前返回具体理由。没有执行器时限时，提示词预算只是约定，不是硬限制。
8. **停止条件**：发现前提不成立、需改未授权文件、接口与事实矛盾时立即返回证据和建议，不猜着做。
9. **交接内容**：状态、改动、已执行检查、未通过/未跑、证据路径和下一位应调用的接口。

## 4. 主代理如何接结果

1. 先看是否越界、是否仍有已知缺口，再看「通过了多少测试」。
2. 核查真实修改文件与声明是否一致；当前工作树有大量原改动，不能把整份git diff当本包修改。
3. 检查新增回归是否来自真实入口，是否真的在修前失败。主代理至少亲跑一次关键路径或对应定点测试。
4. 独立核验会话先拿原问题、完成标准、改动范围和证据入口，不先灌实现者的「全通过」结论；要求主动找一个能推翻结果的反例。
5. 不把复核变第二轮全量开发；发现问题返回具体缺陷，按文件归属交回修复。
6. 对外只报用户结果、当前阻碍和下一步动作。测试通过但日常路径失败时，更新检查方法，不让用户再证明已反馈的问题。

## 5. 后台讨论与执行的可行边界

### 当前工具

同步single/parallel/chain；没有消息续发、任务句柄和原地恢复。不能通过在task里写「后台运行」获得这些能力。

### 最小候选（尚未部署）

复用Pi官方建议的tmux，启动独立命名Pi会话；每个任务有固定任务文件、session文件、输出文件和退出状态。主对话不等待进程结束，需要时检查输出，任务完成再整合。能够脱离前台运行不等于自动发完成通知；后者需要显式通知接入。

对运行中任务的新决定，先记录任务版本并停止/重派受影响工作；不宣称当前一次性-p工具可以收到新消息。需要低延迟续发、取消及自动通知时，再核对Pi RPC/SDK或成熟后台扩展，不为这轮调研直接搭一套调度平台。

同一用户与共享目录仍不是隔离环境。并行编码需要文件归属；独立worktree只在基线可完整复制时使用。本项目现有大量未提交内容，从HEAD新建worktree会漏掉实际基线，不能直接套用。

## 6. 怎么判断真的提效

下一次限定任务记录四项即可，不另造全套评测：派发到可验收结果的总时间、主代理返工次数、重复读取/重复测试、真实入口是否首次通过。附实际模型与用量（宿主可得时），不把子代理自报耗时当全链路耗时。

目前完成的是源码核查、官方资料对照和本会话失败审计，尚无改进前后对照数据；因此不承诺节省百分比。先用新的任务包完成下一项独立工作，再决定是否增加并发或换模型。
