# 任务: 量出每次模型调用的上下文和缓存命中，查清 gpt-6-luna 是否每轮重算对话历史

来源：[论文对照](../research/20261011-harness-paper-review.md)第 0、1 项，用户 10-11 说「开始」。

## 规则

- R1 `time-breakdown.mts` 对每个任务列出每次主循环调用送进模型的上下文和其中命中缓存的量，并给出最大上下文和目标核对判「继续」的次数。
  - 例子(正)：读一份带 `turn_end.usage` 的真实导出，每个任务一行，「每次调用」列形如 `14.1k/9.7k · 18.3k/14.1k`，「最大上下文」列等于这些调用里最大的那个 — 谁检查：工程师对照原始导出手算一个任务
  - 例子(反)：导出里没有 `turn_end.usage`（10-11 以前的记录）时显示「—」，不显示 0 — 谁检查：同上，用 `out/error-analysis/daily/D07-*.jsonl`
- R2 用当前主干的扩展和 gpt-6-luna 跑多步任务，回答：同一次运行里从第 2 次调用起，缓存命中是否随历史增长。
  - 例子(正)：第 2 次起每次的命中 ≥ 上一次调用的总输入的 80% — 结论「已正常，不用修」 — 谁检查：`time-breakdown.mts` 读 compare 组导出
  - 例子(反)：命中停在系统提示词加工具定义的长度（约 9–16k）不随历史增长 — 结论「仍重算」，接着找相邻两次请求从哪里开始不同 — 谁检查：同上

## 技术前提

- 前提：主循环每轮的 `turn_end` 记录带 `usage`（#264 起）。小实验：读 `shared/run-trace-core.ts` 的 `turn_end` 分支。结果：通过。
- 前提：发给 ChatGPT 的缓存键稳定。小实验：读代码，`PiAgentLoop` 的 `sessionId` 取会话 ID（`agent/src/session.ts` 构造 `PiAgentLoop` 处），pi-ai 把它作为 `prompt_cache_key`（`openai-codex-responses.js:171`、`:397`）。结果：通过；抓到的请求正文里第一个会话的键是 `default`（`shared/protocol.ts` 的 `DEFAULT_CONVERSATION_ID`）。

## 边界与不做

- 只量不修：缓存仍重算时，本任务找出不同的位置并写下来，修复另起任务。
- compare 组每条用例都是新会话，所以跨消息的命中另用一个小实验量（同一会话对一篇长文连问 3 条）。

## 结果（2026-10-11，gpt-6-luna，隔离无头 Chrome，主干 `785e0e7`）

- R1 通过：compare 组导出里 dead-next 的 7 次调用与原始 `turn_end.usage` 逐个对上；D07（10-06 导出，没有 `turn_end.usage`）各列显示「—」。
- R2 结论：**同一次运行内，请求前缀不变，命中随历史增长；每开始新的一轮（新消息，或目标核对判「继续」后自动接着做的一轮），从上一轮「本次运行的上下文」的位置起重算。另有一部分调用在前缀完全相同时也整段不命中（推断在服务端）。**
  - 服务端能缓存长历史：脚本直接调 gpt-6-luna，14.5 万 token 的历史从第 2 次调用起每次命中 14.4 万；中途删掉一条消息时，命中退到删除点，不是退回开头。
  - 同一次运行内前缀不变：compare 组 40 次调用的系统提示词、工具定义哈希全部相同；按 `model_request.injected` 逐次比较，「本次运行的上下文」只在新一轮开始时变。signup 第 3、4 次调用命中停在 10.8k，是因为中间目标核对判了「继续」，开了新一轮。
  - 前缀相同也整段不命中：例如 slow-more 同一轮内第 1、3 次调用命中为 0，前后调用都命中。另外 10 个新会话里 6 个第一次调用命中为 0；缓存键按会话分，新会话的键第一次出现（推断：分到了没有缓存的机器）。
  - 换消息时的分叉点（抓了 3 条消息的请求正文逐项比较）：「本次运行的上下文」这条消息插在本次用户消息之前，下一条消息时被拿掉。所以从上一轮的插入点起，后面全部重算。会话第 2 条消息时插入点就在系统提示词之后，整段历史都重算。
  - 同一篇长文连问 3 条：上下文 1.8 万 → 2.4 万 → 3.0 万，命中 0.7 万、0、1.1 万。每条用户消息都带一份当前页快照（约 6k token），同一页在历史里出现了 3 次。
  - 10-06 那几次 10 万 token 只命中约 1.2 万的会话用的是 #258 以前的构建。换消息时整段重算可以用当时系统提示词每次运行都变来解释；但同一次运行内也只命中约 1.2 万，原因没查，当前构建上没有复现。
- 证据：compare 组 `out/acceptance/real-path/2026-10-11T11-58-52-634Z-everyday-baseline-compare-inproc-46970/`；三条消息的请求正文与诊断记录、三个小实验脚本在 `out/acceptance/real-path/2026-10-11T12-08-context-cache-probe/`（不入库）。
- 踩坑：worktree 里把 `node_modules` 整个链回主树后，扩展构建用了主树的代理代码，诊断记录导出为空（`readback-privacy` 也因此失败）。[开发检查](../development/checks.md)已写明这一条，这次没照做。
