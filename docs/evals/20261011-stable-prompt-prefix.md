# 任务: 每条新消息的第一轮也命中提示词缓存（#258），诊断记录量得出延迟预算（#264）

## 规则
- R1 系统提示词和工具定义只放每次都一样的内容。日期、对话历史、任务状态、记忆、站点提示放在本次用户消息前的一条消息里，只在本次运行里带。
  - 例子(正)：同一模型连发两条不同的消息，第二条第一轮的 `cacheRead` ≥ 14k token — 谁检查：工程师用真实阶跃跑，诊断记录 `turn_end.usage.cacheRead`
  - 例子(反)：改动前同样跑，第一轮只命中 0–3.3k — 谁检查：同上
- R2 模型收到的记忆、过往任务、站点提示内容不变，只是换了位置 — 谁检查：memory-used-line、panel-tidy、site-hint、memory-foundation、memory-hardening、remember-corrections（脚本模型）
- R3 问「今天几号」答对 — 谁检查：工程师用真实阶跃问 1 次
- R4 诊断记录能算出 #264 的三个数：首个正文字时间（`first_text`）、每轮缓存命中（`turn_end.usage`）、回答后的后台耗时 — 谁检查：`scripts/eval/time-breakdown.mts` 读真实导出

## 还没答上的问题
- 无。

## 技术前提
- 前提：阶跃按前缀匹配缓存，工具定义排在 system 之后，所以 system 末尾一变，工具定义也失去缓存。小实验：#258 里的 `cache_probe.py` A/B（分支 `assets/latency-20261011`）。结果：通过，B 变体命中 14,080。
- 前提：pi-ai 把阶跃的 `cached_tokens` 读进 `usage.cacheRead`。小实验：读 `openai-completions.js` 的用量换算，再看真实导出。结果：通过。

## 边界与不做
- 「执行约定」段按 `record_task_results` 是否启用二选一，留在系统提示词里：它和工具清单同时变，不多打碎缓存。
- 首字有没有因此变快，样本太少，没下结论（#258 说达不到只当省钱改动）。
- 读页、后台判断、#256 另做。

- 首个正文字差别主要来自轮数：改前总结有 1 次重读 4 轮（#255），改后 3 次都是 1 轮，和缓存无关。
- R4 通过：上表就是 `time-breakdown.mts` 从真实导出算出来的。旧导出没有这些字段，显示「—」。
- 测量脚本（不入库）在 #264 的证据分支上，这次修了两处：本机没有 `timeout` 命令；侧栏刚打开时字打不进去，脚本等满 300 秒（5 次里 1 次）。这是脚本问题，不是产品问题。
- 上表的改后数据用的构建里，上下文消息的开头那句还在 `product-context.ts`，后来挪进了循环。系统提示词和工具定义两次构建完全一样，所以缓存结论不变。
- R2 通过（新构建）：memory-used-line、panel-tidy、site-hint、memory-foundation、memory-hardening、remember-corrections（24 个场景分两次跑完）。这 6 个用例原来只在系统提示词里找记忆和站点提示，现在也看本次上下文消息。第一次跑 memory-used-line 和 panel-tidy 失败，是因为扩展没重新构建；重新构建后通过。
