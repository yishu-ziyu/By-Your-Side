# 任务：网页划词照常可用；拖进侧栏的大小由用户决定

[小样](../../out/previews/drag-feed-grip/index.html) · [原投喂验收](20261005-killer-interactions.md) · [使用说明](../guides/usage.md)

## 规则

- R1 页面元素不再被设成可拖动；在正文里按住鼠标拖动是选字。
  - 正：本机文章页（正文包在 `<article>` 里），在段落上按下、移动、松开后，页面有选中文字，没有开始拖动。机器检查：`scripts/acceptance/real-path/drag-feed-selection.mts`。
  - 反：页面上没有被扩展加上的 `draggable`。机器检查：同上。
- R2 选中任意文字后按住选区拖进侧栏，材料就是选中的那段。
  - 正：选中一句话拖入，材料文字等于这句话，不含同段其他句子，草稿给出解释模板。机器检查：同上。
  - 反：拖出后原文被网页改掉、不再含这句话，松手时拒绝添加并说明。机器检查：同上。
- R3 表格和代码块悬停时出现小把手，按住把手拖整块。
  - 正：悬停表格出现把手；从把手拖入，材料是整张表（按行、单元格用 `|` 分隔）。机器检查：同上；原投喂验收改为从把手拖。
  - 反：鼠标离开表格后把手隐藏；普通段落不出把手。机器检查：同上。

## 还没答上的问题

无。用户 2026-10-05 试过小样，确认「先选中再拖 + 表格/代码把手」可用。

## 技术前提

- 前提：Chrome 拖动已选中文字时，内容脚本能在 dragstart 里加自定义类型，侧栏能读到。依据：原投喂已证明自定义类型跨渲染进程可读（`scripts/probes/killer-interactions.mts`）；选区拖动由本验收实测。

## 边界与不做

- 不再提供整篇文章、卡片的整块拖动。
- 不改侧栏材料胶囊、发送才交给模型、过期校验的规则。
- 不重载日常扩展、不提交。

## 证据

- 原因：内容脚本把 `article`、`[role=article]`、`.card`、`table`、`pre` 全设成 `draggable`。多数网页把正文包在 `article` 里，整篇成了一块；在可拖动元素里按住移动，浏览器开始拖动，不开始选字。
- 改法：页面元素一律不设 `draggable`。拖动已选中的文字时只多附材料凭据，浏览器原有的文字数据照常保留。表格和代码块用页面外一层的把手，放在独立 shadow 里，不改动网页节点。选段的材料凭据留住当时的选区，网页改了这段文字就拒绝。
- 端到端：`npx tsx scripts/acceptance/real-path/drag-feed-selection.mts --headless --run=final`，10/10 通过。产物在 `out/acceptance/drag-feed-selection/final/`：result.json、grip.png、selection-feed.png。
  - R1：页面上被加的 `draggable` 为 0；在正文按住拖动选中了文字，没有开始拖动。
  - R2：材料就是那一句，不含同段其他句子；草稿为「请解释这段内容，并说明依据。」；原文被改写后拒绝添加，并显示「原网页或材料已变化」。
  - R3：悬停表格时出现把手；从把手拖入，得到整张表（`维度 | Ingress | Gateway API` 等两行）；移到普通段落上，把手隐藏。
- 原伴读验收 `killer-interactions.mts` 改为从把手拖，28/28 通过（run=after-grip）。
- 实测发现：macOS 上 Chrome 要按住选区约 150ms 再移动，才会拖动选中的文字，否则会重新选字。这是浏览器的规则，真人也一样。脚本里按下后停 250ms。
- 工程检查：`VITEST_MAX_WORKERS=1 npm run check` 退出码 0，253 个文件、2392 项测试全部通过，文档 0 错误 0 提醒。日志见 `out/acceptance/drag-feed-selection/final/check.log`。
- 未跑：真人手感；把选区拖到侧栏以外其他应用的情况；超长网页里跨很多段的选区（上限 8000 字）。
- 此次未重载日常扩展、未提交。
