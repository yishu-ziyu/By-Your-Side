# 评测：一次模型请求的等待花在哪里

10-15 用户问：任务慢，能不能把每次发给模型的内容“瘦身”。先拆开等待再决定，结论是瘦身几乎省不了时间，真正能省的是建连接。

## 结论

- 一个任务 84% 的时间在等模型（10-08 到 10-15 的 60 个任务，中位每个任务 5 次请求）。
- 内容大小几乎不影响等待：85% 的固定内容命中缓存；把一次请求从约 1.3 万 token 减到 350 token，或去掉历史、去掉全部工具说明，开口最多快 0.3 秒，95% 区间跨过 0。
- Luna 一次主任务请求（连接已建好）：服务端开始回应 1.3–1.5 秒，模型思考到第一个输出 0.5–1 秒（低档），再输出 0.5–2 秒。中档思考一次就要 5 秒以上。
- 每个任务的第一次请求要经用户的代理新建加密连接，实测 0.3–5.3 秒。用户点进输入框时先建好（PR #441），8/8 次复用、建连接时间变成 0，到第一个回应中位 5.0 → 1.4 秒（样本少，区间 −0.7 到 9.2 秒）。
- 扩展发出的模型请求原来会带上用户在该网站的 cookie（例如 chatgpt.com 网页版登录）。同一 PR 改成一律不带。
- “操作完马上再看一次页面”占 100 次调用里的 16 次，约 9 次可省，其中约 5 次已被 10-13、10-14 的改动处理或待验证；剩下约 4 次：切换标签页后交回页面、说明文字、失败时列出候选目标。

## 放弃了什么

- 不删系统说明和工具说明：省时在噪声以内，还可能伤成功率。
- 日志里的“开口”是第一个输出片段，不是第一个网络字节。前后对比要用同一口径，第一次对比把两者混了。

## 怎么重跑

- 内容大小：`scripts/probes/prompt-size-latency.mts --trials=20`（直接调模型，冷 / 热各一组）。
- 截获真实请求：`scripts/probes/request-replay/capture.mts --url=… --task=… [--think-ms=3000]`（隔离浏览器里截获扩展发出的每个模型请求和计时，不存凭据）。
- 原样重放与去掉因素：`scripts/probes/request-replay/replay.mts --from=<截获目录> --variants=asis,history-last-2,no-tools`。
- 提前建连接的验收：`scripts/acceptance/real-path/warm-connection.mts`。

## 还没答上

- 同一请求从扩展里发出比从外面重放慢约 0.5 秒，原因没查。
- “少调几次模型”的空间要等 10-14 的页面变化报告在真实使用里攒一批日志再算。
