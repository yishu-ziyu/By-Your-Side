# 评测：一次模型请求的等待花在哪里

10-15 用户问：任务慢，能不能把每次发给模型的内容“瘦身”。先拆开等待再决定，结论是瘦身几乎省不了时间，真正能省的是建连接。

## 结论

- 扩展发出的模型请求原来会带上用户在该网站的 cookie（例如 chatgpt.com 网页版登录）。PR #441 改成一律不带。

## 规则
- R1 用户点进输入框后几秒再发，任务的第一个模型请求复用已建好的连接，没有建连接和握手阶段。
  - 例子(正)：点进输入框，想 3 秒，发“这页标题是什么”，第一个请求复用连接。 — 谁检查：`scripts/acceptance/real-path/warm-connection.mts`
  - 例子(反)：第一个请求还要新建连接，经代理多等几秒。 — 谁检查：同上，旧版失败
- R2 模型请求和提前建连接的请求都不带用户在该网站的 cookie。
  - 例子(正)：浏览器里有 chatgpt.com 的 cookie，模型请求里没有。 — 谁检查：同上
  - 例子(反)：模型请求带上了网页版登录 cookie。 — 谁检查：同上

## 技术前提
- 前提：Chrome 按请求的凭据模式分连接池，预热请求和模型请求凭据模式一致才复用得上；两边都用 omit。 小实验：隔离浏览器里先用不同模式（不复用），再用相同模式（复用），见 PR #441。 结果：通过

## 放弃了什么

- 不删系统说明和工具说明：省时在噪声以内，还可能伤成功率。
- 日志里的“开口”是第一个输出片段，不是第一个网络字节。前后对比要用同一口径，第一次对比把两者混了。

## 怎么重跑

- 内容大小：`scripts/probes/prompt-size-latency.mts --trials=20`（直接调模型，冷 / 热各一组）。
- 截获真实请求：`scripts/probes/request-replay/capture.mts --url=… --task=… [--think-ms=3000]`（隔离浏览器里截获扩展发出的每个模型请求和计时，不存凭据）。
- 原样重放与去掉因素：`scripts/probes/request-replay/replay.mts --from=<截获目录> --variants=asis,history-last-2,no-tools`。
- 提前建连接的验收：`scripts/acceptance/real-path/warm-connection.mts`。

## 还没答上

- 同一请求从扩展里发出比从外面重放慢一些，原因没查。
- “少调几次模型”的空间要等 10-14 的页面变化报告在真实使用里攒一批日志再算。
