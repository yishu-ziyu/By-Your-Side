# 任务: 没拿到内容的 fetch 算失败，侧栏写一句人话原因

来源：[#304](https://github.com/yishu-ziyu/By-Your-Side/issues/304)。BYS-114 评测里助手同时抓 5 个接口，多次返回 `HTTP 0 (not ok) … 0 bytes`，但 `isError=false`，侧栏把死路当成成功。622 轮评测里 36% 有工具失败，HTTP 0 这类还没算进去。是 #263 分支图「死路灰色 + 原因」的前置。

## 规则

- R1 fetch 没拿到内容算失败：status 0 或非 2xx，这一步失败并带 ≤16 字的人话原因（「连不上这个地址」「页面不存在（404）」「要登录才能下」）。直调 fetch 和 browser_run 里的 `browser.fetch` 用同一判定。
  - 例子(正)：直调 fetch 拿到 404 → 侧栏「发送网络请求 · 页面不存在（404）」；browser_run 里 fetch 拿到 404 → 子步骤同样写这句 — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（d、e）
  - 例子(反)：2xx 但正文空（204）是对方正常答了「没有内容」，不算失败，侧栏不画失败 — 谁检查：同一命令（f）
- R2 给模型的东西不变：直调 fetch 的文字仍是 `formatFetchReply` 原样，失败标志与原因只进 `isError`/`details`；browser_run 里的程序照常拿到原始回执、继续往下跑，不因 404 停下（分页循环可以自己看 `status`）。
  - 例子(正)：程序 `return r.status` 照常返回 404，后面的步骤照常执行 — 谁检查：人（读 `browser-program.ts` 的 fetch 判定）
- R3 click/fill/navigate/js 等工具失败也带 `reason`：工具自己在 `details.reason` 写明了用它；没写就从错误原文取一句人话（`plainToolError`），剥掉选择子、`@N`、loc、英文括注和不可信标记；没有中文就写「没做成」。
  - 例子(正)：「未找到元素: #gone」→「没找到目标」，侧栏不带 `#gone` — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（d）；其余说法（「目标现在不可用」、挡住回执）— 谁检查：人
- R4 侧栏显示原因：tool_end 的 `reason` 字段直接画在步骤后，没有原因才写「没做成」；用户没让执行（heldReason）和拦重复执行的步骤不画成失败。
  - 例子(正)：点击找不到目标，步骤行写「点「不存在的按钮」 · 没找到目标」 — 谁检查：`npm test` 的 answer-straight 用例
- R5 RepeatedToolFailurePolicy 不误升档：三个不同 URL 各失败一次不算重复；同一 URL 同样错误第二次才升档一次；成功一次清掉同工具记录。
  - 例子(正)：a/b/c 三个 URL 各 fail 一次 → 不升档；同一 URL fail 两次 → 升档一次 — 谁检查：人（本任务没改 `tool-failure-policy.ts`）

## 技术前提

- 前提：`AgentToolResult` 支持 `isError` 且 `details` 会原样带进 `tool_execution_end` 事件，所以 fetch 不用抛错也能标失败、带原因。小实验：读 `pi-agent-core/dist/agent-loop.js` 的结果包装与 `tool_result` 钩子。结果：成立。
- 前提：操作键是工具名 + 排序后的输入参数，不同 URL 本来就是不同操作，不会误升档。小实验：读 `tool-failure-policy.ts` 的 `operationKey`。结果：成立。
- 前提：侧栏失败只有一处文案「· 没做成」，加 `reason` 字段即可替换显示。小实验：读 `main.ts` 的 `onToolEnd`。结果：成立。

## 边界与不做

- 不改给模型的文字，不改 `formatFetchReply`。
- 不新增 UI：只在现有步骤行的失败尾巴上换文案。
- 用户没让执行（heldReason）、拦重复执行（repeatRefused）的步骤照旧不算失败，不带 reason。
- browser_run 里只有那一个 fetch 子步骤算失败，整个「连续操作」仍按程序是否跑完判成功；重复失败策略只看顶层工具，看不到程序里的失败 fetch。
- BYS-114 原始 trace 在仓库外的评测包里，不做离线回放；同等路径由 answer-straight 真实用例覆盖（点击失败 → 侧栏写原因）。

## 结果

- 实现：`fetchFailureReason`（`agent/src/fetch-result.ts`）判失败并给原因；直调 fetch 返回 `isError:true` + `details.reason`；`browser-program.ts` 在程序里的 fetch 回执上用同一判定，子步骤带 `error` 和 `reason`。`plainToolError`（`shared/user-facing.ts`）把其他工具的错误翻成 ≤16 字人话。侧栏 `onToolEnd` 用 `ev.reason ?? "没做成"`。
- 原来的 vitest 单元测试已删（项目只要真实端到端用例），覆盖改由 answer-straight 承担。

## 验证记录

- `npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`：a–f 全部 PASS（10-13）。
- 反例：去掉 `browser-program.ts` 的 fetch 判定，e 失败（程序里的 404 子步骤没有原因）；把 2xx 空正文改回算失败，f 失败（多出「接口没返回内容」）。
