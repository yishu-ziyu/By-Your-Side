# 任务: 没拿到内容的 fetch 算失败，侧栏写一句人话原因

来源：[#304](https://github.com/yishu-ziyu/By-Your-Side/issues/304)。BYS-114 评测里助手同时抓 5 个接口，多次返回 `HTTP 0 (not ok) … 0 bytes`，但 `isError=false`，侧栏把死路当成成功。622 轮评测里 36% 有工具失败，HTTP 0 这类还没算进去。是 #263 分支图「死路灰色 + 原因」的前置。

## 规则

- R1 fetch 对方答了非 2xx 算失败，侧栏写原因（「页面不存在（404）」「要登录才能下」）；连不上（端口没人听、DNS 失败）写「连不上这个地址」，超时写「这一步超时了」。直调 fetch 和 browser_run 里的 `browser.fetch` 同一判定。
  - 例子(正)：直调 fetch 拿到 404、browser_run 里 fetch 拿到 404，都写「页面不存在（404）」；fetch 一个没人听的端口写「连不上这个地址」 — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（d、e、g）
  - 例子(反)：2xx 但正文空（204），或 POST 成功后 302（扩展不跟随跳转，拿到 status 0），都不算失败；把 302 当失败会让模型重交 — 谁检查：同一命令（f）
- R2 给模型的东西不变：直调 fetch 的文字照旧，失败标志与原因只进 `isError`/`details`；browser_run 里的程序照常拿到原始回执、继续往下跑，不因 404 停下（分页循环可以自己看 `status`）。
  - 例子(正)：程序先取 204、再取 404，照常返回两个状态码 — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（h 的程序）
- R3 其他工具失败也带原因：工具自己写明了就用它；没写就从错误原文取一句人话，剥掉选择子、`@N`、loc、英文括注和不可信标记；没有中文就写「没做成」。
  - 例子(正)：「未找到元素: #gone」→「没找到目标」，侧栏不带 `#gone` — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（d）；其余说法（「目标现在不可用」、挡住回执）— 谁检查：人
- R4 侧栏显示：原因不超过 16 个字，直接画在步骤后，没有原因才写「没做成」；用户没让执行和拦重复执行的步骤不画成失败。这一轮算不算没做成，看最后结束的那一步：程序里一次 fetch 失败、程序本身跑完，这一轮不算没做成。
  - 例子(正)：点击找不到目标，步骤行写「点「不存在的按钮」 · 没找到目标」；程序最后一次 fetch 是 404、之后直接回答，回执不写「有 1 步没做成」，没有失败图标 — 谁检查：`npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`（d、h）
- R5 重复失败策略不误升档：三个不同 URL 各失败一次不算重复；同一 URL 同样错误第二次才升档一次；成功一次清掉同工具记录。
  - 例子(正)：a/b/c 三个 URL 各 fail 一次 → 不升档；同一 URL fail 两次 → 升档一次 — 谁检查：人（本任务没改这个策略）

## 技术前提

- 前提：`AgentToolResult` 支持 `isError` 且 `details` 会原样带进 `tool_execution_end` 事件，所以 fetch 不用抛错也能标失败、带原因。小实验：读 `pi-agent-core/dist/agent-loop.js` 的结果包装与 `tool_result` 钩子。结果：成立。
- 前提：操作键是工具名 + 排序后的输入参数，不同 URL 本来就是不同操作，不会误升档。小实验：读 `tool-failure-policy.ts` 的 `operationKey`。结果：成立。
- 前提：侧栏失败只有一处文案「· 没做成」，加 `reason` 字段即可替换显示。小实验：读 `main.ts` 的 `onToolEnd`。结果：成立。

## 边界与不做

- 不改给模型的文字。
- 不新增 UI：只在现有步骤行的失败尾巴上换文案。
- 用户没让执行（heldReason）、拦重复执行（repeatRefused）的步骤照旧不算失败，不带 reason。
- browser_run 里只有那一个 fetch 子步骤算失败，整个「连续操作」按程序是否跑完判成功；重复失败策略只看顶层工具，看不到程序里的失败 fetch。
- BYS-114 原始 trace 在仓库外的评测包里，不做离线回放；同等路径由 answer-straight 真实用例覆盖（点击失败 → 侧栏写原因）。

## 结果

- 用户看到：fetch 失败的那一步写出原因，直调和 browser_run 里一样；204、302 照常算做完；程序里一次 404 不会让整轮显示成没做成。
- 原来的 vitest 单元测试已删（项目只要真实端到端用例），覆盖改由 answer-straight 承担。
- 没做：POST 拿到 4xx 时任务账本仍记「结果未知」。要分开 4xx 和 5xx，得把状态码带进账本，不是局部改动。

## 验证记录

- `npx tsx scripts/acceptance/real-path/answer-straight.mts --headless`：a–h 全部 PASS（10-13）。
- 改之前先跑同一用例：POST 302 显示「连不上这个地址」（证明扩展拿到的是 status 0），没人听的端口显示「结果未知」，程序最后一次 404 让整轮显示「有 1 步没做成」和失败图标。
- 反例：去掉程序里的 fetch 判定，e 失败；成功的一步不清掉失败，h 失败；把 2xx 空正文改回算失败，f 失败。
