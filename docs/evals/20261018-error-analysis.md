# 错误分析：30 条日常真实记录的第一处错误

[#237](https://github.com/yishu-ziyu/By-Your-Side/issues/237)。用户 10-06 到 10-18 在日常 Chrome 里的 88 次自然使用中抽 30 条：15 条按耗时、操作次数、重试次数取最差，15 条随机。每条只记最早偏离用户目标的那一处。10-18 用户定：助手先逐条判，判不了的再问用户；30 条里 4 条问过用户，其余由助手判。原始记录含页面内容，不入库，在主目录 `out/error-analysis-1018/`。

## 规则

- R1 排期看次数和损失：「提前放弃」和「说做完了其实没做完」合计 6 条，都被完成核对拦下，但每次用户先看到错的回答、多等 1–2 分钟；这 6 条都在 10-13 之前，10-18 真实网站护栏里这一类明显减少，先不单独开工。
  - 例子(正)：下一轮护栏或日常记录里这一类又多起来，再按它开 issue — 谁检查：`npx tsx scripts/eval/time-breakdown.mts` 与本表同口径复看
  - 例子(反)：只因为某一条最慢就先修它 — 谁检查：人
- R2 排第一的是「模型服务出错」：其中 2 条（T10、T12）模型一直不回、没换备用模型，整件事没做成，后续 issue 先修它。
  - 例子(正)：主模型连续首包超时时换到快速模型接着做 — 谁检查：后续 issue 的真实路径用例
  - 例子(反)：重试 9 次都在同一个卡住的模型上 — 谁检查：同上

## 技术前提

- 前提：日常记录能按运行拆出用户原话、每一步工具、回答和核对结论。小实验：`npm run logs` 导出后按 runId 分组。结果：通过，88 次自然使用都能还原经过。
- 前提：「试一次就说做不到」靠看完整经过判断，助手判得对不对没有第二人复核；4 条判不清的已问用户。
