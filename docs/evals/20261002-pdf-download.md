# 任务: 在 PDF 阅读器打开论文后，助手仍能把完整 PDF 下载给用户

## 完成标准

- [x] 1. 用户在 PDF 阅读器请求下载，文件实际落盘，字节与服务端 PDF 一致；只有 Chrome 报完成才回报已保存 — 谁检查: 无头真实扩展、下载文件与 Chrome 下载记录。
- [x] 2. 网络中断、仍在下载分别回报失败或未完成；能用宿主签发的下载编号查询，不重复开始下载 — 谁检查: 完整/中断/延迟的真实 HTTP 服务与扩展入口。
- [x] 3. 非 HTTP(S) 地址在下载开始前被拒绝，保持现有页面控制权闸门 — 谁检查: 入口反例及控制权回归。
- [x] 4. 本轮下载不依赖本机伴随进程，不增加扩展权限 — 谁检查: 构建、清单差异与代码复核。

## 边界与不做

- Chrome 保存到用户配置的下载目录，不增加任意本机路径写入。
- 不自动放行 Chrome 标记为危险的下载，不把阅读器打开或请求开始记为完成。
- 不用 Node 会话循环替代扩展验收。

## 修改前证据

- GitHub #25 的 10-02 复测：BYS-132 在 M3.1 与 GLM 两种配置均超时。
- 现有扩展有 `chrome.downloads` 完成/中断查询，但模型没有按 URL 开始下载的工具，也没有独立的下载查询工具定义。
- 请求 PDF 的链接可能仅打开 Chrome 阅读器，不产生网页下载事件。新入口将直接使用 Chrome 下载 API。

## 实测与失败修订

- 修改前真实扩展没有 URL 下载工具，完整文件、延迟查询与协议反例失败：`out/acceptance/pdf-download/2026-10-02T12-36-04-470Z/`。
- 下载属于原任务。检查若为每一步另开会话，会触发页面控制权拒绝；改为同一会话查询、取消，未改产品控制规则。
- 延迟查询的脚本请求曾误匹配「延迟下载」而重复启动；改用独立请求名称和实际回执中的宿主下载编号。旧失败保留。
- 下载已完成时取消调用不能把文件说成已取消；按 Chrome 当前状态返回，文件保留。
