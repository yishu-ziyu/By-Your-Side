# 任务: 109 段长文整页翻译在真实路径上约 150 秒内译完，译好一批就出现在页面上，不再被 240 秒时限截断

## 背景

用户在日常 Chrome（只装扩展 0.2.0，阶跃 step-3.7-flash）翻译一篇 109 段文章用了 8 分 43 秒。调查（firstmate `bys-translate-slow-r1` 报告）结论：批次严格串行（每批 ≤8 块），每批 15–25 秒，step 其中 80–88% 在思考；另有一批两次写满输出上限（`length`）、一次撞上 240 秒工具时限。R1（原代码）334.6 s；R2（临时 4 路按轮并发）164.1 s；8 路直连请求全部 200、无限流。用户（captain）选了“修”：几批同时翻、译好一批马上显示、超时按进度判断、`length` 时拆小重试、诊断记录写每批耗时。不改 `reasoning_effort`、不换模型、不改译文质量。

## 做法

行为说明见[整页翻译](../page-translation.md)。

- `runPageTranslation` 由串行循环改成固定宽度的请求池（默认 4 路，允许 1–8），哪一批先完成就先 `apply` 落页。`collect` 新增 `exclude`，页面跳过在途块号；视口优先的排序不变，每批上限（8 块 / 3000 字符 / 24 片段）不变。
- 去掉工具上固定的 240 秒；改为连续 180 秒没有一批落页才停，另设 15 分钟硬上限。
- `length` 时把这批对半拆开，最多两层（8 → 4 → 2），到底只原样重试一次；一批最终失败后不开新批、在途批次照常落页，再如实报告进度。
- 每次翻译请求写一行 `page_translation_request` 到诊断记录（批次、拆分层数、是否重试、停止原因、耗时、块数、token 用量），设置页导出即可看到。
- 验收脚本 `everyday-baseline.mts` 新增 `/long` 练习页（脚本拼出的 109 个原创英文段落块，未使用用户看过的文章）和 `translate-long` 用例，记录页面上第一段中文出现的时刻与译文块数随时间的变化，并从导出的诊断记录里列出每次翻译请求。

## 边界与不做

- 不加 `reasoning_effort`，不换模型，不改译文质量，不改侧栏界面。
- 没有接入“首屏译完”的侧栏进度显示。

- 全部 10 次 109/109 段出现中文。每次请求耗时中位 11.8–14.5 s，最长 20.5–25.3 s；8 路时单请求并不变慢，所有模型请求都是 200。
- 改前批次数：由 `[page-translation]` 控制台行统计（原代码不写诊断记录）；改后来自设置页导出的诊断记录。
- 首段中文仍要 13–20 s：主模型第一轮约 4–8 s，加上第一批（视口优先）一次完整的模型请求。
- 同一强制运行的前一次（`12-23-03-597Z`）译完了 109/109，但模型选了“仅译文”，当时的判据只数双语译文节点，误判为 0 段；判据改为数含中文的段落块（两种显示方式都算）后重跑即上表最后一行。

**请求池宽度取 4。** 8 路比 4 路整轮快约 18 s（均值 51.8 vs 69.7 s），首段快约 3 s。两者都远低于约 150 s 的目标。只测了阶跃；产品面向自配模型的用户，并发上限更低的服务商在 8 路下可能被限流，而一批失败会让本次翻译停止。所以默认 4，常量 `PAGE_TRANSLATION_CONCURRENCY` 可改。

检查：`npx vitest run agent/test/page-translation.test.ts`（新增 6 个用例：池宽上限与不重叠、先完成先落页、length 拆分与上限、有进展不截断且卡住会停、请求元数据、`exclude` 校验；把拆分层数改为 0 或去掉 `exclude` 时其中 3 个失败）；`npm run check` 结果见 PR。
