# 任务: 付款这一下永远由你自己点

10-09 用户决定（Linear YIS-131）：助手可以把表单填到付款前，但是永远不点付款按钮。用户在聊天里说「付吧」也不点（第一版）。

为什么：离线实验里，step-3.7-flash 3 次里有 2 次自己点了免密付款按钮。付出去的钱收不回来，而当时代码里没有任何一步拦住。

## 规则

- R1 助手点付款按钮时，程序不点，网站什么也收不到。网页上圈出这个按钮，底部提示「<网站> · 「<按钮名>」 这一步要你自己点」，只有「知道了」一个按钮，没有「让助手付」。用户自己点付款按钮，照常付款。
  - 例子(正)：练习页的「确认支付 ¥98.00 并报名」，脚本模型去点，服务器收到 0 条；网页上有提示和外圈 — 谁检查：`pay-stop.mts` a
  - 例子(正)：提示还在时用户自己点这个按钮，服务器恰好 1 条 — 谁检查：同上 e
  - 例子(反)：「下一步」「提交评论」照常点到，「支付宝」单选项照常选中 — 谁检查：同上 c
  - 例子(反)：让认付款按钮的判断永远答「不是」，服务器在 a 就收到付款 — 用例必须失败 — 谁检查：同上，故意弄坏产品复跑
- R2 侧栏那一步写「停在付款前，等你自己点」，不标失败。它不算失败的改动：同一轮再点几次也不被当成连续出错，不出「页面没有变化」。助手收到的结果说明扩展不点付款按钮、要用户自己点、不要换别的办法，并请它告诉用户页面上的金额、商家和付款方式后停下。
  - 例子(正)：同一轮点四次，服务器仍 0 条，四步都写「停在付款前，等你自己点」 — 谁检查：同上 a、b
- R3 网页脚本程序（browser_run）里的点击碰到付款按钮，同样不点。
  - 例子(正)：程序去点付款按钮，被拒绝，服务器不增加 — 谁检查：同上 d

## 技术前提

- 前提：付款按钮和发送按钮走同一条点击路径，程序在派发鼠标前已能读出落点上的按钮名字；「用户没让发」的标记已经能让侧栏、任务裁判和「页面没有变化」不把这一步算成失败。所以不需要新的小实验，复用[发送前确认](20261009-send-confirm.md)已验证的前提。结果：通过（以 `pay-stop.mts` 的 a、b 为证）。

## 边界与不做

- 在付款表单里按回车提交：程序不拦按键。
- iframe 里的付款按钮（多数真实收银台在 iframe 里）：程序读不到按钮名字，不拦。
- 名字读不到的付款按钮（只有图标、没有文字和标签）：程序认不出，不拦。
- 网页脚本程序里的页面脚本直接调用按钮的点击：这不经过点击动作，程序不拦。
- 侧栏不汇总金额、商家和付款方式，第一版只写按钮名。
- 网页脚本程序里被拦下时，侧栏那一步仍写「没成功」，并可能出现「页面没有变化」：不点的标记没有传到这一步的结果上。网站照样收不到付款。发送确认在网页脚本程序里被拒时也是这样。
- 用户在聊天里同意也不放行；以后要不要加「让助手付」，由用户另行决定。
