# 任务: 同一会话接着问，第 2 条消息起只有新内容不命中缓存（#271）

## 规则
- R1 历史只追加：本次运行的上下文和用户消息一起留在历史里，不删不改；第 N+1 条消息的第一次请求，以第 N 条消息最后一次请求的全部消息开头。
  - 例子(正)：同一会话连发 3 条，第 2、3 条第一次请求的前面部分和上一条最后一次请求逐字相同（末尾那条每次都换的应用状态快照除外） — 谁检查：`history-prefix.mts` a1、a2
  - 例子(反)：上下文改回只在本次运行里插入，第 2 条的请求从第 2 条消息起就不同 — 谁检查：同一用例，改代码后跑
- R2 同一页没变时不再带第二份：读页结果和历史里已有的一段一字不差，就换成一行指回去；页面变了照带全文。
  - 例子(正)：同一页追问，请求里这一页只有一份读页，加一行「unchanged since your earlier observation」 — 谁检查：`history-prefix.mts` b
  - 例子(正)：换到另一页再问，带新页的全文 — 谁检查：`history-prefix.mts` c
  - 例子(反)：去掉去重，同一页出现两份 — 谁检查：同一用例，改代码后跑
- R3 读页不读进助手自己挂在页面上的浮层（光标名牌、中止按钮、圈注）。没有这条，浮层每次运行重挂、编号会变，同一页两次读出来总不一样，R2 永远不成立。
  - 例子(反)：去掉过滤时，两次读页只差浮层那两行的编号，b 失败 — 谁检查：同一用例（第一次跑就是这样失败的）
- R4 真实阶跃上，第 2、3 条消息第一轮没命中缓存的 token（`input − cacheRead`）≤ 2,000 — 谁检查：工程师交替跑改前改后，读请求的 `usage`
- R5 记忆、过往任务、站点提示仍按本次运行给出；用例只看最后一段上下文 — 谁检查：memory-used-line、panel-tidy、site-hint、memory-foundation、memory-hardening、remember-corrections

## 还没答上的问题
- 无。#271 的 Q1：`conversationHistory` 在文字对话里和真实消息重复，语音轮次只在这里有。所以留着它，但每段只给上一段之后新增的轮次。Q2、Q3 先看诊断记录 `pre_observation.repeat` 的比例再定。

## 技术前提
- 前提：pi 的 `custom` 消息能写进会话日志并原样恢复。小实验：读 `pi-session-persistence.ts`，`reading-handoff` 已经这样用。结果：通过。
- 前提：读页的包装没有随机串，同一页两次读出来能一字不差。小实验：读 `wrapPageContent`；`history-prefix.mts` 第一次跑时两次读页只差浮层编号。结果：通过（去掉浮层后一致）。

## 边界与不做
- 不做压缩，不修剪旧读页（每次修剪都会改历史前缀）。
- 首轮仍给全文，不改成摘要加引用（#255 的证据）。
- 记忆段每次照带，不去重：它多半命中缓存，去重要改 6 个用例的判法，收益小。
- 代价：删掉的记忆在同一会话的旧上下文里还在，直到开新会话。用户原话本来就在历史里，所以不多泄露什么。
