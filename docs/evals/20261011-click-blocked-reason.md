# 任务: 点不了时，助手知道是被谁挡住、还是按钮不可用

10-11 用户同意（对照 browser-use-pi 的 `ax.ts` 之后定的任务 1）。

为什么：以前目标被弹层挡住时，点击回执只写「目标被其他元素覆盖」，模型不知道该先关哪个弹层。不可用（disabled）的按钮照样点下去，回执写「页面没有变化」，模型可能换办法反复点。STATUS 记着「失败时会露出 Chrome 错误码」，这是同一类问题：失败原因对模型没有用处。

## 规则

- R1 目标被挡住时，程序不点。回执写出挡住它的元素：编号 @N、角色和名字。名字来自网页，所以包在不可信网页内容标记里。挡住的元素也收不到点击。
  - 例子(正)：练习页上「Cookie 设置」弹层盖住「保存设置」。脚本模型点「保存设置」，回执里有「挡住」、dialog 和「Cookie 设置」，服务器收到 0 次点击 — 谁检查：`click-blocked-reason.mts` a
  - 例子(反)：把写名字的代码去掉，用例 a 必须失败 — 谁检查：同上，故意弄坏产品复跑
- R2 目标不可用时（按钮带 disabled、在 inert 区域里、带 aria-disabled="true"、或 visibility:hidden），程序不点，回执写「不可用」或「不可见」，不写「页面没有变化」。
  - 例子(正)：点 disabled 的「提交」和 aria-disabled 的「下一步」，回执写「不可用」，服务器 0 次 — 谁检查：同上 b
- R3 正常按钮照常点到，不被新检查误拦。
  - 例子(正)：点「普通按钮」，服务器恰好 1 次 — 谁检查：同上 c

## 技术前提

- 前提：页面里 `elementFromPoint` 命中的遮挡元素，能经扩展的 chrome.debugger（`DOM.describeNode`）换成节点编号，再从无障碍树往上找到它的角色和名字。小实验：`scripts/probes/covered-by-name.mts`。结果：通过（读到 dialog「Cookie 设置」）。
- 踩到的坑：`DOM.getNodeForLocation` 按坐标找元素，找到的是扩展自己画在页面上的「助手操作与状态」层，不是网页的弹层。所以要从页面里的命中元素出发，不按坐标问 CDP。

## 边界与不做

- 调试器被占用时走的页面内备用路径（domops），只保留旧的「被覆盖」说明。
- 透明（opacity:0）的目标不算不可见：常见的自绘勾选框把透明的原生勾选框盖在上面，点它是对的。
- iframe 里被挡的目标：命中检查只看顶层文档，跟以前一样。
