用户同意借鉴Grok Bot SendMessage思路做小实验，并指定cmux Grok负责实现。Boss承担标准/编排/独立验收。2026-09-09派发实现前冻结。前轮失败证据保留，不降低前轮事实、安全和连续性要求。

## 完成标准
- [ ] 1. 正式用户消息有显式交付边界与可追踪标识，区分接收/进展/结果或回答；任务内部text_delta、工具原始输出、worker报告、agent_end本身不得直接冒充正式交付。相同交付不重复显示/播报。— 谁检查：Boss生产路径独立事件/协议测试
- [ ] 2. 单个accepted新任务仍一句自然接收回应，贴合委托对象或目的，不能说已完成；只有接收回应不算已经交付最终结果。已产生结果但遗漏交付时，应有限补交或明确未交付，不能以静默/伪造成功收尾。— 谁检查：Boss状态/缺交付/真实模型测试
- [ ] 3. 受控网页任务的正式结果与语音使用同一份面向用户的交付内容或明确关联的同义口语内容；短语音通常1–3句、无Markdown标记/内部ID，讲出具体发现并保留读取范围与未确认部分，不能把助手报告提升成独立核验。— 谁检查：Boss真实M3+Step+隔离网页，逐句对照来源与界面记录；人听感
- [ ] 4. 随机组织名的活动/访谈两封邀请+周刊标题页，先不打开正文：追问“活动那个呢”点明实际活动对象；“不是访谈，是活动邀请”回到正确对象、不把访谈机构改成活动机构；关开语音后仍可指出该活动名；正文细节须先有实际读取证据。— 谁检查：Boss既有voice-conversation-run真实路径及独立事件序列
- [ ] 5. pause/resume/abort/rejected/failed/unknown保持原真实回执约束；错误/终止不能被旧结果覆盖。会话/run/voice代次隔离，旧结果或中断后的晚到输出不能交付到新轮；重连/重放不自动重做写操作。— 谁检查：Boss旧控制/恢复/隔离测试与故障注入
- [ ] 6. 现有侧栏正式答复/执行过程层级、控件和底栏保持；用户能在现有位置看见正式答复，语音内容与该记录一致且没有重复答案气泡。语音关闭时正常文字任务仍能交付。— 谁检查：Boss生产DOM与真实消息流；人观感
- [ ] 7. 不新增第三个模型/provider，不把普通闲聊与已通过的start接收回应都改成整段缓存；记录实际回答延迟与新增调用，说明代价，不用额外循环掩盖事实或复读失败。— 谁检查：Boss调用/事件证据；人连续体验
- [ ] 8. 执行者停笔后Boss统一npm run typecheck、npm test、npm run build、git diff --check；完整Diff保留前人改动，独立真实用户路径通过才交人试用。— 谁检查：Boss；人最终体验

## 边界与不做
- 用户随后明确要求三人协作：Grok负责Agent主链路、Kimi负责共享协议/ledger、Anti Gravity负责UI/history，按当前contract独占文件。此处仅更新人员归属，完成标准不变。Boss不把最终验收委派给实现者；执行者只做聚焦自测与归属类型检查，不修改本文件/Boss测试/验收脚本。
- 不提交、不推送、不自动重载用户扩展；不用用户正在使用的浏览器、邮箱或真实账户做任务。
- 直接试用户已选择的交付方式，不重做界面命名、视觉、粒子球，不引入大型消息框架/长期记忆/新provider。
- 文案来源规则与内容同一性可用显式工具或等价协议实现，不能仅增加提示词禁令/随机模板后称为消息交付层。
- 参考：docs/research/20260909-grok-message-delivery.md；Will's S的Linear back & forth与You assist me正文已读，采用可纠正、可停止、交付与过程分层；不据此添加多余能力说明/警告界面。
