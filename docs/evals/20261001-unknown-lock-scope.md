## 起因

- 10-01 真实事故：Drive 上传结果不确定后，助手连续 6 次调用 `resolve_unknown_result`（每次「页面读数中没有这段证据，未知状态保留」），直到原地打转保护叫停。

- GitHub #23：原生 confirm/prompt 弹窗（BYS-053、135，8/8 失败），关弹窗被当作写操作，被锁拦下。
- GitHub #25/#27：下载口令作废、时间框不可填后上锁。
- 0aa524b 已放开不带 body 的 GET 和存文件。

## 用户裁决（10-01）

只拦可能重复的危险操作：例如不确定刷卡成没成，就不让它再点一次付款（以及提交、发送、删除）。看网页、打开新页面、关弹窗照常。查不清就告诉用户并停下，不反复查。

## 边界与不做

- 不改危险操作本身的确认流程（提交前确认等）。
- 不放宽对「可能已提交/付款/发送/删除」的保护。
- 不处理时间框读数缺 min/max（#27 的另一半）与 arXiv 下载工具缺失（#25 的另一半）。

### 未覆盖与风险

- **只读脚本超时不记为不确定（标准 2 的一项）未做。** 宿主没有办法证明一段页面 JS 只读；按代码猜不行（effect-policy 已写明）。可选做法是让模型声明只读、扩展用 CDP `Runtime.evaluate` 的 `throwOnSideEffect` 强制执行，但需要真实浏览器实验确认它对常见读页脚本（`querySelectorAll`、`async`）可用，属于新增能力与模型接口变化，需裁决后另做。现在的影响：这类脚本超时后读页、换页照常，点击/填写被拦，交付标「有一步没确认」。
- 「派发前超时」只在扩展事后补报 `not_executed` 时解除（L7）；扩展始终不回话时仍是不确定。
- 点击之外（`double_click`、`press_key`、DOM 回退点击）触发原生对话框仍会等到超时；对话框开着时 `snapshot`/`read_element` 仍会卡 30 秒；`browser_run` 里 `dialog_info` 未启用（#23 其余建议）。
- 「对话框打开事件会在被挡住的 `Input.dispatchMouseEvent` 返回前送达」只在假 CDP 里验证，未在真实 Chrome 复现（未授权浏览器验收）。
- 第二次核查由宿主结束本轮：模型若在同一轮还有别的独立步骤没做，会一起停下；交付说明里只讲这一步。
