# 任务：免按键语音可选 GPT-Live：闲聊直接接话，要动手交给助手，插话马上停

YIS-137 / GitHub #172。用户 10-09 同意在查维基没过的情况下先开工。前提实验见 [GPT-Live 实验](../research/20261009-gpt-live-chatgpt-login.md)。

## 规则

- R1 设置里可以选「GPT-Live（ChatGPT 登录）」，下次开启语音时生效；默认不变。没用 ChatGPT 登录时开启语音，侧栏说明原因，不连接，也不退回别的语音。
  - 正：选了以后，开启语音时只向 `chatgpt.com` 建通话。检查者：`gpt-live-voice.mts`，网络记录。
  - 反：存的不是 ChatGPT 登录凭据时开启，不建任何语音连接，侧栏显示原因。检查者：同上。
- R2 闲聊由 GPT-Live 直接回答，不开任务。
  - 正：说「你好，陪我聊两句」，听到回答，任务数为 0。检查者：同上，假麦克风、真实 GPT-Live。
- R3 要动手的话只开 1 个任务；播报的内容来自任务交付给用户的结果，不是 GPT-Live 自己编的。
  - 正：说「帮我去维基百科查一下全双工」，任务数为 1；送回 GPT-Live 的文字等于侧栏里这次任务的回答；播报文字里的数字和外文词都能在这段回答里找到。检查者：同上。中文专名和说法是否添油加醋，程序只算覆盖率，由人看记录。
  - 反：同一次委派送达两次，只开 1 个任务。回传时故意多加一个假事实，检查必须失败。检查者：同上。
- R4 助手说话时用户开口，0.5 秒内停声；后台任务不因此停止。
  - 正：在播报中途插一句话。从用户开口到侧栏收到的声音降为静音，不超过 0.5 秒；任务照常结束。「用户开口」取两个时刻：假麦克风音频里插话的位置，和插话第一段转写到达的时刻。后者比真实开口晚约 0.2 秒，会让结果偏好看，所以两个都报，以前者为准。检查者：同上，侧栏对远端声音的音量采样。

## 技术前提

小实验 `scripts/probes/gpt-live-extension-premise.mts`（49 行）：在扩展侧栏里建 WebRTC，用 ChatGPT 登录凭据向 `chatgpt.com` 建通话，委派与回传都只走 `oai-events` 数据通道。结果：通过（201；1 次委派；回传后服务端确认收到；随后播报了回传的内容）。原件：`out/acceptance/gpt-live/2026-10-09T04-42-30-314Z-extension-premise/`。

第一次失败：假麦克风在连接建好前就开始播放，开头的话没被听到。这是实验脚本的问题；产品沿用「开口不丢字」规则另验。

## 边界与不做

- ChatGPT 登录凭据由离屏页的模型运行时取用并在快过期时刷新，侧栏不直接读存储。
- 任务进度只送不播报的通道；只有任务交付给用户的结果送播报通道。
- 不改语音默认值，不用 API key，不更新用户的日常扩展；日常扩展的真人试听先征得用户同意。
- 现有三项保护依赖扩展收到的音频帧，GPT-Live 的声音直接从 OpenAI 到侧栏，扩展收不到这些帧，所以这三项不搬过来：按回复编号核对来源、先扣住声音等转写判断「终止任务」、按音频帧确认用户已听到。说「终止任务」改由委派交给任务宿主。
- 「停声」只在侧栏把声音静音；协议里没有取消回答的事件。

## 证据

2026-10-09，隔离无头 Chrome、只装扩展、真实 GPT-Live 与真实主模型 gpt-6-luna，都用 ChatGPT 登录。命令见 `scripts/acceptance/real-path/gpt-live-voice.mts` 开头，原件在 `out/acceptance/real-path/*-gpt-live-voice*`。

| 规则 | 结果 |
|---|---|
| R1 没用 ChatGPT 登录（没有凭据；存的是 API key 两种） | 通过：侧栏写明「GPT-Live 要先在设置里用 ChatGPT 登录」，没有向 `chatgpt.com` 建通话，也没有连别的语音 |
| R2 闲聊 | 通过：直接回答，没有委派 |
| R3 查维基 | 通过：只开 1 个任务（同一次委派故意送达两次）；送回的文字等于侧栏回答；完整播报里的数字和外文都出自回答 |
| R4 插话 | 通过：打断闲聊回答 0.25–0.35 秒停声（6 次）；打断播报中的任务结果 0.33 秒停声（1 次） |

反证：

- 回传时加一个假事实「爱迪生在 1873 年提出」：GPT-Live 照着播了，用例判失败。
- 拆掉三层去重：同一次委派开了 2 个任务，送回的结果和侧栏回答对不上，用例判失败（失败在「回答一致」这一步，还没走到数任务那一步）。

## 测量过程中修正的判据

- 只用 AudioContext 造的麦克风流时，GPT-Live 收到结果后一直不播报（3 次）；换成真实假麦克风设备垫底、再叠加脚本语音后正常。这是测试方法的问题，产品用的是真实麦克风。
- GPT-Live 自己的回答，结束事件要等下一轮开始才到，改为看回答转写。
- 停声原来按 0.1 秒静音判，说话中的停顿也被当成停声；改为连续 0.8 秒静音。
- 播报核对原来对照「送给 GPT-Live 的文字」，反证时假事实就加在这段文字里，所以抓不到；改为对照侧栏里的任务回答。
- 第一版只核对插话前约 1 秒的播报；改为主流程让结果播完再核对，播报中插话另设一种情况。

## 实测发现

- GPT-Live 服务端不会很快停声：用户开口约 1.5 秒后才收到转写，打断闲聊时 3.9 秒后才停，打断任务结果时 6 秒内没停。所以插话由侧栏在本地判定，并立即静音。
- 本地判定的阈值没有在真人外放下校准，GPT-Live 自己的声音被麦克风收回来时会不会误触发还没验，这一点和 StepFun 一样。
- 被插话打断后，如果 GPT-Live 在同一轮里回应用户（例如「好的，先停在这儿」），用户听不到这句回应，因为静音要等它开始新一轮才解除。
- GPT-Live 在委派后、结果回来前，常先说一句「好的，我来查一下」。

## 没验到的

- 外放回声：用户试听时没有专门试外放下 GPT-Live 自己的声音会不会触发插话。
- StepFun 实际出声的用例（要有效 StepFun key）这次没跑；StepFun 设置用例通过。
- 连接建好前说的话会丢；凭据刷新没有跑到。
- 独立审阅后修的三处没在真实服务上触发过：误判插话 2.5 秒后自动放声、通话断开后提示并重连、结果念完才记为已播放。修完后整套用例重跑通过（10-09 06:04–06:07），但这三种情况本身没被制造出来。
- 两次委派紧挨着时，第一次可能拿不到页面资料，5 秒后说没执行；已记入语音架构，没修。
