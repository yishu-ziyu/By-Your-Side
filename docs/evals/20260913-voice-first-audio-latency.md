# 任务：语音首声更快到（在“只有一份正式回答”的前提下）

来源：Codex thread `01a09a5d` 收尾时留下的唯一未完成项——合成语音验证通过后写着“首声等待仍约 5–7 秒；延迟仍是后续改进项”。本轮先量清楚这 5–7 秒花在哪，再判断哪些能安全削减。

用户可观察的结果：说一句话，多久听到第一声。**本轮没有改动这条路径的任何生产行为**，只产出可复现的分解与结论。

## 1. 实测分解

来源：`out/acceptance/voice-greeting-live-2026-09-13T13-08-48-490Z`（合成语音→真实 ASR→真实分类→真实 Pi→真实 TTS→生产 VoicePlayer）。第 1 轮“嗨，晚上好。”逐段：

| 阶段 | 第 1 轮 | 4 轮合计 |
|---|---|---|
| 提交 → ASR 终稿 | 668 ms | 493–733 ms |
| ASR → 分类开始 | 1 ms | ≈0 |
| 意图分类（模型往返） | **2,676 ms** | 1,704–2,676 ms |
| 分类返回 → 主 Agent 首字 | **2,494 ms** | 同量级 |
| 首字 → 正式交付 | 306 ms | 150–310 ms |
| 交付 → 第一帧音频 | 680 ms | 628–698 ms |
| **合计** | **6,825 ms** | 4,907–6,954 ms |

**两段串行的模型往返占 5.2 秒，是全部问题的所在。**

## 2. 三个被数据否决的“本地优化”

### 2.1 分类器调参（否决）

同一提示、同一输入，极小提示作下限对照（`classifier-floor.json`）：

| 调用 | 耗时 |
|---|---|
| 极小提示·第 1 次（进程内首次） | 4,671 ms |
| 极小提示·第 2 次 | 2,432 ms |
| 极小提示·第 3 次（已热） | 1,405 ms |
| 生产分类调用（4 句） | 1,419 / 1,547 / 1,784 / 2,093 ms |
| 同上 + `reasoning:"minimal"` | 1,434 / 1,618 / 1,790 / 3,293 ms |

分类调用的耗时≈极小提示的耗时，说明**这 1.4–2.7 秒是供应商往返本身，不是我们的提示词规模、也不是输出长度**。加 `reasoning:"minimal"` 没有稳定收益（两句更快、两句更慢，噪声主导）。分类提示词只有 2,625 字符，削它没有意义。

### 2.2 换更快的模型跑分类（否决）

同样的分类任务，8 句固定输入，逐句与生产模型对比（`model-compare.json`）：

| 模型 | 中位耗时 | 与生产判断不一致 |
|---|---|---|
| `opencode-go/deepseek-flash`（现用） | 1,734 ms | — |
| `cliproxy/gemini-3.1-flash-lite` | 4,363 ms | 2 处，其中「把姓名改成李明」判成 chat（该动手的没动手） |
| `cliproxy/gemini-3-flash` | 4,205 ms | 1 处，「暂停」判成 pause |
| `cliproxy/kimi-k2.5` | 619 ms | 8 句全部返回空文本，解析不出计划 |
| `cliproxy/gpt-5.4-mini` | — | 池内不可用 |

本地池里的候选要么更慢，要么判断出错。**换模型不是免费提速**。（口径：按解析出的首个 action 比较，单次采样；换模型若要真采用，需要另外的准确率评估。耗时这一项已经先否决了它们。）

### 2.3 TTS 提前建连（不值得）

真实 Step TTS、生产音色、固定文本（`tts-first-frame.json`）：

| 条件 | 送字 → 第一帧音频 |
|---|---|
| 立刻送字（现状，含建连） | 812 / 812 / 915 ms |
| 等 900 ms 建连完成后再送字 | 543 / 544 ms |

即：**建连 + `tts.create` 只占约 270 ms，剩下约 540 ms 是服务端“收到字到出声”的固有时间**。为 270 ms（占整轮的 4%）去改语音流生命周期、每轮多开一个长连接，收益与风险不成比例，本轮不改。

## 3. 唯一还能显著缩短的方向（需要你裁决）

分类（2.7s）与主 Agent 回答（2.5s）现在是**串行**的：先判完这句要干什么，才让主 Agent 开始回答。两者耗时几乎相同。若让它们并行，整轮变成：

```
现在：分类 2.7s + 回答首字 2.5s + 交付 0.3s + TTS 0.68s ≈ 6.2s
并行：max(2.7s, 2.5s) + 交付 0.3s + TTS 0.68s        ≈ 3.7s
```

**预期收益约 2 秒（-35%）。** 做法：闲置态收到终稿时立刻把原话派给主 Agent，同时并行跑分类；主 Agent 的工具调用与正式交付先扣住，等分类结论落地——结论是“闲聊/新任务/看页面”就放行，是“停止/查询/需确认/指定会话”就丢弃这一次生成并按控制路径走。

必须同时看到的风险：

1. **这不是微调，是动你 2026-09-13 刚确认的回答归属规则**（“由主 Agent 负责的回答，语音层等待并播放正式交付”）。上一轮的重复回应事故就出在这条链上，所以我不擅自改。
2. 分类结论不是闲聊时，那次并行生成被丢弃——按本轮 8 句样本，8 句里有 3 句（停止、进度、需确认）会白跑一次模型。白跑的花费与时间不变差，但面板上会短暂出现一次被取消的运行。
3. 需要一个硬上限：分类超时（现有预算 6s/9s）时必须立刻放行或立刻失败，不能让主 Agent 一直扣着不动。

我不在没有你裁决的情况下动这条链。若你认可，我按上面三条风险各配一个反例来做，并用同一个 `voice-greeting-live.mts` 出前后对比。
