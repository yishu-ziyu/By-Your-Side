# 任务: 模型忙或限流时，错误卡自己倒计时、到点自动重试，用户不用点

## 规则
- R1 服务忙（429 限流、Kimi 403「concurrent request limit」、5xx、超时）时，卡上不用点就出现「N 秒后自动重试（第 k 次，共 3 次）」和一条细进度条，到点自动从出错处接着做，答案出来后卡收成一行回执。
  - 例子(正)：Kimi 回 403 同时请求数超限，卡上出现倒计时，约 8 秒后自己重试；再失败时同一张卡写「第 2 次」、等得更久；之后成功，答案出现，用户只发过一次 — 谁检查：`npx tsx scripts/acceptance/real-path/auto-retry-countdown.mts --headless`
  - 例子(反)：卡上只有「稍后重试」，要用户点了才开始倒计时；或 403 被当成 key 无效、让用户换密钥 — 谁检查：同上
- R2 额度或余额用完（quota、insufficient、余额、额度）不自动重试，卡上只有手动的「换一个模型」「稍后重试」。
  - 例子(正)：429 insufficient_quota，卡上没有倒计时，之后 12 秒内模型没有再收到这一轮的请求 — 谁检查：同上
  - 例子(反)：额度用完也倒计时，到点又撞一次 — 谁检查：同上
- R3 倒计时期间随时可以「立即重试」或换模型；自动重试用满 3 次（「立即重试」算提前用掉当前这一次）还不行，卡回到手动按钮。
  - 例子(正)：点「立即重试」，2 秒内模型收到重试请求；连着 3 次都失败后，卡上只剩「换一个模型」「稍后重试」，没有倒计时 — 谁检查：同上
  - 例子(反)：点了「立即重试」还要等倒计时走完；第 4 次还在自动重试 — 谁检查：同上
- R4 只替用户重试刚发生的那次出错，并且只由一个侧栏发：倒计时中用户发了新消息，旧卡停下；重开侧栏回放出来的卡只给手动按钮；两个窗口都开着侧栏时只有一个倒计时。
  - 例子(正)：倒计时中发新消息，新消息答完后再等过原来的到点时间，模型没有收到旧任务的重试，旧卡写「有了新消息，不再自动重试。」；倒计时中重载侧栏，回放的卡没有倒计时，15 秒内模型没有收到请求；第二个窗口的侧栏只有手动按钮 — 谁检查：同上
  - 例子(反)：新消息答完后旧任务又自己重跑；每次重开侧栏都多发一次请求；两个侧栏各倒计时一次 — 谁检查：同上

## 技术前提
- 前提：循环在卡出现前已在 0.5、1 秒各重试过一次（agent/src/pi-agent-loop.ts），卡上的每次自动重试也会再经过这两次；验收脚本按「每次卡上失败 = 本机门口连回 3 次错误」安排。小实验：`scripts/acceptance/real-path/error-recovery.mts` 原有 busy 场景用的就是 3 次。结果：通过
- 前提：等待时间没有测试开关；验收按真实的 8、16 秒等，加快只靠产品自己的「立即重试」。
- 前提：哪个侧栏负责重试不能按窗口编号定，`chrome.runtime.getContexts` 给侧栏的 windowId 是 -1（本用例实测）；改用侧栏页之间共享的 Web Locks。

## 边界与不做
- 不改循环自己的重试次数和间隔。
- 不按服务商返回的 Retry-After 调整等待时间。
