日期：2026-09-07。
角色：本标准由 ChatGPT（校验/编排）在 Coding Agent（实现）开始前提出。用户已授权先排查修复现有 bug，再推进长期能力。
检查基线：`fix/takeover-handoff-closure` / `6e1487b232a161fadc563cb098b42628c8076978`。开始实现时记录实际 base SHA；不得覆盖用户未提交的工作。

本轮不实现会话管理、长期记忆、技能学习、语音或截图附件，也不重新设计界面。路线图中的扩展构想不是实现授权。

## A. 稳定性排查与回归基线

目标：知道现有产品在哪些真实路径上可靠、哪些地方确实失败，并把确认的失败变成可重跑的回归。不是以一次代码扫描宣称“没有 bug”。

### 完成标准

- [ ] A1. 记录实际分支、SHA、Node/npm/Chrome 版本、扩展构建与加载状态、模型配置是否可用。区分测试浏览器与用户日常浏览器，不记录凭据或无关历史。— 谁检查：机器命令输出 + 独立审阅。
- [ ] A2. 实际运行并记录 `npm run typecheck`、`npm test`、`npm run build`、`node extension/test/overlay-check.mjs`；先阅读脚本前提，再运行 `npm run accept:browser`、`npm run accept:team`。每条写明命令、退出码、当次结果；不能引用旧笔记中的测试数量冒充本轮执行。环境不支持写 BLOCKED，不得当 PASS。— 谁检查：机器 + 独立审阅。
- [ ] A3. 建立下述核心路径矩阵，逐条标 PASS / FAIL / BLOCKED / 待人评，附可重复步骤和最小证据。优先复用仓库验收脚本，只补缺口，不新造平行框架。— 谁检查：自动化入口/记录 + 独立审阅。
- [ ] A4. 每个已复现缺陷记录触发条件、预期/实际、构建版本、严重度、脱敏证据和对应 issue；静态疑点单列“待复现”，不伪装真机结论。真实用户反馈优先于猜测。— 谁检查：独立审阅。
- [ ] A5. 修复按缺陷分开 PR：先有在旧代码上失败的最小复现/回归，再修复，再跑同一路径。不修改验收含义、不删除断言、不靠 sleep 或隐藏错误制造通过。更新测试是允许的，但应增强/纠正断言，而不是降低标准。— 谁检查：diff + 前后测试证据。
- [ ] A6. 本稳定化阶段退出前，矩阵内已确认的 P0/P1 缺陷归零；上述机器检查通过；接管/交还关键自动验收至少连续三轮通过；真实扩展的单页与双 Agent 路径有连续证据，观感待评项单列。存在 BLOCKED 时只能交付明确的部分进展，不能宣称底座已稳定。— 谁检查：机器 + 独立审阅 + 用户体验裁决。

### 核心路径矩阵（现有能力，不是新功能清单）

1. 连接与错误：native 主通道；现有 WS 回退；无凭据/模型不可用/断线时有可行动提示，不假显示成功、不无声丢输入。
2. 单页任务：观察→定位→操作→核验；工作标签与当前活动标签不混淆；运行中插话保留任务意图。
3. 控制权：单会话及 Lead/worker 全队接管；在途写动作排空后才宣告归用户；新/迟到写动作不落地；按各自绑定页新 snapshot 恢复；关闭 worker 页只暂停该成员；中止后不可借交还复活。
4. 生命周期：侧栏关闭重开、普通页面刷新、既有断线恢复语义；不把这些与“完整重启 Chrome 后恢复原任务”混为一谈。后者尚非现有承诺，暂不按缺失功能修补。
5. 危险确认：确认/取消/含糊回复；目标或页面变化后旧确认失效；取消不触发动作；确认不重复执行；覆盖已有 UI 入口，不因模型文字自称成功就通过。
6. 选中即问：空闲与任务运行时分别走选区→页上答复→侧栏继续；核对响应归属、取消、引用和消息流是否串台。有风险须先复现，不预设已坏。
7. 视觉与模型：滚动、内部滚动、缩放、窄侧栏、亮暗模式下目标标注/确认控件不错位或遮住关键操作；模型标签不捏造能力；切换成功/失败后显示与实际模型一致。

P0：未经允许的外部写入、接管后继续写、敏感数据泄漏等。P1：主路径不可完成、任务状态丢失/串台、卡死或假成功等。P2：不阻断主路径但误导或明显损害体验。功能尚未实现、主动降优先级的想法不自动归类为 bug。

安全与证据：本地可控页面覆盖自动反例；真实网站仅在授权的测试数据上验证，不以真实付款/发布/删除私有资料作演示。截图、日志不包含 token、cookie、私人正文或完整浏览历史。连续三轮 fixture 通过不能替代真实产品路径。没有本机浏览器访问能力时记录阻塞，不能用模拟画面冒充。

## B. 首个已确认缺陷：模型能力标签真实性

### 已有证据与范围

在基线代码 `extension/src/sidepanel/models.ts` 中，`modelReasoningMeta(provider, modelId)` 仅凭名称推断：所有 openai/openai-codex 都返回“支持档位调节”；未知模型默认返回“极速直接响应”。`shared/protocol.ts` 的 `ModelOption` 只有 id/provider/modelId/name，没有能力证据；`ClientMessage` 只有模型切换，没有思考档位设置消息。

因此目前可确认的是：UI 能力分类没有可信能力输入，且把未知能力当成肯定能力。这是静态代码确认；本轮校验者没有运行用户本机扩展，也不据此断言某个具体供应商模型的真实能力。

### 完成标准

- [ ] B1. 先增加反例：未知 provider/新 modelId、同 provider 不同能力、代理别名、能力缺省或冲突时，不得仅凭字符串输出“极速直接响应”“内置深度思考”或“支持档位调节”的肯定结论。旧代码应暴露失败。— 谁检查：单元测试前后结果。
- [ ] B2. 最小修复可以直接隐藏没有证据的能力标签，或显示中性的“能力未提供”；不得扩充另一张按名称猜测的表。需要展示确定能力时，必须来自已验证的 runtime/SDK/适配器元数据，含可解释来源；信息缺失保守降级。— 谁检查：纯逻辑/协议测试 + diff。
- [ ] B3. 区分模型本身能力与本产品已接通的操作：没有完整设置/回执/真实生效链路，不得暗示用户现在可以调思考档位；不得用“无推理”推导“响应一定快”。本 issue 不要求开发思考强度控件。— 谁检查：生产 UI 渲染测试 + 独立审阅。
- [ ] B4. 模型切换成功后标签来自该模型当前证据；失败时不显示成已切换；旧服务端或缺省字段不崩溃、不残留上一模型标签。若未改协议，证明保守展示同样满足这些条件。— 谁检查：模型/状态/兼容性测试。
- [ ] B5. 生产侧栏而非仅原型页，在未知模型、已知能力、切换失败三种状态下有实际渲染证据；亮暗模式与窄宽度不裁切核心控件。最小文案纠错不顺带改布局或换设计系统。— 谁检查：浏览器测试 + 人评（未测项明示）。
- [ ] B6. `npm run typecheck`、`npm test`、`npm run build` 全绿；检查是否影响 overlay 和既有验收入口并运行受影响项。文档中把历史“已支持档位”的表述与当前实际实现区分开，不把历史记录改写成从未发生过。— 谁检查：机器 + 独立审阅。

### 边界与不做

不更换 Pi、不升级模型或 SDK 以绕过问题、不新增联网探测/高成本请求、不做语音/记忆、不改用户凭据、不把“所有模型现在都可调”作为交付。
