# 任务: Agent 正确识别和报告页面下载结果，做对之后不再无故重复导出

来由：[导出迁移对照](20261008-export-transfer-ab.md) 与 [从纠正中学习](20261008-learn-from-correction.md) 里多次出现：文件已下载，Agent 却说「尚未生成」「尚未导出」；产品自动续做时同一份文件导出 3–6 遍，单次 38–151 秒。用户 10-08 定为本轮唯一交付，学习实验收尾。

分工（用户 10-08）：用户验收；代理定位原因、做最小修复。沿用现有网站、隔离环境和真实扩展，不改学习架构。修复要明显扩大范围时先说明，不自动追加。

## 规则
- D1 数据对：要全部数据就得到 200 条；只要当前页就得到第 1 页那 20 条。
  - 例子(反)：网站 A 只导出了 20 条就结束 — FAIL — 谁检查：`scripts/probes/export-transfer/ab.mts`（下载文件 + 网站记录）
- D2 回答与实际下载一致：文件已下载就不说没生成、没导出；只下载了 20 条就不说全部完成；回答里提到的文件名必须是真的下载下来的文件名。
  - 例子(反)：下载目录里有 customers-1.csv，回答说「目前文件尚未生成」— FAIL — 谁检查：同上（回答原文对照下载目录）
  - 例子(反)：回答说「已保存为 客户列表.csv」，下载目录里没有这个名字 — FAIL — 谁检查：同上
- D3 做对后不再导出：网站记下第一次满足要求的导出之后，不应再有导出。
  - 例子(反)：第一次就导出了 200 条，之后又导出两遍 — FAIL — 谁检查：同上（网站记录）
  - 例子(正)：第一次只导出 20 条，之后改对导出 200 条 — 不算重复（D1 要求它能改对）— 谁检查：同上
- D4 不靠堵住重试过关：自动续做保持开启；第一次做错时仍能在同一轮里改对。
  - 例子(反)：修复后网站 A 第一次只导出 20 条就停 — FAIL — 谁检查：D1 + 代码审查（不删续做、不加「禁止再导出」）

## 技术前提
- 前提：诊断记录能看出每次导出前后 Agent 调了哪些工具、拿到了什么下载回执。做法：每次运行结束在设置页导出诊断记录（沿用 `route-replay.mts`）。结果：通过（10-08）。
- 前提：判分器能分出 D2、D3 的错。`ab.mts --falsify` 加了「说没生成」「编造文件名」「做错却说全部完成」「做对后再导一次」四条错路。结果：通过（10-08，全部与预期一致）。

## 原因（10-08，修前基线的诊断记录）

- **Agent 直接点「导出」时，下载对它不可见。** 产品只在 Agent 先 `arm_event` 再点击时才把 Chrome 的下载回执交给它；没先布置的下载被扩展丢掉。点击回执的「页面反应」又不算 GET 请求，于是写「页面没有因这次点击变化，不要盲目再点」。网络记录里这次导出只剩一条 `failed GET …/export — document (net::ERR_ABORTED)`：这是跳转变成下载的正常样子，但 Agent 和目标核对都读成「导出被取消、没保存文件」。
- **补救动作制造了重复导出。** 看不到回执后，Agent 事后才 `arm_event`，下载早已发生，等 30 秒超时；再用 `download_url` 直接下导出链接，网站又导出一遍。目标核对看不到回执，最多两次催「接着做」。
- 证据：修前 `out/probes/export-transfer/2026-10-08T12-20-11-741Z-ab/` 下 T1-control-1、T2-control-3 的 `result.json`（`tools` 一栏）与 `traces.jsonl`。

## 修法

- 点击引起了下载时，点击回执如实写明：这次点击开始了哪个下载、Chrome 下载记录报告的结果（已完成及保存位置、字节数；未完成；失败及原因）。只认与当前页面同一网站发起的下载，完成与否只认 chrome.downloads。下载没有标签页归属，回执只说「处理这次点击期间开始的」，文件不对时仍可重做。只在两种情况下多等（最多 3 秒）：同网站下载还没报完成；点击引起的文档跳转还没结束或被中止。普通跳转加载完、普通点击没有下载，都不多等。
- 不改自动续做、不加「禁止再导出」、不改目标核对。改动在 [`shared/effect.ts`](../../shared/effect.ts) 与 [`extension/src/background/exec/effect.ts`](../../extension/src/background/exec/effect.ts)。

## 结果（2026-10-08，gpt-6-luna，不给记忆，T1、T2、T3 各 3 次）

修前：同一套脚本，产品两份文件临时退回 HEAD。修后：代码审查后的版本。判分按最终版 D2、D3 统一重判（`rejudge.mts`）。

| | 修前 | 修后 |
|---|---|---|
| D1 数据对 | 9/9（加上另一批干净基线共 17/18） | 8/9 |
| D2 说没生成 | 1 次 | 0 次 |
| D2 只有 20 条却说全部完成 | 0 次 | 1 次（与 D1 失败是同一次） |
| D2 编造文件名 | 0 次 | 0 次 |
| D3 做对后又导出 | 4 次 | 0 次 |

- D3 做到了：修后没有一次在做对之后再导出；T2、T3 六次都只导出一次。
- D2「说没生成」消失。修前那次：下载目录里有 3 个文件，回答「无法确认文件已保存」。
- **修后新出现 1 次失败（T1-control-1）**：Agent 只勾了本页「全选」（20 位），以为选中了全部 200 位；两次导出都是 20 条，回答「生成完整文件 customers-2.csv」，目标核对也判「做完」。回执如实写了 708 B（200 条是 6828 B），但 Agent 读不到文件内容，没发现。推测：修前核对模型看不到回执，会一直催；修后看到「已保存」就更容易放行一个保存了但内容不对的文件。样本只有 9 次，不能断定是修复引起的。
- 修前另有一批干净基线（`…/2026-10-08T12-20-11-741Z-ab/`，没留下载文件）：D3 失败 2 次，D1 失败 1 次（逐页导出 11 遍没导全），1 次 300 秒没结束。
- 剩下的根子是同一个：**Agent 读不到已下载文件的内容**。它要核对条数时只能重新请求导出链接（再导一次），或者凭页面状态猜。修这个要让扩展读本地下载文件，或改目标核对的判断标准，超出本次最小修复，未做。

### 判分器修正（跑后，均先证伪再用）

- 文件名识别把「……导出；customers-2.csv」整段当成文件名：分号等中文标点加入分隔，提到的名字以真实文件名结尾也算对上。
- 「说没生成」原来也抓「不能确认文件里有全部 200 条」：那是没核对内容，不是否认文件存在，收窄为只抓否认存在或已保存的说法。
- 测试工具不认「指定已构建扩展」，每次从源码现场构建：一批本应是修前的运行实际用了第一版修复，作废（`…/2026-10-08T12-34-01-258Z-ab/`）。修前改为临时退回源码重跑。
