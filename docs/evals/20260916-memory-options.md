## 问题定义

在持续合作中保留用户交代的事实、正在推进的事项和有证据的经验，在相关任务中正确使用，并随纠正更新或忘记，减少重复交代与重复纠错。

明确交代直接保存；任务结果依据真实证据留档；推断习惯作为候选。自动学习默认是否开启尚未决定。记忆不增加外部操作权限。当前要求优先于旧记忆。

### 现有实现

- C1 自然表达及补逗号均被拒绝；“记住我的默认邮箱是……”可保存。
- C2 仅“帮我报名”召回为空；加入“表单需要邮箱”后可召回。该探针说明查询表达的限制，不证明完整 Agent 一定填错。
- C3 临时语句不能调用长期保存工具，默认保持；未执行本次表单填写。
- C4 保存新默认邮箱后，旧默认条目依然存在。工具只有新增行为，不能把自然语言更新自动等同于管理 API 更新。
- C5 在直接用户要求为“总结当前网页”时，保存工具拒绝网页内容写入。
- C6 管理 API 删除后不召回；存储边界直接再次 create 可以恢复。这里只说明显式记忆存储没有来源抑制，不声称产品当前会自动重放此来源。自动经验已有单独抑制机制。

### 候选中已确认的产品风险

- 两者均通过真实模型保存自然表达的邮箱，说明无需要求用户使用特殊句式。
- Mem0 C2 对“帮我报名”召回邮箱，但对“比较雨伞和雨衣”也召回同一邮箱。仅凭非空 top-k 不能判定应该注入；需要相关性门槛和反例校准。
- Mem0 C3 保留“本次使用、默认不变”的语义；C4 新增变更事实后，查询“我的默认邮箱现在是什么？”仍将旧邮箱排在新变更之前。需要明确当前有效值，不能直接取第一条。历史记录本身保留并不构成错误。
- Mem0 C5 在本样本中未提取网页工具内容为用户邮箱；单个样本不构成防注入保证。C6 删除后列表为空，再次提交原文本又可存入；SDK 不知道这是旧来源重放还是新授权，来源抑制必须由产品补足。
- EverOS 第一次真实调用的画像正确总结了新默认邮箱，并保留临时邮箱的用途；与此同时，仅凭“总结当前网页”一条消息，生成了“指令极简、目标导向”等推断。候选能维护画像，不代表应原样采纳全部画像。
- EverOS 补验时，C4 新邮箱经历已可检索，但结束时画像仍是旧默认邮箱；本探针等待了经历索引，没有等待画像更新的独立完成信号，因此不能据此断言永久更新失败，也不能算即时更新通过。开启 include_profile 后，“帮我报名”和“比较雨伞和雨衣”都会携带画像；产品仍须选择何时注入。第一次有推断、补验没有同一推断，说明单次样本不能代表稳定策略。
- EverOS 的 memory HTTP API 未提供与现有产品同形的逐条 update/delete 接口；知识文档 CRUD 是另一条 API，不能冒充个人记忆遗忘。Markdown 可以编辑，但源材料、画像、派生索引和后台重新提取的遗忘一致性还需适配。C6 记为未跑。

### 建议

当前不整套替换。优先完善产品持有的个人事实和偏好：自然语言提议写入、来源校验、明确的当前值与临时覆盖、任务/表单需求驱动读取、纠正与遗忘回执。现有本地存储保留为可编辑的事实依据。

EverOS 保留为经历整理与后台候选生成的首选后续探针，不能把其自动画像直接升级为用户确认的偏好。Mem0 作为语义检索对照保留。若大量历史经历的召回已成为主要失败原因，且候选通过相同的删除、范围与反例门槛，再重新决定接入。

这不是两个开源项目质量排名，也不表示现有产品已修复。下一步应先落实事实/偏好闭环，再测同一六场景的真实扩展路径。
