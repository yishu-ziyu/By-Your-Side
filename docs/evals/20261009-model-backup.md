# 任务: 主模型卡住时，换成用户选的备用模型接着做

来源：#156 / Linear YIS-122。起因是 10-01 的日常记录：阶跃模型卡住，「你好」等了 170 秒；另一个任务遇到限流加回答中途断开，丢了约 8 分钟。10-04 只给主任务加了换模型（[验收](20261004-model-failover.md)），备用借用「快速模型」。

## 现在的问题（10-09 读代码确认）

- 默认的「快速模型」是「和主模型相同」，所以默认没有备用。ChatGPT 卡住时，用户等约 90 秒（每次等 30 秒，共试 3 次）才看到错误卡，然后要自己换模型。
- 用户的备用会是另一家服务商（阶跃或 MiniMax，都是套餐）。如果把快速模型选成阶跃来当备用，翻译和解释会变慢，因为阶跃的文字模型每次都先思考，关不掉。
- 换模型的过程中有一段时间不检查用户点没点「停」，备用模型可能在用户停下之后还发请求。
- 只有主任务会换；正式交付、语音判断，以及快速模型和主模型相同时的翻译、核对、记忆、主动建议，主模型出故障时都不换。

## 用户的选择

- 10-08：401 或额度用尽不换，只报原因；换到备用 5 分钟后，从下一条消息起回主模型。
- 10-09：备用单独设一栏「备用模型」，不再借用快速模型。用户在设置里选了备用，就算同意把对话内容发给那家；主模型卡住时直接换，侧栏告诉用户换成了谁，不再每次先问（取代 10-08 的「跨服务商先问」）。

## 规则

- R1 设置页有「备用模型」一栏，默认「不用备用」，只列已填 key 或已登录的服务商的模型。主任务里主模型卡住或暂时出错（连接错误、限流、服务端错误、回答中途断开），有备用就立刻换它接着做，侧栏写明从谁换成了谁；已经做完的步骤不重做；没显示完的半句不和备用的回答拼在一起。401 或额度用尽不换，只报原因。5 分钟后从下一条消息起回主模型。
  - 例子(正)：主模型接了请求不出字，约 30 秒后备用模型回答，侧栏写「已由 ChatGPT 换成阶跃」；主模型只被问一次 — 谁检查：`model-failover.mts`（扩展）
  - 例子(正)：主模型回 503，不等，马上换备用 — 谁检查：同上
  - 例子(反)：主模型回 401，换了备用 — 不合格 — 谁检查：同上
  - 例子(反)：去掉换备用，用例必须失败 — 谁检查：同上，故意弄坏产品复跑
- R2 换模型的过程中用户点「停」，备用模型一个请求都不发。
- R3 正式交付、语音判断，以及快速模型和主模型相同时的翻译、核对、记忆、主动建议，主模型故障时也用备用。

## 还没答上的问题

- 无。

## 技术前提

- 前提：本机脚本模型能同时扮两家服务商（一家卡住或回错误码，一家正常回答），扩展按服务商分别连。小实验：待写。结果：未跑。

## 边界与不做

- 不比价：两家备用都是套餐，不按次计费；不引入按量计费的 key。
- 不做「多个备用轮流试」。
- 语音的实时通话（GPT-Live、阶跃实时语音）断线不在本任务里。

## 结果

- 10-09 第一片（R1 的设置栏和换备用）：设置页有「备用模型」，主任务换它接着做。`model-failover.mts` 五例通过：挂起约 15 秒换阶跃、503 不等直接换、401 和额度用尽只报原因、「不用备用」不换。备用是另一家服务商：阶跃的请求在扩展里被拦下，转给本机脚本模型回答。
- 故意让产品忽略备用设置后复跑，挂起一例失败（90 秒没出回答）。
- 额度用尽常带 429，原来会被当成「忙」而换模型；已改为不换。去掉这项判断后复跑，额度一例失败（换到了备用）。
- 未做：5 分钟后回主模型、半句不拼接、R2、R3。
