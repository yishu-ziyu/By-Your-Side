# 任务: 语音回答时用户一开口，旧回答马上停下，不再跟用户抢话

## 背景

2026-09-25 用户在日常扩展里试用：回答念到一半开口打断，上一句回答一直念完，用户说话时它也在说。

原因（代码核对）：StepFun 生成语音比播放快，回答常在几秒内全部推到侧栏排队。用户开口时侧栏只推进轮次、不动播放（`player.follow`），本地只在供应商回报 `cancelled` 时清队列；回答已生成完时供应商没东西可取消，排队的音频照常播完。开口后旧回复迟到的音频还会被标成新一轮继续入队。

实测后修正：更主要的原因在服务端。StepFun 生成回答期间几乎不断句——插话用例里长回答生成了 75 秒，用户中途开口始终没有 `speech_started`；OS 项目（同一模型）的真人日志里也晚 4–5 秒（`ms_since_estimated_user_onset` 4025/5072）。所以只清本地队列不够，要本地先听出开口。

## 做法

参考 OS 项目「`speech_started` 一到就清播放队列、丢弃被打断回复的迟到音频」，再往前一步改为本地判定：

- 侧栏回答播放中，回声消除后的麦克风累计约 240 ms 超过约 -38 dBFS，就停播并发 `barge_in`。
- 宿主取消仍在生成的旧回复（`response.cancel`），已下发和迟到的旧回复音频作废；不作废最新请求、不设停声锁，下一句的工具调用照常。
- 服务端的 `speech_started` 到达时侧栏同样停播（兜底）。
- 不照搬 OS 的取消工具调用：一句话被切成两轮时前半句的浏览器调用本来就会作废并让模型重调（`a76c82b`）。

## 完成标准

- [x] 1. 回答正在播放时用户开口，旧回答的声音在开口后 1.5 秒内停下，并保持安静到用户说完 — 谁检查: `inproc-voice.mts --case=barge-in`（侧栏实际输出音量 vs 假麦克风里第二句开口时刻，均由测试自己的音量计测得，不读产品状态）
- [x] 2. 用户说第二句期间（开口 1.5 秒后到说完），旧回答不再出声（累计出声 ≤ 200 ms） — 谁检查: 同上
- [ ] 3. 插话后的新问题照常回答（回答含页面备注「周五前发货」） — 谁检查: 同上
- [x] 4. 前置条件：用户开口前 1.5 秒内旧回答确实在出声（累计 ≥ 200 ms）；不满足时本次不算通过也不算失败 — 谁检查: 同上
- [x] 5. 普通问答不受影响 — 谁检查: `inproc-voice.mts --case=question`
- [ ] 6. 附和（如“嗯”“对”）不应掐掉回答 — 谁检查: 人（日常试用）；本轮无可靠的合成附和用例
- [ ] 7. 日常扩展里真人打断手感 — 谁检查: 人

## 边界与不做

- 插话只停声，不取消后台任务（沿用“普通插话先停声，不自动停手”）。
- 不改服务端断句参数，不处理 StepFun 把一句话切成两轮的问题。

## 判据修订

- 第 4 条原为「开口前 0.5 秒内在出声」。两次运行开口正好落在故事句间停顿、开口后 263 ms 内仍有声音，改为 1.5 秒窗口。
- 第 1 条原为「开口后第一次连续 400 ms 没声音」。改前基线也判了通过（开口后 0.42 秒碰上句间停顿，随后又念了 2.9 秒），判据被停顿骗过，改为「从某刻起到用户说完都没有声音」。第 2 条（用户说话期间出声）一直是区分改前改后的主判据。
- 前置条件不满足时第 1、2 条一并判不通过，不算停声成功。
