# 任务: 多页任务少等几轮模型，更快且结果不变差

来源：[提速调研](../research/20261007-browser-agent-speed.md)第 0 步拆时间的结果。

## 规则

- R1 多页任务的轮数和总耗时下降（两步改动合并验收，用户 10-07 决定）
  - 例子(正)：在 Sitegeist 套件“打开三家公司整理成表”里，同一模型（gpt-6-luna）改前改后各跑 3 次，改后中位轮数少于改前，中位总耗时至少降 25% — 谁检查：`everyday-baseline.mts --suite=sitegeist` 的诊断记录 + 拆时间脚本
  - 例子(反)：轮数没变或耗时降不到 25% — 谁检查：同上，判为不值得
- R2 准确不变差
  - 例子(正)：Sitegeist 5 题与日常 6 题，改后每题通过次数不少于改前 — 谁检查：同一脚本的 pass/FAIL
  - 例子(反)：任一题改后通过次数少于改前 — 谁检查：同上，判负
- R3 打开失败或超时照实说
  - 例子(正)：页面超时时，结果只报超时，不附快照，模型仍按原规则去确认 — 谁检查：代码审阅（`agent/src/tools.ts` navigate）
  - 例子(反)：补读页面失败导致整次打开被报成失败 — 谁检查：代码审阅

## 还没答上的问题

- 无

## 技术前提

- 前提：任务开始时的预观察已用同一 snapshot 调用把页面交给模型，耗时约 65 ms（10-07 诊断记录 `pre_observation`）。导航后同样调用可行。小实验：沿用预观察实现，不另写。结果：通过（已在产品中运行）。

## 边界与不做

- 不改 browser_run 程序里的 navigate（程序自己决定何时读）。
- 不处理模型 30 秒不出字的超时重试（改前改后都有，另记）。
- 不改快照内容与长度。
- 不改回答格式（“缺来源网址”实为脚本误判，见下文测量方法修正）。

## 实测

### 第一步：navigate 结果直接带新页面快照

模型 openai-codex/gpt-6-luna，Sitegeist 套件“三家公司整理成表”，各 3 次。

| | 改前 | 改后 |
|---|---|---|
| 轮数 | 7 / 7 / 4（中位 7） | 4 / 5 / 5（中位 5） |
| 总耗时 | 32.2 / 44.3 / 20.4 秒（中位 32.2） | 26.4 / 25.5 / 31.4 秒（中位 26.4，−18%） |
| 工具执行合计 | 0.4–0.5 秒 | 0.4–0.6 秒 |
| 回答内容（人工核对） | 3/3 正确，含来源网址 | 3/3 正确，含来源网址 |

- R1：轮数下降成立；中位耗时只降 18%，**未达 25%，判未通过**。波动从 20–44 秒收窄到 25–31 秒。
- R2：Sitegeist 其余 4 题改前改后都是 3/3 通过；日常 6 题改后 6/6 通过。
- R3：代码审阅成立：超时不补读，补读失败退回原结果。
- 相关单元测试：15 个文件 267 项通过。

剩余耗时：三家公司仍是一轮打开一家（3 轮）加一轮作答；工具执行不到 2%，其余都是等模型。

### 测量方法修正

改前改后 6 次回答全部正确，脚本却判 5 次“回答缺少来源网址”。原因：回答把网址写成 Markdown 链接，侧栏只显示“公司资料页”，脚本只读可见文字。已改为同时读链接地址（`everyday-baseline.mts` PANEL_STATE）。原判定保留在上面的记录里。用户 10-07 确认：链接点得到即算注明来源网址。

### 第二步：多页收集用一个 browser_run（系统说明加一条）

第一步只降 18%，剩余是“一轮开一家”。第二步在系统说明“Speed and decisiveness”加一条：已知多个链接时，一个 browser_run 依次 navigate + snapshot，一次带回。

改前补跑 5 次后共 8 次；两步都改共 13 次（8 次常规 + 5 次带侧栏计时探针，探针已撤）。时间取诊断记录 run_start→agent_end。

| | 改前（8 次） | 两步都改（13 次） |
|---|---|---|
| 轮数中位 | 6.5 | 3 |
| 总耗时中位 | 33.9 秒 | 16.6 秒（−51%） |
| 最慢两次 | 44.3 / 82.2 秒 | 34.9 / 50.6 秒 |
| 30 秒首字超时重试 | 1/8 | 2/13 |
| 回答正确（人工 + 修正后脚本） | 8/8 | 13/13 |

- R1：通过。
- R2：通过。Sitegeist 其余 4 题两步都改后 3 轮全部通过；“做小工具”有两轮变慢（27.4、22.7 秒），输出 token 与首字时间不变，是模型吐字速度变慢，与改动无关。
- 改前也有模型自己选用 browser_run 的情况（8 次里 3 次），耗时 15–36 秒；系统说明让它稳定走这条路。

### 第三步：代码检查后的修正（10-07）

代码检查发现第二步的三个问题，修正后复测：

- browser_run 带回的页面正文没有不可信标记、没有遮凭据，绕过了注入防线 → 与 snapshot 同样处理（新增测试，修前失败）。
- 返回超过 2 万字被截断，只有“[truncated]”一个词 → 写明显示了多少、缺了多少、该怎么办。
- 系统说明残留“navigate 后总要 snapshot”“一个程序只做一步”，与新行为冲突 → 改写。

删掉残留说明后复测变慢（25–38 秒，4–5 轮）。临时记录模型写的程序，发现根因：模型照 navigate 工具说明，以为程序里的 browser.navigate 也带回页面，取 `r.text`，实际为空，只好再读再跑。修法：程序里的 navigate 与直调一致，就绪后带回 `text`（`browser-program.ts`，新增测试，修前失败）。临时日志已撤。

| | 改前（8 次） | 三步都改（6 次） |
|---|---|---|
| 轮数 | 中位 6.5 | 6 次都是 2 |
| 总耗时 | 中位 33.9 秒 | 7.7–12.3 秒，中位 9.8 秒（−71%） |
| 超时重试 | 1/8 | 0/6 |
| 回答正确 | 8/8 | 6/6 |

Sitegeist 其余 4 题、日常 6 题全部通过；相关单元测试 41 个文件 512 项通过。

### 国产模型复核：MiniMax-M3.1-Flash-Preview（minimax-cn 编程套餐）

GLM 编程套餐余额不足、OpenCode Go 订阅停了、Kimi 令牌将过期，改用 MiniMax。设置页 10-06 重做后，API key 服务商走界面配置会卡住，测试改用 `--direct-config` 直接写配置。

| 多页调研 | 改前（4 次） | 改后（4 次） |
|---|---|---|
| 轮数 | 4 / 3 / 2 / 4 | 2 / 3 / 2 / 3 |
| 总耗时 | 10.6 / 14.7 / 9.4 / 21.1 秒（中位 12.7） | 8.1 / 14.7 / 5.9 / 14.8 秒（中位 11.4） |
| 回答正确 | 4/4 | 4/4 |

- MiniMax 改前就常自己用 browser_run 或多开标签页，提速幅度小；没有变慢、没有变错。
- 改后日常“复制一句到草稿框”首轮复制错句子；改前改后再各跑 3 次全部通过，判为模型偶发。改前“做小工具”失败 1 次，改后通过。
- 测试脚本误把新的错误卡片记成“没有报错”（侧栏实际显示了“模型拒绝了请求”卡片），未修，另记。

### 未解决

- 侧栏显示延迟：13 次里 2 次，模型答完后约 22–27 秒脚本才看到回答（诊断记录与请求记录都显示早已结束）。加探针的 5 次未复现，读侧栏都不超过 1.5 秒。原因未确认，可能是产品显示问题，也可能是脚本问题。
- 首字超时：模型 30 秒不出字被判超时再重试，单次多花 30 秒以上。改前改后都有。

环境说明：第 1 次改前测量时，机器上有另一会话的测试浏览器在跑，耗时可能偏高。
