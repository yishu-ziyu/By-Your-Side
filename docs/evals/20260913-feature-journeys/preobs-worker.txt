## 根因（证据）

新任务首轮预观察的 snapshot 是工具帧，扩展在 `executeToolCall` 里用最近发布的身份校验：`current = conversationSummaries.runId`，`runId !== current` 就报“原任务已停止或发生变化，操作未执行。”（[extension/src/background/index.ts:962](/Users/mahaoxuan/Desktop/ego/extension/src/background/index.ts:962)）。运行时的每个帧都经会话回调带上当时的 `progress.snapshot().runId`，而 agent 侧只在 `agent_start` / `status` 时才发 `conversation_updated`（[conversation-manager.ts:471](/Users/mahaoxuan/Desktop/ego/agent/src/conversation-manager.ts:471) 附近）。于是次序是：

1. `progress.request()` 铸出新 runId（扩展还不知道）；
2. `session.sendUserMessage` → 预观察 `rpc.call("snapshot")` 同步发出 tool_call，已带新 runId；
3. 扩展拿新 runId 与旧/空身份比对 → 立即拒绝（trace 里 ms=6）。`agent_start` 之后的身份发布已经太晚。

这正是证据 trace 中 `3e34d831`、`f7a34ff0` 两次 `pre_observation_failed` 的来源；简单任务因此失去预注入，多绕模型轮次。

## 改动（约 15 行）

- 新增 `publishRunIdentity(conversationId)`：把当前 runId 立刻以 `conversation_updated` 发布（[371](/Users/mahaoxuan/Desktop/ego/agent/src/conversation-manager.ts:371)）。
- 用户新消息路径：仅当 `request()` 真的换了 runId 时才发布，且发生在 `runtime.handleMessage` 之前（[615-622](/Users/mahaoxuan/Desktop/ego/agent/src/conversation-manager.ts:615)）——运行中的同一条消息转插话时不换身份。
- 任务动作 `start` 路径：把原来在 `session.startTask` 之后才发的 `conversation_updated` 提到之前（[403](/Users/mahaoxuan/Desktop/ego/agent/src/conversation-manager.ts:403)），语音/动作启动的新任务同样受益。
- 身份闸门本身（runId/epoch 校验、`abortedRuns`、stale run 过滤）一行未动。
