# 任务: 网站方法验收的确认卡按同一规则判定，测量失败不再靠逐个补丁

起因：22replace 在 10-03 重跑 11 轮以上，前 3 次失败都是验收脚本手写批准条件漏了扩展附加参数或宿主自己发起的读页，不是产品问题；同文件其余 8 个 22 组场景对确认卡一律点“允许”，不核对内容。上一步：[前提小实验](20261004-premise-probes.md)。

## 规则

- R1 22 组场景（脚本模型）的每张确认卡由同一规则判定：模型发起的卡必须与当前任务脚本步骤的动作和参数逐项相同，只允许附加扩展补充的 `tabId`/`formRequirements`/`userValueProvided`/`userValueHostname`，且 `tabId` 是练习站标签页；宿主发起的卡只允许读练习站页面（snapshot）和接管练习站标签页（worker_tabs claim）。
  - 例子(正)：在 10-03 全部已存档的 22replace 运行里，当用新规则重判每张卡时，那么当时最终放行的卡全部放行，含首轮被误拒的 `snapshot {tabId}` 与带附加参数的 fill。 — 谁检查：`npx tsx scripts/acceptance/real-path/approval-plan.replay.mts`
  - 例子(反)：在 S22-MISSING 任务下，当出现脚本步骤里没有的卡（重放用 js POST，真实运行用未声明的备注 fill）时，那么拒绝并以“测量失败”结束。 — 谁检查：重放用例＋`--inject-undeclared` 真实运行退出非 0
- R2 卡片绑定不放宽：只认当前选中会话、当前 run、未过期、由验收输入的任务；旧 run 的宿主读页静默拒绝且不算失败，其他旧卡算失败。
  - 例子(正)：旧 run 的 snapshot 卡被拒且场景继续。 — 谁检查：重放用例（10-03 存档中的 stale 卡）
  - 例子(反)：会话不匹配的 fill 卡被拒并失败。 — 谁检查：重放用例
- R3 故意设计的越权动作（编造备注、页面脚本提交、POST、回车提交）仍按脚本步骤放行，让扩展自身的防线接受检验；判定结果以服务器 POST 计数为准，不由批准规则代替。
  - 例子(正)：22edge 的 `js` POST 卡放行后服务器 0 POST、场景通过。 — 谁检查：`remember-corrections.mts --scripted --only=22,…,22fetch`
- R4 22 组 9 个场景在新规则下第一轮全部通过，测量失败 0。 — 谁检查：同上命令，产物里 `consent-log.json` 无未知卡

## 还没答上的问题

- 无。22fetch、22edge 的卡片形状在第一轮观察中确认；出现新形状即按 R1 记失败，再修声明，不放宽规则。

## 技术前提

- 前提：10-03 存档里 22replace 出现的确认卡只有 snapshot、fill、click、worker_tabs 四种，扩展附加参数只有上述四个键。小实验：`jq` 汇总 `out/acceptance/real-path/*/22replace-consent.json`（8 份存档）结果：通过。

## 边界与不做

- 只改 `remember-corrections.mts` 的 22 组（脚本模型）；真实模型的 22live 与其他场景仍是原行为，迁移另议。
- 不新增通用 JS/POST 批准，不改产品代码，不改场景的期望结果。

## 结果

**离线重放（R1、R2）**：12 轮 10-03 存档共 179 张卡。06:51–08:10 七轮当时被误拒导致测量失败的卡，新规则全部放行；5 个改造反例（未声明 js POST、改填写值、别的标签页、别的会话、已过期）全部拒绝并记失败。2 张未计：06:53 早期日志缺模型请求记录；08:16 一张卡所属任务标记后来已改名。

**测量方法修订（保留原记录）**：首版规则要求读页卡属于当前任务，重放显示上一任务收尾的读页卡在 10-03 各轮有时被旧脚本拒绝、有时放行，场景都通过。该类卡只读练习站，期望改为“不算失败”，规则恢复为“属于验收输入任务的当前 run 即放行”。不改任何场景的成功判据。

**真实运行第 1 轮** `out/acceptance/real-path/2026-10-04T03-44-04-739Z-remember-corrections-scripted-73857/`：7/9 通过，22replace 首轮通过（10-03 存档有 12 轮运行）。R4 未达成：22b、22fetch 测量失败。两者同因——browser_run 批处理步骤内部的 fill/click 与网络 POST 各自弹卡，旧脚本对这两个场景一律点允许，从未核对过；新规则首次把它们暴露出来。修复：脚本步骤旁显式声明批处理内部动作（`form-method-rules.mts` 的 `S22_NESTED`），内部卡须在声明里、所属 browser_run 有原生调用记录、属于当前任务与 run。规则对第三类“核对后重设”卡明确拒绝。

**真实运行第 2 轮** `…/2026-10-04T03-57-33-129Z-remember-corrections-scripted-82823/`：4/9。批准规则 0 张误拒；失败来自产品。22 的“补备注后继续”前，宿主重启续接的读页卡获批 631 ms 后仍被判“未获准或确认已作废”，原任务停在中断，占住练习站标签页，其后 22b/22scope/22override/22replace 连锁失败。代码与卡片证据指向竞态（推断，未修）：`agent/src/session.ts` 续接预读不带新 runId，`extension/src/background/index.ts` 用会话摘要里的旧 runId 绑定确认；`activation-consent.ts` 批准时重读的上下文含会话当前 runId，摘要切到续接 run 后不再相等。批准早于切换才生效。

**真实运行第 3 轮** `…/2026-10-04T04-09-08-005Z-remember-corrections-scripted-96914/`：8/9，第 2 轮竞态未复现。批处理内部动作按声明放行，扩展拒绝空备注提交，0 POST。22b 的回车部分失败：扩展同样 0 POST、备注为空，但给出的是 #38 合入的通用“回车或空格可能提交当前表单”拒绝，而场景期望“备注为空”的专门拒绝。属于场景期望与已合入安全规则的冲突，是否改成功定义待用户裁决；本步不改。

**结论**：补上批处理声明后，第 2、3 轮共 321 张卡零误拒（第 1 轮 169 张中 2 张因声明缺口被拒）；R4 未达成，剩余失败都在产品侧（续接竞态、回车拒绝原因）。

**反例 `--inject-undeclared`**：首版注入 js POST，结果整轮通过——扩展在弹卡前就拒绝了这次表单绕过，卡片没到批准规则，反例没有检验到规则（`…/2026-10-04T04-20-15-260Z-…-5380/`）。改为多填一个未声明的备注值后，卡片被拒并以测量失败结束，服务器 0 次带该值的提交（`…/2026-10-04T04-21-35-454Z-…-6798/`）。

**用户裁决（10-04）**：回车提交被 #38 通用规则拦下、0 POST 且备注为空，算拦住。22b 期望改为接受“备注为空”专门拒绝或通用回车拒绝之一；其余条件不变。复跑 22b 通过，回车部分 `enterRefused:true`、0 POST（`…/2026-10-04T04-35-37-179Z-…-14393/`）。续接读页竞态由用户决定立即修复，另立验收。
