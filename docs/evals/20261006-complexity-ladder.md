# 任务: 一条命令量出浏览器自动化做到第几级（L1–L7），重构前后用同一把尺子比

背景：重构方向取决于产品要撑住多复杂的浏览器自动化（用户 2026-10-06）。调研发现 L5 长任务、L7 多任务同时跑在现在的扩展形态里没有证据，所以先造尺子再动底座。

## 规则

- R1 一条命令按级跑完、出表：`node eval/harness/ladder.mjs --tag <名> --models openai-codex/gpt-6-luna` 跑 [ladder.json](../../eval/tasks/ladder.json) 每题 3 次，写出每级通过数、中位工具调用、中位耗时、环境失败数和每题各次结果。
  - 例子(正)：基线跑完，`eval/runs/ladder-<名>/ladder.md` 有 L1–L7 七行 — 谁检查：命令输出
  - 例子(反)：站点连不上、限流、验证码计入失败 — 谁检查：`ladder.md` 的「环境失败」列与 judge 的 environment 字段
- R2 L6 像用户一样接管：页面满足题目的 `takeover.when` 时，框架点侧栏「接管」，等到「已暂停」，用鼠标和键盘改一个字段，再点「交还」。只有改的值被保留、其余要求做完才算通过。
  - 例子(正)：BYS-149 冒烟，框架在 11.9 秒接管，264 毫秒后显示已暂停，电话改成 13911112222 — 谁检查：结果 JSON 的 `takeover`
  - 例子(反)：助手交还后把电话改回 13800000000 — 谁检查：judge（规则写明判失败）
- R3 L7 两个任务同时跑在同一个浏览器：第一题发出后，框架在新标签页、新会话里发第二题；所有会话都不在「运行中」才收尾；两个会话的回答都交给 judge。
  - 例子(正)：BYS-150 冒烟，两个会话都回答、judge 通过 — 谁检查：结果 JSON 的 `parallel.conversations` = 2
  - 例子(反)：第二个会话还在跑就收尾 — 谁检查：收尾条件读会话菜单状态
- R4 新题的答案有独立来源：每题的判分规则来自站点本身（手算或逐页核对），不来自助手的回答。
  - 例子(正)：BYS-148 库存最多 22 本、19 本的三本，是逐页抓取 19 个详情页算出的 — 谁检查：人（本文件记录）
  - 例子(反)：用某次助手回答当标准答案 — 谁检查：人

## 技术前提

- P1：同一浏览器、真侧栏里两个会话能同时跑，框架能观察到。小实验：[p1-two-conversations.mts](../../scripts/probes/ladder/p1-two-conversations.mts)（脚本模型）。结果：通过，两个任务的点击在时间上交错。顺带发现：后台标签页里的任务每点一下约 8 秒，前台约 2.6 秒（原因未查）。
- P2：公开站点里有没有稳定的跨站 iframe 表单。小实验：[p2-frames.mts](../../scripts/probes/ladder/p2-frames.mts)。结果：checkout.stripe.dev 打开后没有表单 iframe；Stripe 文档页只有统计、验证码框。改用本地页（127.0.0.1 嵌 localhost 表单，Chrome 当跨站 iframe 跑），见 [ladder-sites.mjs](../../eval/harness/ladder-sites.mjs)，题目标「本地合成页」。
- P3：在 git worktree 里跑评测，诊断记录是空的。原因：借用主仓库的 node_modules 时，`@sideagent/agent` 指向主仓库的 agent 源码，构建的浏览器替身（诊断记录写 IndexedDB）只匹配本目录的 agent，没有生效。在 worktree 里 `npm ci` 后恢复（32 条）。
