# 任务: 同一个失败不再反复跑，今天的测试结果一条命令看清

开发环境优化第二项（A）。规则来源见[一页现行规则](20261012-one-rulebook.md)。

## 为什么

2026-10-07 至 10-11，真实路径用例每天跑 103–269 次。10-08 同一个用例（目标核对）跑了 30 次，30 次都因为同一句“回答里没有词条里的事实”失败。第 2 次失败时答案已经清楚，后面 28 次只是在等。

- 10-10 已经有“合并时不跑大回归”的规则，10-11 仍跑了 269 次。所以要让工具本身拦住，不能只靠规则。
- 每个用例的结果文件格式不同（至少 6 种），算不出“今天通过率”。但是每个用例都用退出码表示过或不过，所以流水只记退出码，不改 105 个用例。
- 日常基线用例在等待期间每 2 秒存一张侧栏截图和一份 HTML，是 `out/` 涨得最快的来源。

## 规则

- R1 同一用例、同样参数、同样代码失败 2 次后，第 3 次不跑，退出码 2，并说明怎样看失败原因、怎样强制再跑。
  - 例子(正)：临时用例连续退出 1 两次，第 3 次被拦下，退出码 2；加 `BYS_RERUN=1` 后照常运行 — 谁检查：临时用例 `zz-ledger-probe`（已删）
  - 例子(反)：换了参数（`--other`）或改了代码，不算同一个失败，照常运行；退出码 2（没加 `--headless`、缺凭据）表示没真正跑，不算失败 — 谁检查：同上
  - Ctrl-C 或被杀掉的运行不进流水，也不算失败。
- R2 `npm run runs` 列出今天每个用例的运行、通过、失败、被拦次数和分钟数，以及总通过率。 — 谁检查：命令输出
- R3 真实用例照常运行，并记进主目录的流水；在工作树里运行也记在主目录。 — 谁检查：`keep-foreground` 在工作树里 PASS（37 秒），流水多一行 `ok: true`
- R4 7 天前、没被 docs/scripts/eval 引用的运行目录自动清理；只认带日期的具体引用，工作树和主目录都查，包括没提交的文件。 — 谁检查：第一次运行清理了 146 个目录（239 MB），被引用的 73 个保留；主目录里一份未提交文档引用的假目录被保留，删掉这份文档后假目录被清理
- R5 日常基线默认不再每 2 秒截侧栏，加 `--wait-shots` 才截。 — 谁检查：人（代码审阅）

## 技术前提

- 前提：所有用例都通过 harness 启动，退出码表示过或不过。小实验：`grep -l 'from "./harness'` 覆盖 87/105 个用例；其余 18 个不记流水，也不被拦。结果：部分成立，已写进边界。

## 边界与不做

- 不统一各用例的结果文件格式；通过率只看退出码。
- 不清理 `out/` 里真实路径以外的目录（experiments、builds 等约 1.3 GB），因为它们是一次性证据，删不删由用户决定。
- 评测（`eval/harness`）的等待截图不变，它是等待体验评测的一部分。
