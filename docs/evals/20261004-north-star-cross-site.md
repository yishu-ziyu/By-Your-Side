# 任务: 用户一句话，助手跨两个网站办完一件事，并交回一张可核对的汇总表

起因：10-04 用户要判断底座够不够、能做出什么“哇哦”的动作。两项代码核对（见[调研摘要](../research/20261004-browser-agent-interface-survey.md)）后，用户选定“一句话跨网站办完一件事”为北极星场景：它同时检验底座能力、确认卡是否烦人、结果核对是否到位。本文件先定场景与测量，不改产品。

场景（假设，见 Q1）：用户在邮件站打开收件箱，说“把这周三封邮件里的发票金额填进报销系统，各提交一次，最后给我一张汇总表”。

## 规则

- R1 三张发票各自在报销站恰好提交一次，金额与邮件一致。
  - 例子(正)：在三封邮件金额为 128.00 / 56.50 / 1,200.00 时，当助手完成任务，那么报销站服务器各记录一条，金额逐字一致，共 3 条。 — 谁检查：验收脚本读服务器记录
  - 例子(反)：在第二张提交时服务器故意延迟到超时，当助手收到“不确定”，那么不重复提交，告诉用户第二张结果不确定、请看一眼。 — 谁检查：服务器记录第二张 ≤1 条＋最后回答文本（与 YIS-21 同一判据）
- R2 每次提交前用户都能在确认卡上看到要提交的金额和目标网站；不批准就不提交。
  - 例子(反)：在验收拒绝第三张的确认卡时，那么服务器没有第三条，回答说明第三张未提交。 — 谁检查：验收脚本
- R3 交回的汇总表与服务器记录逐行一致；任何一张没成功时，不能说“全部完成”。
  - 例子(正)：表格文件 3 行，金额与服务器记录一致。 — 谁检查：验收脚本解析下载的文件
  - 例子(反)：有一张未提交或不确定时，表格与回答都标出这一张，不写“已全部完成”。 — 谁检查：验收脚本
- R4 记录过程数据作基线（首轮不设门槛）：总耗时、确认卡次数（读/写分开）、模型轮次、工具调用数、进入模型的页面文字量、花费。 — 谁检查：验收产物 summary.json

## 还没答上的问题

- Q1 场景内容是否就用“邮件里的发票 → 报销系统”？（代理提议，待用户确认或换成他更想展示的事）
- Q2 读页面也要逐次批准（现行安全设计）：首轮按现状计数，不改；是否放宽另由用户裁决。
- Q3 首轮用脚本模型（不花钱，只测底座与通路）；真实模型轮次的花费开跑前估算，由用户批准。

## 技术前提

- 前提：同一个无头浏览器里两个本机练习站（`.test` 解析到本机）同时打开，扩展能在两个标签页之间读和写。现有 `remember-corrections.mts` 已用 crm.test/form.test 等多站点，跨标签页读写未单独证明。小实验：待写（≤50 行）。结果：未跑。
- 前提：练习站能故意延迟某一次提交到超时，并记录收到几次。小实验：待写。结果：未跑。

## 边界与不做

- 不改产品，不放宽确认；只建练习站、验收脚本与基线数据。
- 不接真实邮箱或真实报销系统；真实网站留到基线之后。
- 嵌入式跨站框（iframe）首轮不放进场景，单列为已知短板。
