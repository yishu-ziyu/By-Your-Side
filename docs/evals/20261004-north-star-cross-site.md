# 任务: 读文章时划选感兴趣的词，助手去用户常用的网站查，整理后每个词一条写进 Flomo

起因：10-04 用户要判断底座够不够、能做出什么“哇哦”的动作。两项代码核对（见[调研摘要](../research/20261004-browser-agent-interface-survey.md)）后定“一句话跨网站办完一件事”为北极星。初版场景是“邮件发票 → 报销”（代理提议）；用户当天改为自己真实会做的事：读 Claude / OpenAI 博客，划选关键词，去常用网站（维基百科、X）查，整理进 Flomo。本文件先定场景与测量，不改产品。

用户确认（10-04）：关键词由用户在文章里**划选**；Flomo **一个词一条**笔记。

## 规则

- R1 去哪查来自记忆：用户曾说过“查资料常去维基百科和 X”，助手就去这两处查；记忆里没有时先问，不擅自选。
  - 例子(正)：在记忆里有“常去维基百科和 X”时，当用户划选“Model Context Protocol”并说“查一下”，那么助手只在维基百科和 X 搜这个词。 — 谁检查：验收脚本读练习站访问记录
  - 例子(反)：在记忆为空时，那么助手先问去哪查，用户回答前不访问任何搜索站。 — 谁检查：同上
- R2 整理内容只来自实际打开过的页面，每条要点带来源链接；搜不到就写“没找到”，不编。
  - 例子(反)：在 X 搜索结果为空时，那么笔记写“X 上没找到相关讨论”，不出现 X 上不存在的内容。 — 谁检查：脚本比对笔记文字与练习站页面原文
- R3 每个词恰好写一条 Flomo 笔记；写前确认卡显示笔记全文；不确定时不重写。
  - 例子(正)：划选 2 个词，那么 Flomo 服务器恰好收到 2 条，内容与确认卡一致。 — 谁检查：练习站服务器记录
  - 例子(反)：在第二条保存时服务器故意慢到超时，那么第二条 ≤1 条，回答说明“第二条不确定，请看一眼”（与 YIS-21 同一判据）。 — 谁检查：同上＋最后回答文本
- R4 记录基线（首轮不设门槛）：总耗时、确认卡次数（读/写分开）、模型轮次、工具调用数、进入模型的页面文字量、花费。 — 谁检查：summary.json

## 还没答上的问题

- Q1 多个关键词怎么划：现有页面上下文只带“当前一段划选”（`shared/protocol.ts` `selection`）。一次划一段含多个词，还是每划一次说“加上这个”？（首轮按“每次划一个词、各发一句”测，逐个收集是否要做另议）
- Q2 读页面也逐次确认（现行安全设计）：首轮按现状计数，不改；是否放宽由用户裁决。
- Q3 真实网站轮次需要用户日常 Chrome 里 X 与 Flomo 的登录，且违反“验收只用无头隔离浏览器”的默认，必须另行取得用户授权；首轮只用练习站与脚本模型。

## 技术前提

- 前提：同一无头浏览器里 4 个本机练习站（blog / wiki / x / flomo，`.test` 解析到本机）可同时打开，扩展能在它们之间读写。现有 `remember-corrections.mts` 已用多个 `.test` 站点，跨 4 站未单独证明。小实验：待写（≤50 行）。结果：未跑。
- 前提：记忆能存“常去的查资料网站”并在新任务开始时被召回。小实验：待写。结果：未跑。
- 前提：验收脚本能在练习站页面上制造划选，并让侧栏发送时带上划选文字。小实验：待写。结果：未跑。

## 边界与不做

- 不改产品，不放宽确认；只建练习站、验收脚本与基线数据。
- 首轮不接真实博客、维基、X、Flomo；真实网站一轮在基线之后、取得授权之后。
- 嵌入式跨站框（iframe）、X 登录墙与限流首轮不覆盖，列为已知风险。
