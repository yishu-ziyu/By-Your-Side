## 2026-09-19 独立 worktree 的技能快速复用

技能编译器的临时目标也会进入既有结果账本。不同语义对象不能共用同一个 `[data-sideagent-target]`，否则第二个字段被当成第一个字段的重复填写；按语义对象分配标记，同一对象保留同一标记，不绕过去重。

“程序返回”“页面读回成立”“最终结果交付”是三个时点。既有宿主可能在 agent_end 之后补交付，候选只能在同 runId、状态空闲、账本允许完整报告且有真实 finding 时收尾；新任务和改口不得继承旧轮的待完成学习。任意 JS 或未知写入仍阻止学习，只有宿主自己生成的只读轮询错误可以在新的成功读回后恢复候选资格。

模型只用snapshot读结果时，唯一具名的status/alert节点可触发一次有时限的真实read_element来形成凭证，不能直接拿快照文字当凭证；多节点或只有输入框时不猜。改口后完成的残段不重新开始学习，避免保存成缺少前半段的“完整做法”。

额外 program-first 提示的配对没有满足目标，暂时显式开关启用；不能以技能复用的低延迟证明首次执行策略有效。原始失败、修正计时边界及当前门槛见[验收](evals/20260919-skill-fast-loop.md)。

验收必须连诊断目录一起隔离。本轮遗漏 `RunTrace` 默认目录导致日常 trace 轮转，未恢复旧日志；今后验收在构造会话前设置 `SIDEAGENT_TRACE_DIR`，Vitest 默认也是独立临时目录。会话/技能数据与诊断日志不要混称为同一种存储。

## 2026-09-19 集成到主线期间的续接结论

本轮来源与集成历史、当前状态分别见[集成验收](evals/20260919-skill-loop-integration.md)与 STATUS，勿用早期 worker 的合并中快照判断当前 Git 状态。

路由的候选概率判断原本同时承担「是这份做法」和「材料齐全可执行」，缺材料请求下模型会压低它，于是 `needs_input` 被吞成 `no_match`。已拆出独立的 `clarify_i` 判断（非执行、门限 .85，非目标样本 ≤.33、缺材料样本 .88–.93）；执行门限仍为 .9，且澄清路径结构上不可能执行。以后不要把这两个判断重新合成一条。

本树 `npm ci --ignore-scripts` 装不上 `rolldown` 的 arm64 原生绑定：lockfile 里 `@rolldown/binding-darwin-arm64` 只有 optionalDependencies 引用、没有包条目（npm 可选依赖已知问题）。正确修法是按 lock 的版本把平台绑定补进 `node_modules`；不要删锁文件或改依赖版本。

本轮 DeepSeek worker 内 Chrome 启动 SIGABRT，但主代理已有权限环境下同一隔离验收器可正常运行。不能把一个 worker 的启动失败推断成整个宿主无法验收；无需更改 Chrome 的 sandbox 参数。

技能运行的材料不进公开面，但"公开面"有三条容易漏的边：①`invokeDisplayTool` 的顶层 `tool_start.params`；②`observeProgramStep` 的子步骤（`onStep` 绑在 `createBrowserTools` 的闭包上，直接 `tool.execute` 也会触发，所以顶层隐藏后 `fill value` / `read_element expect` 仍会漏）；③失败文本（RPC 错误会把材料写回 message）。前两条按白名单只发"对哪个对象做什么"，第三条用本次已知材料逐个替换成 `[本次材料已隐藏]`——保留"哪一步没完成"的事实，异常本体仍原样给私有执行判定。`tool_observation` 只进结果账本（`conversation-manager` 提前 return），不下发侧栏、不进 RunTrace；账本落盘的是结果项描述，不含读数原文。

学习资格必须针对执行器真实能交付的内容：私下核验页面不等于向用户报告查询结果。旧判断曾假设执行器会报告结果，因此仅加新提示不足以修复已保存技能的本地匹配。现以输出契约版本认证，对所有来源失效旧资格；改内容必须删认证，显式手动执行仍保留。结构检查须先于认证独立运行，否则学习尚未完成就被资格门槛挡住。实测保守漏学及原错误口径见集成验收。

本地模板匹配必须要求每个材料槽位有成对引号；固定字面后缀仍会允许把后缀之前的额外动作吃进材料。无引号请求交语义判断，不能用字面后缀假装确定性边界。公开脱敏同时不能改变账本的执行身份：私有材料的哈希由宿主计算后传给账本，禁止用占位值求哈希。

## 2026-09-19 T05 接续入口：两个“看不见的断点”

A04「恢复触发后挂起」不是模型问题，而是扩展上行连接：旧连接 onclose 排的重连定时器（1s）在新连接建立后照常触发，`connectNative()` 的 teardown 把刚建立的 transport 拆掉，宿主侧等价于一次瞬时断连 → `manager.disconnect()` 中断正在续跑的 turn，且被中断过滤吞掉终态事件。修复在 `extension/src/background/uplink.ts`：定时器到点与 connectNative/connectWs 入口都在已有活传输时直接返回，`retry()` 先清旧定时器。复现器 `scripts/acceptance/t05-connect-repro.mts`（不调模型）：旧代码 host2 连接后 ~835ms 自杀重连，修复后 6s 稳定。任何“重连/补取视图”的新代码都要遵守同一约束：不得为了刷新而拆除正在服务任务的活连接。

`confirm_blocked_write` 的确认卡在本票前从未真正到达面板：`WriteConfirmBroker` 发出的 `consent_request` 少了 envelope `conversationId`，`parseServerMessage` 要求 `request.conversationId === msg.conversationId`，后台静默丢弃整条消息，用户只能等到「确认已过期」。这是 P0 有界恢复在实机上全军覆没的直接原因。补 envelope 字段 + 协议往返回归（`agent/test/task-confirmed-recovery.test.ts`）。同类的“宿主发了但面板收不到”问题，先查协议校验与 envelope，不要先怀疑 UI。

接续入口（`extension/src/sidepanel/resume-entry.ts`）的 「继续」只发 `task_action/resume`（requestId + expectedRunId + expectedControlVersion + 当前活动页 context），由 `ConversationManager.dispatchTaskAction` 的 resume 分支走既有 `session.resumeInterruptedTask`：先重读页面、核对身份、带持久检查点提示词。按钮出现的唯一依据是 T02 视图的 `resumable`（已扩到「idle/error 但只交付部分结果且恢复输入仍在」，与宿主实际支持的 resume 分支一致）。重启恢复期间用户手改的字段由两处提示词保护（`session.ts` RESTART CONTINUATION、`shared/control.ts` handbackContinueText）；若模型请求重设人工值，确认卡上应拒绝而不是允许。

集成注意：`agent/src/conversation-manager.ts` 本票只加了 2 处（`task_view_query` 分支、检查点不可用守卫放行），T04 合入时按此串行 rebase；T03 任务条与本组件各有一份等待原因文案，集成时合并到一处。

## 2026-09-19 记忆判断失败定位（MiniMax M3 期间）

user_memory「记忆判断失败，尚未修改记忆」有多个独立来源，不能混为「模型不行」：①插话到达即 `invalidateUserTurn`（session.ts 约 L884/L1253），会 abort 进行中的判断子调用，且 steer 通道从不重新 `beginUserTurn`（仅 sendUserMessage 路径），本轮剩余时间记忆写入必死；②同一回合 `turn.change` 同时缓存成功与失败（memory-runtime.ts：重试不能问到同意为止），同轮重试 2ms 返回旧失败；③判断子调用 15 秒硬超时（`AbortSignal.timeout(15_000)`），MiniMax-M3 `supportsReasoningEffort: false` 且无 thinkingLevelMap，思考压不下去，实测 15012ms 撞超时（deepseek-flash 的 minimal 映射为关思考，同类调用 4.9s 完成）；④底层 stopReason/errorMessage 在 session.ts 约 L442 被吞，界面只能说「记忆判断失败」。实测链（00:13–00:17）：插话后 6ms abort → 两次「当前记忆操作已失效」→ 用户点重试开新回合、M3 判断 15s 超时 → 同轮缓存失败 → 换 deepseek-flash 新回合 4.9s 成功。待裁决改进三点：超时按模型自适应或放宽；steer 后重新授权当轮重试；记录底层错误原因。证据 trace：`~/.sideagent/traces/1789745681628-dcc0bb06-236b-4d46-9015-7793aec002d6.jsonl`。

## 2026-09-18 Ticket 7 显示属性域

显示修改的两个失败来源必须分开查：执行层（in-page display 是条件赋值，省略字段天然保留原值）从不是缺陷；模型面才需要「只提交本次要求改变的字段」的指引。最新插话的明确修改要求对**其指明的属性**优先于任务早期限制（如「不要修改页面」），未指明属性仍受约束——缺这句时 MiniMax 会整体放弃执行显示修改。

配对串行窗口有归属缝隙：上一臂的交付 flush 晚到、落进下一臂事件窗口时，deliveryIdentity 会假阳性（混入的交付 runId/会话属于上一臂，内容是其答案）。生产多会话下属正常后台流量；修验收台时按「本臂 runId 配外会话 / 本臂会话配外 runId 才算失败，双外忽略」区分，不要预过滤掉背景交付。见[属性域修复](evals/20260918-display-attribute-scoping.md)。

## 2026-09-18 提示词预算与插话原任务契约

预算门槛是工程约束不是产品标准：`tool-surface` 测的是 SYSTEM_PROMPT 长度，09-16 时余量只剩 2 字符，谁最后加提示词谁越线（这次是 P0 `confirm_blocked_write` 指引 +170）。上调到 16,000 后不等于免检：再加内容仍要在预算内裁剪仲裁。

插话销账只认 Pi 原样回显的精确文本（`consumeCorrection`），所以任何附在插话载荷里的模型面提示都必须让 `record.input` 与实际载荷完全一致，否则补充永远销不了账、写入被永久阻挡。契约文本只进模型载荷，不进用户面回执。见[预算与契约](evals/20260918-prompt-budget-and-steer-contract.md)。

验收脚本效率分层：`--smoke`（1 对 2 臂，~2.5 分钟）迭代、`--pairs N --skip-boundaries` 抽查、全量只留正式证据；部分范围永远不置 `results.passed`，退出码凭显式 `pairsExpected` 判定。正式门槛仍 10 对+6 边界。并臂并行不可取：两臂同时跑会争本地模型池和 CPU，页变更计时的中位数口径会被污染。

关闭臂剩余已知问题：模型偶发擅自多改显示参数（pair-0 只要求改宋体，它把仅译文切成双语；字体与原任务答案都对）。属基线模型精度问题，非契约修复引入；开启臂 Jev 参数提取无此问题。未处理，保持整跑退出 1。

## 2026-09-18 Jev 显示修改 review 修复

页面实例变化属于请求失效，不是普通路由未命中；否则同一旧要求会借主模型回退在新文档重新执行。拒绝前已登记的要求也要从本次可恢复要求中撤销，不能在重启时复活；撤销必须绑定当次记录与 run，保留后来观察到的页面和后来的要求。

显示已经执行、读回已经核验、原任务已经收到修改是三个事实。Pi 接收修改失败不能删除补充登记来放开旧计划；保留输入与执行状态，沿已有接管/交还只补交接。核验 await 之后及最终回执之前再次核对生命周期。结束提示按 verified/unverified/unknown 分别生成，不用“有一段 fact 文本”推断成功。见[修复与反例](evals/20260918-jev-display-review-fixes.md)。

配对测试要隔离每臂会话和等价页面，避免上一臂“已由运行时改好”的聊天成为下一臂的依据。测试预置译文也必须携本臂 conversationId；默认注入会把页面提前归给 default，不能以关闭所有权检查解决。原任务可能在改口前后分别交付报告；验收看同一 run 最后一次原任务报告，不能拼接两份报告后误判为重复字段，也不能挑较早的正确报告。实际执行去重按 RPC 身份和参数核对，重放同一回执不等于重复执行；被闸门拒绝后主模型完成属于回退，不统计为 Jev 直达。

## 2026-09-18 接收持久化与有边界的确认续接

“已接收”回执必须以真实可恢复存储为准：Pi 的 SessionManager 在首个 assistant 消息前不创建文件，`appendCustomEntry` 可能只进内存。现在 `ConversationStore.sessionManager()` 用 SDK 自己的 header 建文件并 `setSessionFile` 接管（SDK 标为 flushed）。新任务不再分别写“附件条目 + 检查点条目”，而是单条 `sideagent-task-acceptance-v1` 同时保存检查点与必要附件；否则第二次 append 失败会留下半提交状态。派发分支在这一次 append 失败时回滚内存进度并明确“未接收”，不启动模型。不要把“调用了保存方法”当成“文件已可恢复”，也不要把两次独立 append 当成原子接收。

恢复旧未知写入时不能把旧项改成 executed：`recordConfirmedRecovery()` 新建一条独立结果项，旧项只写 `supersededBy`，只有取代项 satisfied 时才解除阻塞；新尝试若仍未知则继续锁住其他写入。`confirm_blocked_write` 先读当前页面（select 用 `displayValue` 取可见选项文字），已满足就只记录“当前要求满足”的新证据、不写入；需要重设时用户确认绑定 conversationId+runId、要求指纹、tab、**documentId**、对象与参数。点击允许时宿主重新读同一对象核对 documentId，允许后工具再次读，最后真正 `fill` 还受扩展 `assertObservedDocument` 保护；因此同 URL 刷新也不能复活旧确认。若最后一层明确返回 `not_executed`，只保留原 unknown，不再错误新建第二个未知写入。save/send/pay/delete 不走这条路。系统提示词有 15,000 字符硬预算，新增说明必须净额挤出，细节放工具描述。

旧 unknown 的原 fill 参数不能依赖模型复述：账本只增加 `valueHash=SHA-256(value)`，不保存字段明文。无需用户确认的“当前状态已经满足”必须同时满足稳定同一 target（旧 `@ref` 不算稳定）和相同 valueHash；模型换对象、改值、或旧快照没有 valueHash 时，即使新对象当前恰好已有这个值，也必须展示具体动作让用户确认。这个约束防止模型用“另一个看起来相同的字段”替代原未知动作。

## 2026-09-17 长任务重启检查点

实机发现的程序步骤编号是原始回执身份，不是文件/任务 key；不能把 `/` 替换为 `-` 来迁就 taskId，否则会破坏精确关联或引入碰撞。无效最新检查点也不能回退到较早快照，旧快照可能漏掉一次已发生的写入；应只隔离该会话并保留原文件。面板发送的是 task_action/start，不是 legacy user_message；继续语义必须在接收边界内解析，同时用原请求做幂等指纹，避免首次恢复成功后的重发被误判为新任务。见[实机反馈修复](evals/20260917-p0-acceptance-fixes.md)。

宿主重启和连接丢失不能冒充任务完成，也不能自动重放动作。后续 P0.4 已补任务级完整要求、页面 URL 指纹、Pi 原文件中的附件和未启动待办恢复；恢复仍需明确指令与新读数。不能把最近聊天中的所有用户发言提升为本任务修订，否则旧任务会复活。恢复读页走普通接收通道，暂停/取消必须能抢先使它失效；磁盘保存失败也不能阻止停止执行。辅助脚本在途但无结果绑定时，重启后保守保留不确定性。页面指纹不是账号身份，不同选择器之间也没有通用语义去重证明，见[恢复实现与边界](evals/20260917-p0-recovery-matrix.md)。

最终 finding 的参数生成早于同批工具执行，生成时允许交付不等于稍后仍允许；因此只在真实交付工具校验通过后送入语音，不能为首声速度重新把未执行参数当作事实。partial 是本轮交付终态，不是账本完成：保留未确认写入，自动补交付与窄“继续原任务”入口也必须守同一边界。读回只证明来源/顺序/页面范围，仍需模型对照用户目标，不能把它写成 successVerified=true。

用户已明确将实机模拟留给本地 Agent。2026-09-17 晚复测已由本地 Agent 执行，不再是待办；结果见上段与[修复与复测结果](evals/20260917-p0-acceptance-fixes.md)，缺预算或环境记 BLOCKED、未跑记 NOT_RUN 的口径不变。

复测裁决：保留程序步骤证据和未知写入保护，不把安全停写算成业务完成。下一步补范围明确的恢复决策，不清空 unknown，也不因页面实例更换或普通“继续”推断旧动作未发生。当前目标满足、新一次用户授权与旧动作实际执行是不同事实，必须分别记账；恢复清掉旧基线后，新 snapshot 不能伪造前后对比。见[裁决与后续标准](evals/20260917-p0-retest-adjudication.md)。

### 2026-09-13 首声等待：供应商往返是地板
