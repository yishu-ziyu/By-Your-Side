记忆系统：架构与交互调研

2026-10-01 · 依据：DDIA（ddia.vonng.com）对照现有代码；Mem0、Zep/Graphiti、Letta、LangMem、Claude、ChatGPT、Copilot、Cursor 等一手资料；CHI 2025/2026 与 2026 年记忆研究。标「已核对」的是我在代码里亲自确认过的。

一句话结论：底子的大方向是对的（本机、一个文档、串行写、保留旧版本），不需要推倒重来，也不需要同步引擎这类重武器。真正的问题集中在三类：没有被检查的规则（"同一件事只能有一个生效值"靠手工维护）、失败不留痕（判断失败、读坏数据都悄悄吞掉）、删不干净（"忘掉"之后，原话还留在诊断记录和过往任务里）。先花一小块把这三类补上，再做纠正询问。交互上最大的缺口是：你看不到它这次用了哪条记忆。

一、架构：现在哪里不稳（对照 DDIA）

DDIA 讲什么我们现在风险（今天撞到的）建议
多条数据之间的规则要在写入前检查（第 8 章 事务）"同一件事只有一个生效值"靠一条条指针手工维护连续替换后撤销出现两个生效邮箱每件事一个编号；每次写入前自动检查规则，不满足就拒绝写、数据不动
新代码读旧数据、旧代码读新数据都不能丢东西（第 5 章 编码与演化）过往任务读到看不懂的格式就当成空的，下次写入把原数据整个覆盖（已核对 task-history.ts:76-94）降级或数据有一点损坏，过往任务永久丢失统一格式规则：看不懂就只读、绝不覆盖；不把丢了条目的结果写回
晚一点可以，丢了不行；用请求编号去重（第 13 章）"要不要记"失败直接吞掉，不留记录（已核对 memory-runtime.ts:135）GLM 忙时你说的话悄悄没记住，事后也查不到失败留一条记录；放进"待判断"队列，任务结束后补判；用消息编号防止补判记两次
写完要能读到自己写的（第 6 章）面板手里是一份旧快照删除后点撤销报"版本冲突"（已修一部分；助手那边新记一条时面板仍会过期）每次写入给整份记忆一个递增版本号，面板发现变了就重新读
时钟会跳，不要用时间判断谁新（第 9 章）用"任务结束时间"当防覆盖的凭证；有效期存成绝对时间改时区等情况下日期和有效期会对不上（推断）用递增计数当凭证；以日期为准，读取时再算有效期
删除个人数据要删干净（第 12、14 章）"忘掉"只删记忆本身原话还留在回执、诊断记录、过往任务摘要里诊断记录只存编号不存原话；忘掉时连带清理
写入持久性没指定，用 Chrome 默认的"宽松"模式（已核对）断电或系统崩溃时可能丢最后几次写入记忆写入改成"严格"模式，一行

不要做的（规模：几百条、一个人、一个浏览器）

不上"操作日志当唯一数据源"（删除个人数据时反而麻烦）；不上 CRDT / 同步引擎（Automerge、Yjs、Zero 等，解决的是多人同时编辑）；不拆成一条一条存、不上向量检索、不上浏览器里的 SQLite。Mem0 在 2026-04 把"模型直接改写、删除记忆"去掉了，改成保留旧版本并相连——和我们现在的做法一致。

三、建议的顺序

  1. 先加固底座（新的一小块，约 1–2 天，用户几乎看不到变化）：同一件事一个编号 + 写前自动检查；过往任务读坏不覆盖；判断失败留记录 + 任务后补判；整份记忆的递增版本号让面板自动刷新；严格写入；诊断记录只存编号。
  2. 第二块：纠正后开口问你（已定 B 样式），带上 ②"在记忆里查看"。
  3. 第三块：回答下方"用了几条记忆"（①）和面板按种类分组（③）。
  4. 之后：导出 / 导入（一个带版本的文件，重复导入无害）；"查记忆"工具。
取舍用户开发者以后改下一个 agent 接手
