## 二、没做完的：Jev 提问方式重构（在 GitHub 分支上，未合并）

背景：Jev（TypeSafe System One）只做判断，点击由代码执行。原来的接入每一步都问一个宽泛的代理式问题：“Choose the next operation…”，附一段很长的规则说明，并把整页状态都发过去。这与官方指南相悖：System One 用来写软件，而不是当代理，应当由代码掌控流程、只问窄问题。

- **`fm/bys-jev-build-r1`（`64a6410`）**：已按新方式实现，由代码组合几个窄问题：指向哪个控件、是否在视图里、该先打开哪个菜单、是否已完成、是否高风险写入。同时加入连接层失败重试一次，以及一个“直接交付”开关（默认关）。单元测试 3083 项全部通过。**30 轮验收只跑了一部分就被停下**，数据在 `jev-build-partial/`：
  - 决策段已跑约 18/30 轮：新做法在 S5 两个入口、S6、S6N 以及留出任务 H1、H3–H8 上全部成功（18/18），**网络失败为 0**（重试生效），错误写入 0，误报完成 0。
  - H2（列表分区里只有一个按钮）两种做法都失败，而旧做法还产生了 45 次错误写入，原因在观察层。
  - 多标签和端到端两段只跑了开头。
- **`fm/bys-jev-fix-r1`（`4abe606`）**：上一轮在旧框架里打的 3 处循环补丁，已被上面的重构取代，只作参考。
- 用户已经做的决定：
  1. 要把重构做进产品，跑完完整 30 轮验收并达标后才合并。
  2. “直接交付”（Jev 判定完成、执行器确认送达、非高风险时不再让主模型复核）只有在 30 轮验收里误报完成为 0 后才能打开；删除、付款、发送、发布始终要确认。
- 验收门槛（原定）：无网络故障的运行里，新做法每个任务都不差于旧做法；S5、S6、H1–H8 合计 ≥ 90%；错误写入 0；误报完成 0；成功运行中 ≥ 90% 以循环自己的 `needs_verification` 结束；Jev 单次请求 p90 ≤ 1 s。第一次跑留出任务得到的结果即为验收结果。
- 继续的方法：检出 `fm/bys-jev-build-r1`，变基到 `main`，用 `scripts/acceptance/jev-compare/run.mts` 补跑剩下的轮次。可以 3–4 个进程并行跑（每轮用一个全新的隔离浏览器是为了隔离状态，开销约 1 s；主要耗时来自串行）。
