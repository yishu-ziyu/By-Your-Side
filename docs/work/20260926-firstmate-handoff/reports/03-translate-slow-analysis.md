# 为什么这次翻译要 8 分 43 秒

**直接回答：** 慢在一批一批地等模型。扩展把整篇文章切成若干批（每批最多 8 段），然后逐批串行发给 step-3.7-flash。这个模型每批都要先“思考”一大段，才开始输出译文。实测一批 8 段要 16–26 秒，其中 80–88% 的时间在输出思考内容，真正写译文只要 3 秒左右。109 段约 14–15 批，即使一次都不出错也要 5 分半左右：我在隔离 Chrome 里用同样 109 段的页面、同一模型、未改动的代码复现，结果是 334.6 秒。这次多出的约 3 分钟来自两次失败：第二批的思考“刹不住车”，两次都写满了 10000 token 的输出上限（`length`），第一次调用因此白白耗掉约 2 分钟、只交出 8 段；之后翻译撞上 240 秒的工具时限被强行停下，正在跑的那一批作废，又多花一轮模型决策。字体（宋体）、网络首包和扩展自身开销加起来不到 3 秒，与慢无关。早先记录的“17–20 秒”是在 3 句话的测试页上测的，只有 1 批，并不代表长文章也能这么快。

**trace 里看不到的部分（已说明的缺口）：** 导出的 trace 没有逐批记录。每批的 stopReason、耗时和 token 用量只由 `console.error('[page-translation]', …)` 输出（`agent/src/session.ts:2614`），在扩展模式下这些日志留在 offscreen 页面的控制台，不会进入导出文件。所以表中只能看到每次工具调用的起止时间，批次层面是推算的：

## 2. 起因、放大条件与可见症状

- **可见症状：** 侧栏 8 分 43 秒、4 步，其中两步是报错后重来。
- **结构性原因（占约 5.5 分钟）：** 批次严格串行（`page-translation.ts:70-114` 的 for 循环，每批 `await translate`），每批 ≤8 块、≤3000 字符、≤24 个片段（`extension/src/shared/page-translation.ts:255`）；而 step-3.7-flash 每批都要先思考 13–23 秒。109 段 × 串行 × 每批约 21 秒，约等于 5–6 分钟。
- **这次的触发因素（多出约 3 分钟）：**
  1. 第 2 批思考失控，两次请求都写满 10000 token（`length`），约 2 分钟作废，只保住第 1 批的 8 段。
  2. 240 秒的工具总时限（`agent/src/tools.ts:415`）截断了调用 #2，丢掉一批正在进行的请求，也多出一轮主模型决策。
- **放大条件：** 文章长度（109 段）。3 句话的测试页只有 1 批，所以看不出问题。
- **已排除的因素：**
  - 宋体：display 只用 0.18 s。
  - 网络首包：主模型 2.2–4.9 s；隔离复现中 19 次请求的首包为 0.7–4.5 s。
  - 扩展模式的收集和写页面开销：复现中模型请求共 332.4 s，整轮 334.6 s，扩展自身约 2 s。
  - 限流：并发实验里 8 路同时请求均为 200，没有 429。

**最早的分歧点：第一次翻译请求有没有带上思考。**

- 09-16 的失败复盘发现，同样的 `length` 是“可选思考耗尽输出预算”造成的（`20260916-page-translation-failure.md:27`）。修复方式是翻译请求不再传 `reasoning`，注释写着 “Omit reasoning: the adapter disables optional thinking”（`agent/src/session.ts:2605`，commit 59bdd1a，2026-09-16）。
- 这个前提只在 pi-ai 认为模型会思考（`model.reasoning: true`）时成立。这时适配层会主动发送 `thinking:{type:"disabled"}`，见 `node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:631-700`，各分支都以 `&& model.reasoning` 为条件。我打印过实际请求体：deepseek-v4-flash 和 glm-5.3-flash 都带着 `"thinking":{"type":"disabled"}`。
- 2026-09-24 扩展内置 agent 时（commit de381b0），StepFun 被注册为 OpenAI 兼容服务，写死了 `reasoning: false`（`extension/src/inproc/model-runtime.ts:111`）。于是翻译请求里不会带任何思考控制参数；而 step-3.7-flash 默认就会思考（官方文档写默认档位 medium，只有 low/medium/high 三档）。本次 trace 里主模型的每轮回复也都带着 `reasoning_content`，印证了这一点。
- 另一个 240 秒时限和每批 8 段的上限都来自 59bdd1a（09-16），之后没有改过。设计这两个上限时，每批只需几秒。

## 4. 反事实实验（均在隔离环境，不碰日常 Chrome，不输出密钥）

### 4a. 同一批请求直接调 API（`scratch/ab.mts`，与扩展完全相同的模型对象、提示词和 `maxTokens: 10000`）

step-3.7-flash，3 批原创英文测试文本，每批 8 段、2.6–2.8k 字符：

| 变体 | 每批用时 | 译文首 token 时刻 | 思考字符 | 输出 token |
|---|---|---|---|---|
| 产品原样（不带参数） | 25.7 / 25.0 / 16.0 s（均值 22.2） | 22.8 / 21.4 / 13.0 s | 6949 / 7638 / 4975 | 3320 / 3732 / 2348 |
| `reasoning_effort:"low"` | 14.6 / 18.1 / 12.8 s（均值 15.2，−32%） | 11.1 / 15.4 / 10.2 s | 4583 / 6005 / 2601 | 1925 / 2824 / 1944 |
| `reasoning_effort:"none"` | 27.0 / 19.6 / 28.3 s（无效果） | 23.9 / 16.5 / 25.7 s | 10670 / 5782 / 3835 | — |

- 结论：产品原样请求每批 81–89% 的时间花在思考上，而 StepFun 没有真正关闭思考的开关。
- 9 次里有 2 次 `segment_mismatch`（译文段落对不上）。在产品里这会让整批重新生成一次，是另一个耗时来源。
- 这 9 次都没有出现 `length`：失控是偶发的，我没能在小样本里复现。

### 4b. 真实用户路径复现 R1（未改动代码）

- 命令：`CASE_LIMIT_MS=900000 npx tsx scripts/acceptance/real-path/everyday-baseline.mts --headless --inproc=stepfun/step-3.7-flash --only=translate-long`。
- 在 fixture 里临时加了 `/long` 页面：1 个标题 + 96 段原创英文 + 12 个列表项 = 109 块，没有使用用户看过的文章内容。
- 结果：**334.6 s** 通过。第一次 translate 调用 **240.0 s 被时限截断**，完成 72/109（第 11 次请求 `net::ERR_ABORTED`）；主模型再调一次，82.0 s 补完。19 次请求的首包 0.7–4.5 s；每批中位数约 21 s。
- 这证明即使一次失败都没有，这个长度的页面在 step-3.7-flash 上也要 5.5 分钟，并且会撞上 240 秒时限。

### 4c. 最小反事实 R2：只把批次改成并发，其余不变

- 临时补丁（未提交，随工作区丢弃）：每次 collect 取 4 批，按原来的 8 段 / 3000 字符切开，用 `Promise.all` 并发翻译，再一次性写入页面。
- 结果：**164.1 s**，比 R1 少 51%。一次调用就完成 109/109，没有撞 240 秒时限；宋体 display 0.04 s。
- 每轮要等最慢的一批：有一批单独重跑了 59.3 s，是拖尾的请求或格式重试。

### 4d. 直接并发探测（`scratch/concurrency.mts`）

- 4 路并发：墙钟 26.2 s，其中 1 路 “Connection error.”。
- 8 路并发：墙钟 **34.8 s**，全部 200、全部解析通过。
- 同样的 8 批串行预计约 170 s。StepFun Step Plan 在 8 路并发下没有限流，每路延迟没有明显变长。

### 寻找反证：哪些结果推翻或削弱了我的解释

1. **“换回 deepseek、关掉思考就行”今天不成立。** opencode-go/deepseek-v4-flash 的请求体确实带着 `thinking:{type:"disabled"}`，但服务端仍输出了 5.3–5.9k 字符的思考，每批 16.4–26.6 s。09-16/17 那两次 82 s / 92 s 的成绩用的模型 id 是 `deepseek-flash`，今天目录里只有 `deepseek-v4-flash`，无法确认是模型变了还是服务端行为变了。
2. **“去掉思考就会快”对所有模型并不成立。** glm-5.3-flash 真的关掉了思考（0 字符），但每批仍要 14.4–20.7 s：它只输出约 540 token，速度约 30 token/秒。所以根因的准确表述是“串行批次数 × 每批延迟”，思考只是 step 上每批延迟的主要组成部分。今天能用的三个模型每批都在 15–25 秒，**并发是唯一与模型无关、并且已经实测有效的办法**。
3. **`length` 失控是推断，没有直接观察到。** 证据有三条：`length` 的定义、10000 token 的上限、09-16 在 deepseek 上观察到的“只有思考、没有译文、11024 token”。但本次导出没有逐批日志，我对 step 的 22 次直接请求（A/B 10 次、并发 12 次）和 R1、R2 两次真实路径里都没有出现 `length`，只能说它是偶发的。
4. 我的测试段落平均 336 字符，可能比真实文章的平均段落更长，每批更满，R1 可能偏慢。不过 R1（334.6 s）仍比用户的 527.7 s 快，差值与“两次 length + 一次截断”的推算吻合。

## 5. 怎样把时间降下来（只是建议，未改产品）

| 建议 | 依据 | 大致收益（109 段、step-3.7-flash） |
|---|---|---|
| 1. 批次并发，用固定宽度的请求池（如 4–8 路，不要按轮等最慢的一批），每批写好就立即落页 | R2 −51%（4 路、按轮等待）；8 路直测 34.8 s vs 串行约 170 s | 5.5 分钟 → 约 1.5–2.5 分钟；用请求池可以避免拖尾，收益更大（估计） |
| 2. 240 秒时限改成按进度判断，或者在工具内部自动续跑，而不是抛错交回主模型 | R1 和本次都在 240 s 处丢掉一批，还多一轮决策 | 每撞一次时限省约 25–40 s；做了第 1 条后基本不会再撞 |
| 3. 处理思考失控：遇到 `length` 时把这批拆小再试，或降低单批 `maxTokens`，让失控更早失败 | 本次两次 `length` 共约 95–120 s 作废 | 本次可省约 1–1.5 分钟；属于偶发情况 |
| 4. StepFun 翻译请求带上 `reasoning_effort:"low"` | 每批均值 22.2 → 15.2 s（−32%，n=3） | 串行时约 −1.5 分钟，并发后收益按比例缩小；译文质量需要人看 |
| 5. 把逐批记录写进导出的 trace（stopReason、耗时、token、失败原因） | 这次只能推算批次层面发生了什么 | 不省时间，但下次看导出文件就能定位原因 |
| 6. 用“首屏译完”作为体验指标 | collect 已经优先翻当前视口（`page-translation.ts:241`）；本次首批 8 段约 40 s 后才出现 | 让“即时”落在用户看得见的部分；需要在侧栏显示进度 |

- 换模型目前**不推荐作为主要手段**：今天实测的三个模型每批都在 15–25 秒。
- 这些发现意味着有值得交付的修复，首选第 1、2、5 条；原因清楚，并且已有 R1/R2 同一路径的前后对照可以作为验收基线。是否推进由 firstmate 决定。
