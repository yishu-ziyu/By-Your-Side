# 持续对话中的多要求调度

用户要求从三条边界检查：输入归属、执行容量、结果交付（[基线与证据](evals/20260916-voice-load-boundaries.md)）。
登记、准入和回传已接入，验收见[实施验收](evals/20260916-voice-multi-request.md)。恢复确认、全部任务控制与精确续播是后续项。运行状态以 [STATUS](STATUS.md) 为准。

> 本页的声音生成与确认流程早于 Realtime 3，不能直接套用。当前声音链路见[语音架构](voice-architecture.md)。

## 问题与不变量

用户的说话节奏，与任务、模型、页面和播报的完成节奏不同。
系统收到完整要求后，要保留它的身份与结局：不因下一次开口而取消它，也不让积压的任务无限启动。

1. 已接受的完整要求只有一个可查询的去向：执行、等待、澄清、完成、失败或中止。重放相同请求不重复执行。
2. 输入先分成补充、查询、独立要求和任务控制。只有明确的独立要求才新建执行单元；指代不清时，只澄清归属。
3. 执行带上来源页面、任务身份和控制版本。排队期间页面变了，就重新核验，不点旧定位。
4. 执行终态与交付终态分开。正文生成、等待播报、播放完成、被用户静音是不同事实。
5. 中止某个任务不清空其他任务；「全部停止」要有明确的作用范围。停声与中止的区别见[语音架构](voice-architecture.md#停声不等于中止任务)。

## 设计取舍

- 不另造模型执行内核，不删除现有的单运行会话保护。
- 可以复用独立会话作为内部执行容器。但用户不应为每个独立要求手动切会话，所有会话的结果也不应混进当前语音。
- 登记要在执行之前。等待回调不是任务队列；排队不等于已接受或已执行。
- 获得页面资源后，再核验原页面，不自动抢占。
- 一个要求完整登记以后，就不再跟着那一次开口的语音轮次一起结束。所以用户之后说的纠正，指向一个不变的任务身份。
- 语音服务只订阅当前会话里明确登记过的任务。每个结果到达时，语音服务按这个结果自己所属的任务检查它是否仍然有效。

## 最小落地顺序

1. **登记与回传一起落地。** 每个独立要求保存来源会话、请求身份、执行身份、原页面、状态和交付状态。
   登记成功才说「已收到」；存储失败就直接报未接收。不先自动创建无限会话。
2. **有界准入。** 活跃任务、等待要求、播报积压各有独立限制。限制数字是策略候选，不是测出的承载能力。
   文字入口与语音入口走同一准入，否则额度可被绕过。
3. **资源与任务控制。** 同页冲突保持等待并显示原因；独立的新页可占空闲名额。
   新要求先进先出，阻塞的任务不挡可运行的独立任务；任务控制不占普通等待名额。
   中止等待中的任务不碰执行器；中止运行中的任务，要等真实回执再释放名额。暂停保留页面占用，不算释放资源。
4. **结果调度。** 用户说话时，保留所有已登记的结果；空闲后逐条短报，必要时说出任务名。
   只有播放回执标记已播；静音只影响声音。播放队列放不下的结果留作未播交付，之后从账本再取，不因新结果到达而删旧结果。
5. **恢复。** 重启后，待执行要求不丢。结果未知的任务按[结果未知的边界](unknown-results.md)核验，不自动重跑外部动作。
   结束语音连接不中止已接收任务；重新开语音也不自动重播全部旧结果。
