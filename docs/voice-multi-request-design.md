# 持续对话中的多要求调度

依据：用户要求从输入归属、执行容量、结果交付三条边界检查；[基线与证据](evals/20260916-voice-load-boundaries.md)。登记、准入和回传已接入，验收见[实施验收](evals/20260916-voice-multi-request.md)。恢复确认、全部任务控制与精确续播是后续项。运行状态以 [STATUS](STATUS.md) 为准。

> 本页的声音生成与确认流程早于 Realtime 3，不能直接套用。当前声音链路见[语音架构](voice-architecture.md)。

## 问题与不变量

用户的表达节奏与任务、模型、网页和播报的完成节奏不同。收到完整要求后，系统应保留这个要求的身份与结局，不应因为下一次开口而取消它，也不应让积压的任务无限启动。

1. 已接受的完整要求有且只有一个可查询去向：执行、等待、澄清、完成、失败、取消。重放相同请求不重复执行。
2. 输入先区分补充、查询、独立要求和控制。明确独立要求才新建执行单元；指代不清时只澄清归属。
3. 执行应携带来源页面、任务身份和控制版本。排队期间页面变化后，应重新核验，不应点击旧定位。
4. 执行终态与交付终态分开。正文生成、等待播报、播放完成、被用户静音是不同事实。
5. 停声不取消任务；取消某个任务不清空其他任务；“全部停止”应有明确的作用范围。

## 复用与新增职责

| 位置 | 现有能力 | 应增加的能力 |
|---|---|---|
| 输入账本/语音分类 | 片段拼接、意图与当前性 | 完整要求登记后脱离声学 turn 寿命，纠正指向稳定任务身份 |
| manager | 会话及运行时、语音计划、跨会话回执 | 会话来源与独立执行单元的关系；接受/等待状态；任务目录供指代判定 |
| dispatcher | 请求去重、持久回执、普通输入顺序、控制优先 | 准入应在执行之前，不应把回调等待误当任务队列；queued 不等于 accepted/executed |
| 浏览器资源管理 | 页面归属、移交、版本检查 | 等待原因传回调度；获得资源后再核验原页面，不应自动抢占 |
| VoiceService | 当前会话订阅、交付去重 | 只订阅当前会话明确登记的执行任务；按结果自身的任务检查有效性，并回传播放回执 |
| VoicePlayback | 单路播放、排队、停声 | 队列超载有明确去向；待交付账本保留全文，播放队列只取下一项，不静默淘汰 |

不另造模型执行内核，不删除现有单运行会话保护。可以复用独立会话作为内部执行容器，但不应让用户为每次独立要求手动切会话；也不应把所有会话的结果混入当前语音。

## 最小落地顺序

1. **登记与回传一起落地。** 每个完整独立要求保存来源会话、requestId、目标执行身份、原页面引用、状态及交付状态。登记成功才说已收到；存储失败时，直接报告未接收。不应先自动创建无限会话。
2. **有界准入。** 活跃根任务、等待要求、播报积压各有独立限制。限制数字是策略候选，不是测出的承载能力。文字入口与语音入口应走同一准入，否则额度可被绕过。
3. **资源与控制。** 同页冲突保持等待并显示原因；独立新页可占空闲执行名额。新要求 FIFO，阻塞任务不阻挡可运行的独立任务；控制不占普通等待名额。取消等待任务不触碰执行器；取消运行任务等真实控制回执后释放名额。暂停保留页面占用，不应当作资源释放。
4. **结果调度。** 用户说话时保留所有已登记任务结果；空闲后逐条短报、必要时明确任务名称。只有 playback_done 标记已播；静音只影响声音。超出热播放队列的结果保留为未播交付，从账本再取，不因新结果到达删除旧结果。
5. **恢复。** 重启后待执行要求不丢；执行结果未知的任务沿现有 unknown 规则核验，不自动重跑外部动作。结束语音连接不取消已接收任务，重新开语音也不自动重播全部旧结果。
