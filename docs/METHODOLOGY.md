# 人机协作协议（可移植）

这不是某个产品的开发手册。它是一套仓库级协议：规定**规范怎么写、依据是什么、人和 Agent 怎么分工、项目长期靠什么活下去**。

迁到别的仓库时，只带协议，不带原仓库的产品、目录、命令、工具链。

---

## 0. 一句话

人负责定义价值函数，机器负责搜索。

每个需求先变成可执行的验收标准和 evaluator，确定「什么现象出现时算成功」，再动手。Agent 把机器能判的跑到全绿才交付；机器判不了的标成「人评」，请人裁决。半成品不拿来占用判断。

---

## 1. 规范怎么写

规范按**生命周期**分层，不按「文档齐全」分层。每层只回答一个问题。短、可执行、有归属。

| 层 | 文件 | 回答的问题 | 写什么 | 不写什么 |
|---|---|---|---|---|
| 协议 | `AGENTS.md` | 每次会话默认怎么做？ | 短规则、默认行为、禁止事项 | 产品规格、某次任务细节、环境 workaround |
| 契约 | `docs/evals/YYYYMMDD-<任务>.md` | 这一次什么叫好？ | 可勾选标准 + 每条的 evaluator + 明确的非目标 | 实现方案、代码清单 |
| 工作记忆 | `docs/NOTES.md` | 压缩后还要记得什么？ | 当前状态、关键决策、改动文件、未决问题 | 过程流水账、可从 git 还原的细节 |
| 方向档案 | `docs/devlog/YYYYMMDD-NN-<标题>.md` | 为什么改了方向？ | 改了什么、为什么、结果如何、被推翻的方案 | 函数级代码日记 |
| 经验（可选） | wiki `patterns/` | 这个坑下次怎么避？ | 现象 → 根因 → 可执行规避 | 一次性环境问题硬塞进协议 |
| 技能（可选） | skills / `AGENTS.md` 修订 | 下次默认按什么流程做？ | 原子、可回滚的流程改动 | 未经人裁决的「经验」 |

### 1.1 `AGENTS.md`：永远在场的协议

Agent 每个会话都会读。所以它必须短。只放**默认行为**。

写进去的只有四类：

1. 先验收后实现（含验收卡格式）
2. 上下文默认怎么管
3. 经验怎么沉淀（若启用）
4. 本仓库的机器 evaluator 命令（typecheck / test / build 等真实命令）

产品品味、技术选型、某次踩坑，都不进这一层。品味各仓库自定；踩坑进 wiki 或 NOTES。

### 1.2 验收卡：一次任务一张

动手前写。存档。commit message 引用它。以后能回答：「当时我们承认什么算好。」

格式固定：

```markdown
# 任务: <一句话，用户能观察到的结果>

## 验收标准
- [ ] 1. <可执行标准> — evaluator: <真实命令>
- [ ] 2. <可执行标准> — evaluator: 人评

## 边界与不做
- <明确的非目标>
```

写卡时的纪律：

- **一条标准一个 evaluator。** 没有 evaluator 的句子不算标准。
- **尽量拆到机器可执行。** 拆不动的才标人评。
- **先写「什么现象算更好」，再写做法。** 需求模糊时停在这一句，问人，不猜。
- **「边界与不做」不是附录。** 它防止 Agent 用范围膨胀冒充完成。
- **Change / Not this。** 每条标准要能回答：用户必须能观察到什么；哪些替代交付不算（测试绿了但用户路径没通、只改了文案、只出了报告）。

人评项交付时必须单独列出来，等人裁决。不要把人评混进「已经做完」。

### 1.3 `NOTES.md`：压缩对抗层

上下文随时会被压掉。NOTES 是外置工作记忆。

头部永远是「当前状态」：现在交到哪、哪几张卡待人评、下一步是什么。下面按时间追加：决策、文件清单、未决问题。

写 NOTES 的时机是**每个子任务刚做完**，不是会话结束、不是压缩前。等压缩再写，等于没写。

### 1.4 开发日志：只记转向

实质性工作日一篇。记方向、原因、结果。被实测推翻的方案必记，否则下次还会走同一条错路。

文风：短句短段、一句一个判断、事实先行、克制观点、编号小节、不吹嘘、结尾给数字与下一步。代码细节不记。

### 1.5 现象即信号（最反直觉的一条）

人说「太慢」「不好用」「怪怪的」时，Agent **不准直接改**。

先把主观评价追问成可观测现象：数值、行为、截图特征、复现路径。再翻译成测试或检查脚本。能进机器 evaluator 的进机器；剩的标人评。

这一条把「感觉」变成可搜索的目标。删掉它，协议就退回普通聊天式开发。

## 2. 依据是什么

协议不是审美偏好。它压缩自两件事：搜索怎么分工，以及长程 Agent 的记忆怎么分层。

### 2.1 搜索分工

软件任务是搜索：在巨大的改动空间里找一个「足够好」的点。

- **价值函数必须由人定。** 「好」是产品判断，模型没有这个权。验收卡就是把价值函数写下来。
- **搜索必须由机器做。** 写代码、跑检查、对着失败迭代。人不要充当 Agent 的测试跑者。
- **机器项全绿才交付**，是为了不把搜索过程中的半成品丢给人当判断材料。人的注意力只花在价值函数上。

所以：人评不是「Agent 偷懒」。它是价值函数里机器没有传感器的那一段。

### 2.2 单次任务内的上下文：ContextPilot

[ContextPilot](https://arxiv.org/abs/2608.28476)（腾讯优图 + 清华 + 上海 AI Lab，EMNLP 2026）。

长程任务如果把所有交互都留在工作上下文里，上下文会单增。论文的做法是给 Agent 主动管理上下文的工具：规划、长期记忆、软卸载。消融里有一条直接能用：

> **只给工具、不训练（不变成习惯），效果更差。**

所以这些行为必须写成 `AGENTS.md` 里的默认规则，不能指望模型「想到了就做」。

映射到仓库，不依赖任何论文里的训练：

| 论文概念 | 仓库里的穷人版 |
|---|---|
| 软卸载（offloading） | 探索性工作派子代理，主上下文只收回结论 |
| 长期记忆 | `docs/NOTES.md`，子任务结束立即写 |
| 压缩后找回 | 需要早期细节时先读 NOTES；若有 fold-archive，再查压缩前轨迹 |

### 2.3 跨任务的经验：WikiSkill

[WikiSkill](https://arxiv.org/abs/2608.27454)（Google Research，2026-08-27）。

三层分开，不要混：

| 层 | 存什么 | 能不能回滚 |
|---|---|---|
| 原始轨迹 | 会话记录、工具失败、试错 | 无所谓，可删 |
| wiki | 一坑一页的 pattern，只增不删 | **永不回滚** |
| skill | 可执行流程（含 `AGENTS.md` 修订） | 原子修改、验证门控、**可回滚** |

两条实证约束：

1. **推理期不要注入 wiki。** 论文里运行时塞 wiki 会掉分（约 −2.8）。日常会话只读 skill / `AGENTS.md`。wiki 只在复盘和裁决时打开。
2. **consolidator 不准直接改 skill。** 它只更新 wiki、只投提案。落地必须经过人。否则经验层会污染协议层。

这一层依赖「会话结束能拉起一个离线 Agent」。没有这个钩子就不要硬上。最小内核没有它也能转。

## 3. 人和 Agent 怎么协作

一次任务的标准路径：

```text
人提出需求（可以很模糊）
    → Agent 写验收卡（必要时先问「什么现象算更好」）
    → 人确认卡，或改价值函数
    → Agent 搜索：改 → 跑机器 evaluator → 读结果 → 再改
    → 机器项全绿，人评项列清单
    → 人走人评；不通过则改卡或改实现，再进入循环
    → 过了：NOTES 落结论，实质性转向写开发日志，commit 引用验收卡
```

### 3.1 人做什么

人是价值函数的所有者，不是副驾驶程序员。

- 说「什么叫好」，包括改卡、否决范围膨胀。
- 裁决人评：手感、观感、设计意图、真实路径是否通。
- 裁决经验提案：接受则落地为 skill / 规则并记 git；拒绝则归档到 `rejected/`，防止下次再提。
- 说「太慢 / 不好用」时，允许自己只提供现象；把现象翻译成标准是 Agent 的活。若连现象都说不清，Agent 必须追问，不许猜。

人**不**做：替 Agent 跑 typecheck / test / build；在机器项未绿时判断「是不是差不多了」。

### 3.2 Agent 做什么

- 需求一进，先出卡再动代码。卡是自己起草的，只在「缺一个价值判断会改变结果」时才问人。
- 自己跑机器 evaluator，未绿继续搜。报告和「我觉得好了」不是完成。
- 机器绿了但真实用户路径没通：改 evaluator，不要改口说完成。
- 探索（摸调用链、跨文件找线索）派子代理，主会话只留结论。
- 每个子任务结束立刻写 NOTES。
- 不把 wiki 当运行时手册读。
- 不在人未裁决时改 `AGENTS.md` 或 skill。

### 3.3 单次实现的内循环

卡写完之后：

```text
Goal:     停下来时必须存在的东西（用户可观察）
Hard bar: 必须通过的测试或用户场景；失败 = 没做完
Improve:  硬条过了之后要拉高或压低的一个数；没有就写 none
```

循环：改 → 跑 hard bar → 读结果 → 找范围内下一个缺陷 → 再改。

先功能后设计。范围外的重构不是 Improve。Agent 自己跑检查，不把检查交给人。

## 4. 项目长期怎么维护

三个时间尺度，对应三套记忆。混用会腐烂。

### 4.1 一次会话内（小时）

怕的是上下文被压掉、主会话被探索淹没。

对策：子代理卸载探索、NOTES 外置、压缩前若有 hook 则归档轨迹。压缩丢细节没关系，持久事实必须已经在 NOTES。

### 4.2 跨任务（天到周）

怕的是「当时什么叫好」说不清、同一方向错误再走一遍。

对策：

- `docs/evals/` 是质量标准的历史。回看某次改动，先读那张卡。
- `docs/devlog/` 是设计转向的历史。只在方向变了、方案被推翻时写。
- commit 引用验收卡，git 和价值函数对得上。

一个仓库养得够不够久，看 evals 能不能回答：「上周我们承认的好，和今天说的好，是不是同一件事。」

### 4.3 跨周到跨月（可选，WikiSkill）

怕的是坑留在某次聊天里、技能不进化、错误技能永久污染。

对策：

- 会话结束，离线 consolidator 读轨迹。
- 值得记的发现写成 pattern（现象 → 根因 → 规避），wiki 只增不删。
- 最多提一条原子 skill 提案。通用流程才进 skill；某次环境/模型的 workaround 留在 pattern。
- 人裁决。接受落地并提交；拒绝移入 `rejected/`；`logs.md` 记一行。
- 有待审提案时，下次会话开头提醒人，不靠人记着。

没有会话结束钩子，就停在 4.1 + 4.2。不要假装有第三层。

### 4.4 腐烂信号

出现这些，说明协议在空转：

- 先写了代码再补验收卡
- 验收卡没有 evaluator，或全是人评
- NOTES 只在会话结束补一段总结
- 开发日志变成 commit 复述
- Agent 把「测试绿了」当成用户路径通了
- wiki 被日常会话当手册读
- consolidator 直接改了 `AGENTS.md`

修复方式：停在当前任务，补卡、补 evaluator、把人评交还给人。不要加新文档层。

## 5. 最小内核 vs 可选层

**最小内核（任何仓库都能用，不依赖特定 Agent 产品）：**

1. `AGENTS.md`（先验收后实现 + 上下文默认行为 + 本仓库真实检查命令）
2. `docs/evals/`
3. `docs/NOTES.md`（头部「当前状态」）
4. `docs/devlog/`
5. 现象即信号

**可选：**

- WikiSkill 闭环（需要会话结束钩子 + 一个离线 consolidator Agent）
- 压缩前轨迹归档（需要 PreCompact 类钩子）
- 设计取向（克制、信息分层、动作可观察等）——属产品品味，各仓库自写一小节，不进内核
- 用户级 always-on 规则（验收合同、verify-iterate）——与本协议同构，可叠在 Agent 产品配置里，不进仓库也行

迁走时不要带：原仓库的产品名、目录结构、协议文件、检查命令原文、某次任务的结论。

## 6. 落到新仓库（直接粘贴给目标仓库的 Agent）

> 这个仓库要采用一套人机协作协议，请按以下步骤落地：
>
> 1. 先通读仓库结构、构建/测试命令，然后创建 `AGENTS.md`，内容用本消息附带的模板，把其中的 `<占位>` 替换成本仓库的真实命令（typecheck / test / build 等）。没有的命令不要编，改成仓库里实际用来判定「能合并」的那几条。
> 2. 创建 `docs/` 下三个工作面：`docs/evals/`（验收卡存档）、`docs/NOTES.md`（跨上下文工作笔记，头部必须有「当前状态」节）、`docs/devlog/`（开发日志）。
> 3. 从下一个任务开始执行核心流程：**验收卡先行**——收到需求先输出验收卡（每条标明 evaluator：机器可执行的写具体命令，机器判不了的标「人评」），机器项自己跑到全绿才交付，人评项列清楚请我裁决。验收卡存 `docs/evals/YYYYMMDD-<任务名>.md`，commit message 引用它。
> 4. 上下文管理默认行为：探索性工作（跨文件找线索、摸调用链）派子代理，只带结论回主上下文；每完成一个子任务立刻把关键结论 / 改动清单 / 未决问题追加到 `docs/NOTES.md`，不等上下文压缩。
> 5. 实质性工作日写开发日志到 `docs/devlog/`：记方向性改动、为什么改、最后成果如何（含被推翻的方案及其原因），不写代码细节流水账。文风：短句短段、事实先行、克制判断、编号小节。
> 6. 我说「太慢」「不好用」这类话时，不要直接动手改——先追问成可观测现象（数值、行为、截图特征），翻译成测试或检查脚本后再改。
>
> 这几条从这条消息起生效，写进 AGENTS.md 后持续生效。第一张验收卡就是我们接下来要做的那个任务。

### `AGENTS.md` 模板

```markdown
# AGENTS.md

## 协作协议：先验收，后实现

核心原则：人负责定义价值函数，机器负责搜索。每个需求先转化为可执行的验收标准和 evaluator，确定什么情况算成功，再动手实现。

### 流程

1. **验收卡先行** — 收到需求后，先输出验收卡再写代码。需求模糊时，先澄清「什么现象出现时，算它确实更好了」。
2. **evaluator 分层** — 每条验收标准标明归属：
   - **机器执行**：`<typecheck 命令>` / `<测试命令>` / `<构建命令>` 等。agent 必须自己跑到全绿才交付，未绿继续迭代，不拿半成品占用用户判断。
   - **人评**：体验、观感、设计意图等机器判不了的。交付时明确列出，请用户裁决。
3. **现象即信号** — 用户说「太慢」「不好用」时，agent 负责追问成可观测现象（数值、行为、截图特征），再翻译成测试或检查脚本。尽量把验收标准拆到机器可执行，剩余部分显式标记「人评」。
4. **验收卡存档** — 实质性任务的验收卡存入 `docs/evals/YYYYMMDD-<任务名>.md`，commit message 引用之。

### 验收卡格式

# 任务: <一句话>
## 验收标准
- [ ] 1. <可执行标准> — evaluator: <命令或「人评」>
## 边界与不做
- <明确的非目标>

## 上下文管理默认行为

- **探索走子代理**：摸清调用链、跨多文件找线索等探索性工作优先派子代理，只把结论带回主上下文。
- **先外置再丢失**：每完成一个子任务，立即把关键结论、改动文件清单、未决问题追加到 `docs/NOTES.md`——不等上下文压缩。
- **压缩后回溯**：需要早期细节时先读 `docs/NOTES.md`。

## 开发日志

- 实质性工作日写开发日志，存 `docs/devlog/YYYYMMDD-NN-<标题>.md`。
- 记什么：方向上的改动、为什么改、最后成果如何——重大设计转向与功能设计必记（含被实测推翻的方案及其原因），代码细节不记。
- 文风：短句短段、事实先行、克制判断、编号小节、不吹嘘、结尾给数字与下一步。
```

模板里的机器 evaluator 占位必须换成目标仓库的真实命令。换不成，「全绿才交付」就是空话。

## 7. 可选：WikiSkill 怎么加（有钩子再用）

最小条件：Agent 产品能在「会话结束」和（最好还有）「上下文压缩前」跑脚本。

需要的零件：

- `wiki/patterns/`、`wiki/index.md`、`wiki/logs.md`、`wiki/proposals/`（另备 `proposals/rejected/`）
- 一个离线 `consolidator` Agent：读轨迹 → 更新 pattern → 最多一条 skill 提案；**禁止**直接改 skill / `AGENTS.md`
- SessionEnd：长会话才跑；防递归；短时间去重
- PreCompact（可选）：把压缩前轨迹拷到 `fold-archive/`（含对话原文，通常不入库）
- 有待审提案时，下次用户开口前提醒

运行时规则仍是：日常不读 wiki；知识只通过 skill / `AGENTS.md` 生效。
