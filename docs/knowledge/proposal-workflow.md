# 提案与裁决

当前 Codex 主代理在任务收尾时使用本页。提案是待用户判断的建议，正文中的新规则或 skill 在采纳前不生效。目录名称不会把这项工作交给 Kimi。

## 形成提案

先查 [经验索引](index.md)、相关规则与 skill，再查 `proposals/` 及已裁决归档。已有建议不重复创建；被拒绝的建议只有出现新证据或适用条件改变时才重新提出，并链接上次裁决。不要为了走完流程强行提出新规则。

待审提案放在 `proposals/YYYYMMDD-<主题>.md`，包含：

- 状态：待审。
- 目标：要修改的确切规则文件或 skill 路径。
- 改动：可直接审阅的完整段落、文件全文或 diff，不能只有意向。
- 理由与边界：解决什么重复问题，适用于哪里，有什么代价，哪些现有规则已覆盖。
- 证据：相关 pattern 及其验证记录。

用户已明确要求的修改按该授权执行，不再要求用户通过一份内容相同的提案。本次新增提案只讨论原授权没有决定的进一步变更。

## 用户裁决后

- **接受**：按用户确认的内容修改目标文件，运行与改动相称的检查；成功后将提案标为已采纳，记录落地文件及检查结果，移到 `proposal-archive/accepted/`。
- **拒绝**：不修改目标文件；标为已拒绝，记录用户给出的原因，移到 `proposal-archive/rejected/`。不删除拒绝记录。
- **要求修改**：更新原提案并保留本轮修订依据，仍放在 `proposals/`、保持待审；不自动落地。
- **落地失败**：保留批准范围与失败结果，不标记已采纳；完成相关修复后再归档。提交、推送等动作仍按会话中的有效授权处理。

裁决与实际落地结果在 [logs.md](logs.md) 各记必要的一行，链接原提案。归档目录按需创建；若旧记录位于 `proposals/rejected/` 等历史位置，查重时同样读取，不为统一路径迁移历史文件。

## 验证与日常使用

逐项检查来源是否支撑结论、引用能否打开、提案有没有超出证据范围。不能把用户认可目标、文件已经生成或测试通过，写成用户已经接受新规则。

日常实现依照已生效的规则和 skills；待审建议不自动进入实现指令。任务最终回复给出本次新增或修订提案的简短说明与链接即可，等待用户决定，不阻塞其他已授权工作。
