# Pattern: 可见的 GUI 测试窗口会抢用户前台，浏览器验收要走无头

## 现象

2026-09-11 凌晨，同一套验收脚本跑了十来次，每次都新起一个 `Chrome for Testing` **可见窗口**
（当时还特意用 `--window-position=-3000,-3000` 藏到屏幕外，以为这样就不打扰）。用户的实际感受：

> 现在还是不断跳出这个浏览器窗口……它就立刻跳出来，把我所有窗口都缩小、隐藏，专门把它那个窗口弹出来，
> 占据我的前台。占据两三秒后它就消失了，留下我一地鸡毛。

`--window-position` 只挪位置，**不阻止 macOS 把新窗口激活到前台**；每次启动＝一次抢焦点，一次就是两三秒。

## 根因

- macOS 上启动 GUI 应用会激活它；Chrome 启动即建窗口，用户注意力被搬走一次。
- 「藏到屏幕外」「开小窗」「跑完杀掉」都只是缓解，不改变「有一瞬间它占据前台」这个事实。
- 验收脚本被反复执行（本轮十几次），单次 2–3 秒的打扰累加成明确的不满。

## 方法

- **验收默认无头**：`--headless=new`，不创建窗口；扩展、MV3 service worker、CDP `Input` 可信事件、
  `Page.captureScreenshot` 在无头下都可用（本轮 16/16 通过，与有窗口时同结论）。
- **脚本自带硬拒绝**：启动参数里没有 `headless` 就直接报错退出，防止以后手滑改回去。
- **需要可见窗口时先问用户**：涉及“看得见的运动”这类检查（光标飞行、动效帧推进）无头不成立
  （后台标签页 RAF 不推进），这种检查要单独安排并征得同意，不能顺手起一个窗口。
- **不要另起可见实例代替既有通道**：本仓库的验收通道本来就连用户日常 Chrome（`local.yishu.chrome-main`），
  抢前台的临时实例不是安全默认。

## 适用条件

在本机跑任何浏览器自动化、截图、验收时都适用，尤其是被反复调用的脚本。不是本机、无 GUI（CI）时无此问题。

## 验证

- 改无头后同脚本连续三次 **16/16**；`pgrep -fl "Chrome for Testing"` 无输出，临时 profile 清理干净。
- 有窗口时同样的检查也通过，说明差异只在「有没有窗口」，不影响验收结论（本条不依赖可见帧推进）。
