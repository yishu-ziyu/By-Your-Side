# 路线与决定

本页保留产品方向及其修订依据；实际状态与当前任务只看 [STATUS](STATUS.md)。历史阶段不作为自动开工授权。

## 最近的方向决定

1. 自然交流、可靠执行、越用越熟练是产品目标。09-20 的讨论强调先解决反馈不足，再看慢和理解错误；不应让票组和局部指标遮住用户结果。
2. 日常语音使用 Realtime 3；网页操作复用现有任务、页面控制、授权与结果账本。Jev 作结构化判断（Jev 已退役，见第 9 条），主模型负责开放式内容和核验；分工应由实际任务验证。[方案与标准](evals/20260920-general-browser-contract.md)
3. 用户后来要求先开放日常试用，由自己尝试陌生任务。这项要求修订了「完整评测通过后才开放试用」的先后顺序，没有降低正式质量与速度标准。[试用修订](evals/20260920-general-browser-trial.md)
4. 用户最新要求先整顿文档系统，避免过时材料误导开发；当前体验失败仍应沿真实路径解决，不因文档整理结项而消失。[当前状态](STATUS.md)
5. 09-23：产品要分发给他人，长期支持 macOS、Linux、Windows，先专攻 macOS。验收：在没有 Node、Pi CLI 和开发者代理的干净电脑上，用户能安装产品，在界面里配置模型，并完成第一次真实任务。用户曾选「扩展＋配套应用、运行时随产品打包」。随后用户对照 Sitegeist（只装扩展，开发者模式加载）提出质疑：安装、代码量和模型配置都偏重。当时形态和模型配置方式在重新评估；未裁决前不迁移 Node/Pi 核心。
6. 09-24 裁决：产品形态只做扩展，把任务核心搬进扩展（先花一天试搬，并用双入口行为契约验收）。界面分工为「侧栏是家，页面是现场」：结果先在原文旁以小卡指向，完整任务卡、中止与确认留在侧栏。侧栏关闭时，只在助手当前操作的标签页显示胶囊，其他标签页不显示。密钥、记忆和其他标签页的内容不进入页面层；语音只在扩展里采集。侧栏以任务卡为主还是以对话为主暂不决定；第一版做好后，在真实使用中再定。
7. 09-25 裁决（用户梳理项目后确认）：目标用户是陌生人，自己安装扩展、自己配置模型。**即时交互排第一位**：用户说一句，回应当场出现在用户当前看的页面上。用户一眼就能感知（圈画、原地翻译与换字体、划词追问）。替用户操作网页排在其后，可先慢一些。语音是核心入口，不是可选附加。参照对象是可交互视频 ACTx486：回答接回内容本身，而不是放在旁边。由此：
   - **主路径**：安装 → 配置模型（文字与语音）→ 开口或选中 → 页面当场变化 → 看清做成没有 → 中途插话、改口、中止。排期看是否改善这条路径。
   - **先做错误分析，再定测什么**（依据 [Hamel Husain、Shreya Shankar 的 evals FAQ](https://hamel.dev/blog/posts/evals-faq/)）。用户当判定人，逐条看约 30 条真实记录（本机会话与浏览器导出的诊断记录）。每条写一句哪里不对：只写第一处，不是模型的错也写。然后归类计数，得出按频次排序的错误清单，决定下一步修什么。计分板由真实流程和已确认的错误组成，只判通过或不通过，报告全部通过率。陌生人场景先按维度手工组合补充，之后换成真实试用记录。「多快算即时」看完真实记录后再定。
   - **语音服务**：语音稳定性是发布阻断项。继续用 StepFun 还是更换，由同一批用例的对比实验决定，不再只修症状。
   - **暂停开发**（保持现状、不删除）：显式记忆（09-27 按第 8 条恢复两层）、技能复用、EverOS、多会话协作；第 1 条的「越用越熟练」随之后移。
   - 原因：功能方向十余个，近期可靠证据只集中在读页问答、简单操作和圈画；精力多花在补 StepFun 服务端问题；测什么一直由开发者设想，没有来自真实记录的错误清单；最看重的即时交互实际要 8–51 秒（翻译约 20 秒、圈画 13–51 秒）。[开发日志](devlog/20260925-01-即时交互排第一先做错误分析.md)

8. 09-27 裁决（用户日常试用截图：订阅表单问邮箱、说「没有跨对话的记忆」、让用户自己去 Gmail 点确认）。记忆、主动性、任务感一起做。恢复第 7 条暂停的记忆，但只做两层：用户亲口说的个人资料（自动记、给撤销，网页内容一律不记）和过往任务摘要。技能复用、网站做法、EverOS 仍暂停。助手为目标直接去别的已登录网站操作；登录、验证码、付款、发送、删除仍停下等用户。任务不随一轮结束；没做完时，用户随口补一句算同一任务。同一条路径应在用户用的每家模型上都有像样的效果。依据：ChatGPT 记忆从「点名才记」改为持续整理；浏览器记忆可被网页投毒；Claude in Chrome 的「自动」权限模式。[验收](evals/20260927-memory-proactive-task.md)

9. 10-01 裁决（代码盘点后）：本机助手模式正式退役，产品只剩扩展；只在本机模式可用的 Jev 随之退役。分两步：第一步撤下使用说明；第二步把依赖本机程序的浏览器检查逐套切到只装扩展，切完后删除本机入口与 Jev 代码。多会话协作检查只能靠本机程序，所以随之删除。技能复用与 EverOS 同样只在本机模式运行，去留见第 10 条。[验收](evals/20261001-retire-native-and-dead-code.md)

10. 10-01 裁决：记忆与「越用越好用」是用户最想要的方向。这个方向是产品能自我进化、留住用户的核心，不再作为暂停项。本条与第 7 条合并执行。错误分析照做；逐条看真实记录时，专门标出「它要是记得就不会错」的地方，先做其中最痛的一处。候选第一步：把「用户纠正 → 助手提出规则 → 用户确认 → 以后照做」做进扩展。技能复用（看演示学会做法、下次照做）的代码保留在主线；按记忆当初的做法补浏览器存储后，接进扩展。EverOS 需另装 Python 服务，与只装扩展冲突，所以移出主线；「从经历里学习」改在扩展自己的记忆上做。

11. 10-02 裁决（能力边界）：**能做的范围不设限，承诺的可靠程度分三档。** 工具覆盖浏览器全部操作，只决定「能碰到什么」。每步都可能出错，多步时各步的成功率相乘；所以可靠程度由步数与结果能否当场核对决定（9 月底 full-1：读页 72–89%，多页调研 46–54%）。
   - **第一档 必须稳**（目标约 95%，当场出结果）：只读或一步、结果在当前页一眼可核对。读懂页面、划词提问、圈画指给你看、单步操作。正例：「这段逻辑站得住吗」「打开 Travel 分类」；反例：「把这页每段都翻译」不属于此档（段落多、逐段难核对）。
   - **第二档 应该做好**（目标约 80%，做完交给用户核对）：多步但都在可见页面上、结果有明确对错。多步操作、提取成表格、填表不提交。正例：「找最便宜的书告诉我价格」「整理成 CSV」；反例：需要跨多个网站汇总判断的调研不属于此档。
   - **第三档 陪着做**（不以一次做完为目标）：步数多、结果难当场核对或撤不回。多页调研、整页翻译、提交/付款/发送/删除。应分段交付、关键处停下给用户看；不承诺无人值守一次完成。
   - 判档看任务本身而不是类别名：同是「操作」，一步点开属第一档，十步填完并提交属第三档。分档用于评测报表（按档报通过率与目标差距，不只报总分）与排期（先补第一档缺口）。一般模型在各档达标，才算产品本身合格。评测题的类别与档位对应见 `eval/tasks/tiers.json`。

## 保留的产品主线

长期方向仍是这四项：可靠执行与恢复、运行中纠正与接管、记忆与技能复用、可核对的成果交付。其中记忆与技能复用按第 10 条恢复为优先方向，EverOS 移出。这四项不是严格串行的未开工阶段：部分已有实现，部分缺验证。不应继续把 09-17 的「P0 唯一核心开发」写成今天的全部安排。

首次使用、主动提醒、持续观察等未完成方向不由本页自动启动。旧提案、候选参数、被推翻方案见[整理前路线图](history/20260920-roadmap-snapshot.md)，具体历史证据仍保留原链接。
