# 一直听：实时语音验收方案（BDD）

## 0. 目标与边界

**一句话**：用户开着「一直听」，它看着用户的页面陪着聊，能随手标出来；也能派它做长任务，过程中随时问进度，做完接着聊。

- 本方案只规定用户看到、听到的结果，以及这些结果出现的时间。用哪家语音服务、怎么实现，由工程决定。任何实现只要全部用例通过，就算完成。
- 费用不在本方案考虑范围内。
- 阈值和判定规则只能由产品负责人修改。实现方不得为了通过而改阈值、改用例或改判定口径。
- 开口时间（M3、M6 应声、M8c）由产品负责人定为 2.0 s：MOSS-Live 服务端自身从用户说完到第一声约 1.7 s，1.0 s 在该服务上不可达；2.0 s 仍能拦住宿主额外引入的等待。

## 1. 测量口径（所有用例共用）

### 1.1 环境

| 层级 | 环境 | 证明什么 |
|---|---|---|
| L1 自动门禁 | 隔离 Chrome，装真实扩展；麦克风用 `--use-file-for-fake-audio-capture` 喂预先录好的 WAV；语音服务用真实服务；网页任务模型可以用脚本模型；网页用本机夹具页 | 程序层面达标。每条用例都要跑 |
| L2 真模型 | 同 L1，但网页任务换成默认测试模型，网站换成真实网站 | 真实能力。场景二、三各跑 1 次 |
| L3 真人 | 用户在日常 Chrome 里外放试用 | 最终确认，由用户判断 |

只有 L1 全部通过、L2 全部通过、L3 用户确认，三层都满足才算完成。汇报时必须写明每条结果来自哪一层。

### 1.2 时间点（全部取侧栏同一个时钟，不用服务端时间）

| 记号 | 定义 |
|---|---|
| `t_speech_start` | 侧栏采到的麦克风音频里，这句话第一帧 RMS 超过 0.01 的时刻 |
| `t_end` | 这句话最后一帧 RMS 超过 0.01、且之后持续 300 ms 低于阈值的那一帧的时刻 |
| `t_sound` | 回答的第一段音频在侧栏播放器里真正开始播放的时刻（`AudioBufferSourceNode.start` 的播放时间换算成墙上时间） |
| `t_stop` | 播放器停止输出的时刻 |
| `t_text(x)` | 文本 x 第一次出现在侧栏 DOM 里的时刻（MutationObserver 记录） |
| `t_mark` | 圈画层第一次出现在页面 DOM 里的时刻 |
| `t_task` | 侧栏出现这件任务卡片的时刻 |
| `t_verified` | 任务核对完成、侧栏过程行变成「已核对页面」的时刻 |

这些时间点都由侧栏和页面自己记，和语音服务无关，换哪家服务口径都一样。每次运行把它们写进 `result.json`。

### 1.3 重复次数与通过规则

- 每条 L1 用例连续跑 **5 次**。
- **正确性**（答对、圈对、没误点、没新开任务等）：5 次全部通过。
- **时间**：5 次的中位数 ≤ 阈值，且每一次都 ≤ 阈值的 2 倍。
- 超时、没有产出可判定的结果、中途崩溃，都算这次**失败**，不能算「无法判断」后跳过。
- 同一条用例因为同一个原因失败 2 次，就停下来分析，不要盲目重跑。
- **夹具操作容差**：夹具按计划在某个时刻做的操作（断网、开口、页面变化、插话）允许有偏差，但只能偏向让产品更难通过的一侧，且不超过计划值的 10%，最多 500 ms。超出就是夹具失败：这一次作废重跑，不计入 5 次；同一原因出现 2 次，先修夹具再继续。所有实际时刻都用 `Date.now` 记录，写进 `result.json`。音频本身有多长（某句话、某次附和）按采到的 PCM 样本数除以采样率计算，同时也记下 `Date.now` 的差值；判断时长是否在容差内，以样本数算出的时长为准。产品判定和阈值不变。

### 1.4 个别指标的判定细则

- **M5**：变化前的旧内容至少要显示 3 秒；从页面变化到用户开口（第一帧 RMS > 0.01）的实际间隔，在 1000–1100 ms 之间才算有效。
- **M8a**：断网期间，侧栏可见文字里要出现「重新连接」「重连」「正在恢复」中的至少一个，不能只有「连不上」「已断开」这类失败说法；恢复后这条提示自动消失；整个过程用户不用点任何东西。实际断网时长在 5000–5500 ms 之间才算有效。10 秒从实际恢复网络的时刻算起，到提示消失、语音会话重新就绪为止；恢复后那句追问另外判，要满足 M3 并答对。
- **M2b**：提问要限定回答长度，让正常回答在 30 秒内说完；夹具最多等 90 秒。一段回答过了 90 秒还没结束，算产品失败，先查清原因，不能靠延长等待来通过。
- **M8c**：属于 1.3 节「5 次」规则的例外，只跑 1 次。挂了 2 小时之后，用户说的第一句话必须做到 `t_sound − t_end` ≤ 2.0 s，没有 2 倍的放宽，回答也要正确。这一句测的正是用户最常遇到的「放了很久再开口」，所以只看它这一次。同时在 `result.json` 里记下：这期间连接一直没断，还是开口时才重新建立的。M3 自己仍按 5 次的规则单独判定。
- **服务分工（用户指定）**：凡是用户问、它答的对话，都由 MOSS-Live 自己回答并出声，包括 1.x、2.2「做到哪一步了」、2.4「第二家是做什么的」、3.1 的提示句和 3.2。MiniMax 只用来朗读任务完成后的结果，即 2.4 主动说的结果摘要和 3.1 用户说「说吧」之后念的结果。宿主可以把真实的任务事实通过 `session.update` 等方式交给 MOSS，但如果由宿主文字模型组织好答案、再交给 MiniMax 念出来，充当对话回答，这类用例不算通过。
- **回答必须由模型现场生成**：L1 只允许「网页任务执行时的浏览动作」用脚本，包括调哪些工具、读到什么、产出什么结果。语音意图判断（这句话该聊天、该开任务、问进度，还是要并进已有任务）必须用真实模型，用产品日常配置的那个，因为 1.2、2.1、2.3、3.2 测的正是这一步，M6 的时间里也包含它；语音回答必须由真实模型根据当时的真实任务状态现场生成，预先写好的答案不算数。
- **L3**：只有用户本人在日常 Chrome 里试用才算 L3，代理操作的结果和无头浏览器的录音都不算。L1、L2 通过后可以合并并更新日常扩展，但汇报只能写「L3 待用户试用」，并附一份不超过 6 步的试用清单，每一步写清「说什么、应该看到或听到什么」。

## 2. 全程时刻指标

| 编号 | 时刻 | 判定 | 阈值 |
|---|---|---|---|
| M1 | 开口 | 一句时长 ≥ 3 秒的话：说完之前，侧栏已经出现转写的前几个字；说完后，完整转写出现得够快 | `t_text(完整转写) − t_end` ≤ 0.5 s |
| M2a | 停顿不抢话 | 一句话中间停 1.2 秒：侧栏只出现 1 条用户消息、1 段回答 | 5/5 |
| M2b | 附和不打断 | 回答播放中用户说「嗯」（约 0.4 秒）：回答继续播到结尾，实际播放时长 ≥ 回答总时长的 95% | 5/5 |
| M3 | 它回答 | 普通问答，`t_sound − t_end` | ≤ 2.0 s |
| M4 | 打断 | 回答播放中用户开口说新问题：`t_stop − t_speech_start` 足够短，并且接下来答的是新问题 | ≤ 0.3 s |
| M5 | 看见 | 页面上的显示内容在 T 时刻变化，用户在 T+1 s 开口问，回答的是变化后的内容 | 5/5 |
| M6 | 动手 | 操作类请求：先有口头应答，任务卡片随后出现 | `t_sound − t_end` ≤ 2.0 s；`t_task − t_end` ≤ 2.0 s |
| M7 | 做完 | 用户没在说话时：`t_sound(结果) − t_verified` | ≤ 3.0 s |
| M8a | 断线 | 连接被切断 5 秒后恢复：侧栏显示「重连中」，然后自动恢复，用户不用做任何操作；恢复后问前面聊过的内容，回答正确 | 恢复 ≤ 10 s；回答 5/5 正确 |
| M8b | 连不上 | 语音服务地址被拦截：用户开口后出现明确的中文提示，说明连不上、该去哪里检查；不能一直转圈，也不能没有反应 | 提示 ≤ 10 s |
| M8c | 长时间挂着 | 一直听开着、2 小时不说话之后再开口问页面问题：满足 M3 | 跑 1 次 |

## 3. 场景

### 场景一：陪我看

夹具页：
- **鞋 A 页**：鞋底材质只写在商品图片里，DOM 里没有这段文字；页面上有一块「尺码表」；还有若干按钮，页面会记录所有点击和输入。
- **鞋 B 页**：价格和鞋 A 不同。
- **公式页**：用 KaTeX 渲染的一段推导，其中一步用到一个有名字的定理。

```gherkin
用例 1.1 看图回答
  假如 一直听已开启，当前标签页是「鞋 A 页」
  当   用户说「这双鞋底是什么材质」
  那么 回答的文字包含图片里写的那个材质名称
  并且 满足 M3

用例 1.2 边说边圈，不误操作
  假如 一直听已开启，当前标签页是「鞋 A 页」
  当   用户说「把尺码表圈出来，不要点」
  那么 页面上出现圈画层，盖住尺码表元素的面积 ≥ 80%，且圈画层面积不超过尺码表元素面积的 2 倍
  并且 t_mark − t_end ≤ 2.0 s，且 t_mark 早于这轮回答播完
  并且 这次运行中页面记录到的点击和输入都是 0

用例 1.3 跨页比较
  假如 用户在「鞋 A 页」问过价格，然后切到「鞋 B 页」
  当   用户说「和刚才那双比哪个便宜」
  那么 回答里同时出现 A、B 两页上的真实价格，结论正确

用例 1.4 公式
  假如 当前标签页是「公式页」
  当   用户说「第三步是怎么推出来的」
  那么 回答里提到的公式符号和页面上的第三步一致（按预先写好的关键符号逐个比对）
  当   用户说「把用到的那个定理标出来」
  那么 圈画层盖住那个定理名称，标准同 1.2
```

### 场景二：派它做长任务，聊进度

夹具：本机调研站，3 家公司各一页（公司名、业务、融资情况都是虚构的）；还有一个列表页。L1 用脚本任务模型，让任务固定按「搜索 → 逐家阅读 → 汇总」走，总时长约 60 秒。

```gherkin
用例 2.1 派任务
  当   用户说「帮我调研一下这几家公司，列个对比」
  那么 满足 M6，侧栏只出现 1 件任务

用例 2.2 问进度
  假如 任务进行到第 2 家公司
  当   用户说「做到哪一步了」
  那么 回答里包含当前步骤（第 2 家公司的名字），以及至少 1 条已经查到的内容
  并且 回答里没有任何还没读到的公司或事实（按侧栏过程记录逐条比对，出现一条就失败）
  并且 满足 M3
  并且 任务的编号没变，过程记录连续，没有重新开始

用例 2.3 中途加要求
  当   任务还在跑，用户说「顺便看下它们有没有融资」
  那么 侧栏的任务数量仍然是 1
  并且 最终的对比结果包含每家公司的融资情况

用例 2.4 主动说结果，接着追问
  当   任务核对完成，此时用户没在说话
  那么 满足 M7，结果摘要里至少有 2 家公司的名字
  当   用户说「第二家是做什么的」
  那么 回答和结果表第二行的业务一致
  并且 没有新开任务，也没有重跑任务
```

L2：同样的说法，换成真实网站和默认测试模型跑 1 次。判定：用例 2.2 的「不编造」逐条对照侧栏过程记录；2.4 的追问逐条对照侧栏里的结果。

### 场景三：两件事同时进行

```gherkin
用例 3.1 不抢话
  假如 场景二的任务在后台跑，用户切到「鞋 A 页」用场景一的方式聊天
  并且 任务核对完成的时候，用户正在说一句长话（这句话的 WAV 已经对准时间）
  那么 在 t_end 之前，侧栏没有播放任何助手音频
  并且 在 t_end 之后 3.0 s 内，它说一句提示（包含「做完」或「完成」），并询问要不要听
  并且 这句提示里不直接念完整结果
  当   用户说「说吧」
  那么 它念出结果摘要，标准同用例 2.4

用例 3.2 聊天不受影响
  假如 后台任务正在跑
  当   用户在「鞋 A 页」问用例 1.1 的问题
  那么 满足用例 1.1 的全部判定，回答里不夹带任务进度
```

## 4. 交付物

- 每条用例都对应一个真实路径验收用例，接进 `npm run accept` 体系。每次运行产出：
  - `result.json`：上面所有时间点、每条判定的通过或失败、失败原因；
  - 侧栏和页面的录屏，以及侧栏的音频录音（用户要能自己看、自己听）。
- 一张汇总表：每条用例一行，列出层级（L1、L2）、5 次里通过几次、时间中位数和最大值、证据路径。通过、失败、没跑分开写。
- 计时规则（多久重送、多久判断断线、什么时候主动开口）写成假时钟模拟测试 `*.sim.ts`。

## 5. 完成的定义

1. L1 全部用例按 1.3 的规则通过；
2. 场景二、三的 L2 各跑 1 次，结果通过；
3. 把汇总表、录屏和录音交给用户，用户在日常 Chrome 里试用后确认。

任何一条没满足，都不算完成。阈值不合理的话，提出来交给产品负责人决定，不能自行修改。

## 6. 不在本方案内

- 外放回声、真人口音和环境噪声：只在 L3 由用户判断。
- 费用、额度。
