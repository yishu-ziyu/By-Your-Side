# 语音慢与连接体验差：链路诊断

2026-09-09，用户要求找通用原因，不对单一句式打补丁。本轮只读产品与用户日志、调用真实模型做不执行操作的诊断；未重载或操作用户浏览器，未修改产品实现。

## 已验证的因果链

1. 意图输出协议脆弱。应用按标点拆分句子，要求模型分配的parts覆盖全部下标；语气词也占独立下标。真实M3对“嗯，先打开购物网站，然后帮我查一下今天的天气。”连续两次输出parts=[1]、[2]，遗漏0；两次均为成功返回stop，应用以classifier_invalid_reply拒绝。其他网站与动作也能复现，不依赖YouTube或邮箱。
2. 错误作用范围过大。StepVoiceSession.routeInput的catch调用fail；fail发state:error并close(false)，关闭语音socket。VoiceClient.receive遇到state:error调用fail→stop，释放麦克风与AudioContext。这是程序主动把单句判断错误升级为整段语音中断；connection_failed日志名也将业务失败混成连接失败。
3. 纠正任务缺语义上下文。classifyVoiceInput输入只有state、本句text/clauses及本句命中的会话名，没有当前任务目标和最近有效指令。原话复测首次漏语气词并把YouTube当target，重试后通过结构校验，却输出start+start；这说明结构通过也不足以证明理解了纠正原任务的语义。历史失败时未留原始候选，不能断言这就是截图那次具体拒绝条件。
4. 反馈被串行阶段累加。VoiceTurnDetector按20ms帧等35个静音帧提交，设计引入约700ms收尾；最终转写到达后才执行独立意图模型，判断完成后才生成回答。未命中缓存的固定回执还要更新语音指令、等配置确认、生成完整音频并校验对应转写后才播放。缓存只改善命中回执，不能消除其余阶段。
5. 工具完成定义过重。openTab创建标签后等待waitForLoad(tab,30000)，使用Chrome complete状态，再返回结果；用户“打开页面”与“整个页面加载完成”被绑定在一个工具完成时刻。网络/重资源加载会扩大等待。该代码事实能解释等待机制，但现存日志不能精确拆出地图那次19.6秒中各环节占比。

## 对照探针

[原始结果](20260909-voice-root-cause-probe.json)：六个输入串行调用生产classifyVoiceInput及当前真实M3，捕获每次响应，不访问网页、不执行动作。包括原话、无语气词、单语气词、明确纠正、其他复合动作、简单命令。其他复合句确认两次漏0→失败；简单命令898ms成功。原话这次第二次候选通过，不能伪称重现了历史完全相同响应。

## 优先修复的系统边界

- 分离单句可恢复错误与连接故障。判断失败清理本轮、说明未执行并继续收音；已经接受或结果不明的操作只能查原请求，不能重放。
- 调整语音意图接口：传入受限的当前目标/最近有效指令；语气词和内容定位由应用处理，避免模型承担易错下标搬运；目标使用受控候选，验证否定/条件/控制顺序仍保留。须跨句式、跨任务验证，不能直接删掉覆盖校验或补一条“嗯”的白名单。
- 区分页面创建、可交互、加载完成。按操作真正需要的就绪程度等待，反馈实际状态；不能提前说操作已成功。
- 给转写、模型每次请求、页面各就绪时刻和首音补分阶段诊断；保留隐私边界，不默认写入完整语音或私人页面。
