## 代码因果链

- mark工具仍存在（agent/src/tools.ts、extension/src/background/exec/input.ts），主任务提示词明确要求圈选用mark。
- voice-intent将看页面回答归observe；能力问句归chat，缺少“当前委托+后续纠正要求实际圈画”的充分边界。observe在manager直接调用answerVoiceObservation，后者是无工具的只读completeSimple调用，不能执行mark。chat补答也没有工具。这使“看见对象”与“对对象做动作”断开。
- 普通语音回答与操作执行必须区别：回答分支没有直接工具权限，不代表整个产品不能圈画。不能靠解除所有限制让只读回答假称做过。
- answerVoiceObservation/composeUserDelivery都等completeSimple完整文本，然后publishDelivery到界面，再让Realtime模型原样复述。
- voice-session在response.audio.delta把音频存入guarded.audio，只在response.done全文normalizeSpeech相等后释放；失败整段重试一次，再失败显示未播出。为防止复述改字采用的整段校验，直接破坏低延迟播放。
- normalizeSpeech仅去标点空白，数字/模型ID等读法变化可能触发不一致，但本次原始候选未记录，不能宣称已证实具体差异。
- 页面观察回答直接登记reply，未统一约束Markdown，截图中的**和反引号确实泄漏到正文。

### 第1步：只恢复语音圈画的执行路径

目标：用户说“找到页面上的X并圈出来”，实际进入现有执行器并调用mark；上下文纠正“你可以圈出来的/不是解释，圈出来”保留当前对象并执行。对“先别圈/我只是问能不能圈”不执行。

验收：已知中文、含英文模型ID/数字/Markdown的回答均可播放；上游首音频到客户端交付目标<=200ms；首段文本到首音频目标<=2s，先用5轮实测确认可达性，达不到则报告而不假称完成；长答案在合成结束前已开始播放；插话立即停旧音频、不重播、不重复执行任务。当前音色若不能复用，先向用户报告，不静默换声音。通过后用户只检查文字后的开口等待与打断，再停下。

### 第3步：再实现“答案边写边说”

让面向用户的正式正文流式产生，以短语/短句增量同时进入UI与同一TTS流；不等全文，不暴露内部思考或未完成的工具参数。播过的片段不可回写，后续是追加；旧轮晚到片段在打断后丢弃。避免再补一轮模型专门润色。

验收：至少三句的真实答案中，第一段音频在最终文字生成前开始；只使用一份正式正文；无丢字/复读，英文ID显示准确，口语读法不必逐字符相同；记录首个正文片段、上游首音频、客户端首播放、全文结束四个时间；用户听感通过后才算交付。

## 补充：为什么Harness只用了观察工具（用户要求继续追根）

### 定点真实模型探测

使用未修改的生产BrowserAgentSession.classifyVoiceInput、同一个MiniMax M3、隔离会话，无页面工具调用。脚本/tmp/ego-mark-routing-probe-20260909.mts，结果/tmp/ego-mark-routing-probe-20260909.json。是按用户所述重建输入，不是无法恢复的原始请求重放；每条一次，证明可复现，不代表错误率。

| 输入 | 上下文 | 实际分类 |
|---|---|---|
| 在当前页面找到临时模型ID，然后圈出来。 | 无运行任务 | observe |
| 你可以圈出来的。 | 上句要求圈画，助手错误声称无法圈 | chat |
| 不是让你解释，我是让你把它圈出来。 | 同上 | steer |

### 四个Harness责任点

1. **路由器先剥夺能力，却没拿到完整能力定义。** classifyVoiceInput使用独立VOICE_INTENT_PROMPT，只传state/text/clauses/会话标题/goal/对话。没有主Agent SYSTEM_PROMPT、browser tool schema或mark能力说明。它对“看页面+圈出来”做能力判定，却不知道圈画是产品已有的可执行标注工具，也没有“必须满足原句所有动作”的可判定结果字段。
2. **一次分类被当作终局。** manager的observe是直接调用observe_page→无工具completeSimple→publishDelivery→return；chat同样补答后return。有完整工具的主任务Agent根本没有接到原始请求。观察回答只返回string，无法结构化上报“这里只完成观察，还欠标注，需要交给执行器”。Harness没有核对“用户还要求圈画，但未有mark结果”。
3. **错误的能力自述又进入事实输入。** TaskProgress将正式reply存recentTurns/latestDelivery；answerSourcedChat在没有latestResult时直接以latestDelivery.text作为facts。于是“我不能圈”虽不是工具证据，却被放入下一轮事实输入；compose提示又要求依据来源、不改事实。产品能力没有独立权威来源去纠正它。这条链路在代码中已确认；没有持久化本次compose原始输入，不能宣称逐字恢复了线上调用。
4. **对话没有保存待完成操作。** observe只记录对话，不调用request建立goal/run；系统保留了“说了什么”，却没有结构化保存“用户要圈X，观察完成，标注未做”。后续“你可以圈出来的”只能再猜chat/steer，不能可靠继续原委托。单独加圈字关键词修不了这一类丢动作。

### 修正第1步的方向

不以“为圈出来加一个关键词”作为修复。正常网页请求应由带实际浏览器工具和同一上下文的执行Agent承担；语音入口负责接收、控制/会话定位和交接，不先把一般网页请求锁进一个无工具的答题器。保留只读快路时必须限定纯观察问题；需要动作或无法完成原委托时，交回执行器，不能把解释当成完成。

第一步验收覆盖“找对象并圈画”、同对象后续纠正、先读后点/标注、只读及否定反例。能力自述以工具注册表/实际权限为依据；先前助手自述只能作为对话记录，不能成为能力事实。对已授权但未做的操作保存对象和剩余动作；没有执行回执就不判完成，过期/否定/已取消的请求不能自动升级执行。

本次仍只复盘，未改产品。用户未要求取消分步检查，后续继续每步人工验收。
