# 语音架构、调度与交互原则

[文档导航](README.md) · [架构](architecture.md) · [使用说明](guides/usage.md#语音交互)

本页只写代码里看不出的目标、理由和服务端已知坑。

目标是像坐在旁边的靠谱搭档：说到的就做，做完才说，只在真的需要时才问。

按住说话的播报连接提前准备；为何没有采用听写预热候选、网络定位、对照结果及未验证范围，见[播报连接验证](evals/20261028-speech-connection.md)。

## 任务调度、多要求与请求结果

- **停声不等于中止任务**：停声或关闭语音通话只停声音或结束语音连接，后台网页任务照常运行。用户要结束任务只能中止。
- **后台忙时不挂断**：机器满载时扩展后台会十几秒不回消息，所以侧栏换新连接后用原语音编号认领，不断线。

## 排队任务的口播

任务排队时还没有开始执行，但原通话必须保留这句要求。任务一开工，就接上其进度和终态，不能等正式结果交付时才认领。

隔离扩展中的真实 GPT-Live 已验证“排队后开工、中止后说出结果”和“长任务仍在执行时说出进度”；麦克风使用合成语音，文字执行与分流由脚本固定。禁用开工绑定后，进度用例会失败，不代替真人外放验收。

消息送达不能算已出声：GPT-Live 偶尔对结果回了“已收到”却一直不开口，数据通道上看不出原因（见过一次，确认句刚说完时送到的中止结果之后 30 秒无声；照同样时机人为重放没能复现）。所以服务确认收到后 3 秒还没听到助手开口，就原样重送一次，再不开口就记进语音分段计时，`npm run logs -- --voice` 的备注会写“结果重送过”或“结果没念出来”。服务迟迟不确认收到时不重送：见过它把结果压了 16 秒才确认，这时重送，它缓过来会念两遍。`--case=queued-stop-unvoiced` 由脚本吞掉第一次送出并替服务确认：修复前一直无声，修复后约 3 秒重送、只说一次。

别的会话里的任务，播报时用用户自己说的第一句称呼它：只说“任务已终止”，语音层会自己猜是哪一件，曾把刚停掉的按钮清单说成“现在可以继续处理按钮清单了”。不用侧栏标题，因为标题按网站起，同一页上两件任务曾被起名为“语音练习”和“语音练习摘要”，语音层照念也分不清。

排队的任务没开工就结束时，靠这件自己的请求收条收尾（按请求编号认，对它说的别的话被拒不算）：用户说“取消…那件”时，那句自己的回话已经说了取消，原委派只悄悄收尾，不念第二遍；开不了工（本机存储写不进、名额被抢）时念“哪件没能开始，原因是…”，原因只取宿主说明的第一小句，整段浏览器英文报错送去会被语音层连原因一起略掉。`--case=queued-cancel` 与 `--case=queued-start-fail`（只让这件的开工记录写盘报 QuotaExceededError）验过；开工失败恰好和排队确认句同时到达时，语音层会把两句并成“排在后面、还没开始”，名字和原因丢失，尚未处理。阶跃星辰实时语音没有接这条收尾。

## 阶跃星辰服务端的坑

产品侧无法根治，只能快速发现并提示用户重说：

- 生成回答期间服务端几乎不判用户开口，侧栏靠本机阈值判插话（未用外放校准，「嗯」「对。」等短句可能掐断回答或被服务端当附和丢弃）。
- 取消生成或会话刚就绪时，服务端偶发挂住十几秒才开始听（期间仍发转写增量，不能凭转写增量判服务端正常）。
- 带停顿的一句话常在逗号处被服务端切成两轮，侧栏把同一轮的几段拼成一行显示。
- 浏览器 WebSocket 报错不带原因，分不清网络断连还是密钥被拒，侧栏统一提示连不上并引导去设置页检查。
