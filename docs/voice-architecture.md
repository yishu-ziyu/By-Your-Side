# 语音架构、调度与交互原则

[文档导航](README.md) · [架构](architecture.md) · [使用说明](guides/usage.md#语音交互)

本页只写代码里看不出的目标、理由和服务端已知坑。

目标是像坐在旁边的靠谱搭档：说到的就做，做完才说，只在真的需要时才问。

## 任务调度、多要求与请求结果

- **停声不等于中止任务**：停声或关闭语音通话只停声音或结束语音连接，后台网页任务照常运行。用户要结束任务只能中止。
- **后台忙时不挂断**：机器满载时扩展后台会十几秒不回消息，所以侧栏换新连接后用原语音编号认领，不断线。

## 排队任务的口播

任务排队时还没有开始执行，但原通话必须保留这句要求。任务一开工，就接上其进度和终态，不能等正式结果交付时才认领。

隔离扩展中的真实 GPT-Live 已验证“排队后开工、中止后说出结果”和“长任务仍在执行时说出进度”；麦克风使用合成语音，文字执行与分流由脚本固定。禁用开工绑定后，进度用例会失败，不代替真人外放验收。

消息送达不能算已出声：GPT-Live 偶尔对结果回了“已收到”却一直不开口，数据通道上看不出原因（见过一次，确认句刚说完时送到的中止结果之后 30 秒无声；照同样时机人为重放没能复现）。所以侧栏写进结果后 3 秒还没听到助手开口，就原样重送一次，再不开口就记进语音分段计时，`npm run logs -- --voice` 的备注会写“结果重送过”或“结果没念出来”。`--case=queued-stop-unvoiced` 由脚本吞掉第一次送出：修复前一直无声，修复后约 3 秒重送、只说一次。

任务开工前启动失败、仍在排队时取消，尚未覆盖，需要根据队列的请求结果另定语音收尾。

## 阶跃星辰服务端的坑

产品侧无法根治，只能快速发现并提示用户重说：

- 生成回答期间服务端几乎不判用户开口，侧栏靠本机阈值判插话（未用外放校准，「嗯」「对。」等短句可能掐断回答或被服务端当附和丢弃）。
- 取消生成或会话刚就绪时，服务端偶发挂住十几秒才开始听（期间仍发转写增量，不能凭转写增量判服务端正常）。
- 带停顿的一句话常在逗号处被服务端切成两轮，侧栏把同一轮的几段拼成一行显示。
- 浏览器 WebSocket 报错不带原因，分不清网络断连还是密钥被拒，侧栏统一提示连不上并引导去设置页检查。
