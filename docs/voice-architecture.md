# 语音架构

本文写语音链路为什么这样设计，以及服务端的已知坑。任务控制见[任务调度](voice-dispatch.md)。

## 一次语音请求

- 简单网页操作由语音模型直接调用正式工具，不经过主模型规划。复杂研究、内容生成，或直连工具做不下去时，语音模型才委派给任务系统。
- 只读问答与修改页面分开。口头翻译不算已翻译页面。
- 程序分别记账：操作已执行、目标已核验、用户已听见。三件事不能互相推出。

套餐 2.5 不装配网页工具，所以任务宿主先按真实转写分流：明确是闲聊，才放行原生回答；网页请求交给任务助手。
来源未确认、分流失败或超时，都不放行原生回答。用户选了无效的套餐时，语音拒绝启动，不回退按量。

## GPT-Live

- GPT-Live 只接受 WebRTC 通话，而且鉴权要带请求头。所以侧栏直接与 OpenAI 建通话，声音不经过扩展。
- 因为扩展收不到 GPT-Live 的声音帧，所以按音频帧做的三项保护都不适用：按回复编号核对来源、先扣住声音等转写判断「终止任务」、按音频帧确认用户已听到。
- 服务端停声慢：插话后很久才停，念任务结果时更久。所以侧栏在本地判断插话，立即把远端声音静音，任务照常。
- 只有任务交付给用户的结果送去播报。请求结果只作静默背景，GPT-Live 不念。
- 语音回传有大小上限，长回答只摘读完整的开头，未完成说明优先保留，并告知全文在侧栏；不增加一次摘要模型调用，也不截断半句话冒充完整结论。
- 服务端拒收会明确显示语音不可用并结束通话，不能仍显示「在听」。结束语音不等于中止后台任务。
- 通话开始和当前页变化时，只同步该面板窗口的页面标题与站点，帮助理解「这个页面」；不传地址参数、正文或附件，不把这些背景当成操作授权。
- 已完成的真实语音话轮用于同一通话的后续指代；被停声或插话打断的助手话轮不当作用户已听到。任务仍由委派触发，不因转写到达重复执行。
- 协议里没有取消回答的事件，所以「停声」也只在侧栏把这一段回答静音。
- 没用 ChatGPT 登录时，语音不建连接，也不退回阶跃星辰。
- 已知缺口：通话建好前说的话不会被听到。两次委派几乎同时到达时，前一次可能拿不到页面资料，最后以「没有执行」结束。

## 停声不等于中止任务

本节是这条规则的唯一说明。

- 停声只停播放的声音。关语音通话也只结束语音连接。两种情况下，后台任务都照常运行。
- 用户要结束任务只能中止。用户在可控任务期间说「终止任务」时，任务宿主直接中止任务。
- 插话停掉旧回答的声音，但不作废最新请求，也不中止后台任务。

## 四种生命周期

每种对象有自己的身份，彼此不能混用：

- 声音话轮：停顿不一定等于完整的任务要求。
- 用户输入：晚到的转写、补充和新要求不能随意合并或丢弃。
- 网页任务：停声或关通话不等于中止任务。
- 结果播放：生成完成、音频已送出、实际播完是三件不同的事。

## 提示词和程序分别保证什么

提示词只能引导，不能保证。程序检查的才是硬边界。

- **简短、不先念计划、结尾不反问。** 只靠提示词引导，不能保证每轮遵守。
- **音色。** 服务端回显音色 ID 不证明听感稳定，只能真人试听。
- **人设。** 人设插在身份句之后，并写明与规则冲突时以规则为准。实测放在规则末尾几乎无效；示例句会被模型照搬。口吻像不像只能人判断。
- **不重复派发、旧话轮不执行。** 程序能拦重复和过期，不能证明模型理解正确。
- **页面读写权限与新鲜度。** 由程序检查。提示词不能代替授权。
- **「终止任务」不被抢答。** 有可控任务时，程序先扣住服务端的自动回复，等本轮转写。转写比首帧音频晚一点，所以只在可控任务期间多等这一段。中止失败时，助手如实说没停。
- **要操作页面却先读页。** 读页结果附上下一步提示。因为只说「读页后直接回答」时，模型常常说完「我先获取快照」就结束了。

## 阶跃星辰服务端的坑

产品侧补救不了这些问题，只能快速发现，并让用户重说。

- 生成回答期间，服务端几乎不判定用户开口，所以侧栏在本机判定插话。判定阈值没有用真实扬声器外放校准过，用户说「嗯」这类附和也会掐断回答。
- 取消生成后，服务端有时马上开始听，有时十几秒后才生效，或者挂住。挂住时用户的新问题会丢失。
- 服务端判定开口比人声晚几秒。会话刚就绪就开口时，服务端常常完全不回应，过一阵后断开。
- 服务端卡住时，主动提交音频也救不回来。卡住时它仍持续发转写增量，所以收到转写增量不算服务端有回应。
- 带停顿的一句话会在逗号处被切成两轮，调静音时长也没用。推断：模型自带的话权协调按语义切句，而官方没有提供语义断句参数。前半句常在服务端开始回答后才转写完，所以侧栏把同一轮的几段拼成一行显示。
- 服务端会把「对。」这类短句当附和清掉，不给转写。那句话丢失。
- 连接失败时，浏览器的 WebSocket 错误不带原因，所以产品分不清是网络问题还是 key 被拒。侧栏只说连不上和去哪儿查。

## 读记录的坑

- 记录里「判停后首个音频」只是服务端判停后音频到达的时间，不是用户实际听到答案的时间。
- 日常记录的识别结果落在 turn 2 是正常的，因为服务端检测到第一段说话才进入 2。
- 扩展内部的消息传输不是另一次模型推理，但也不能假定零开销。归因要看同一轮的时间戳。

## 对已做过的事情追问

语音问“刚才的脚本在做什么”时，需要本任务的实际操作记录，不能只拿最后的百科答案，也不能用一句进度模板代替解释。查询只读取记录并回答，不因此重新执行网页动作。操作参数和脚本是待解释的数据，不是给回答模型的新指令。

目标已经核对完成时，历史失败尝试不能盖过最终结果；仍无法确认的操作后果继续明确保留，不把它们一并抹掉。

侧栏与后台的连接短暂迟到不能直接等同于断线，否则网页任务还在做，语音却已结束。需要重连时，语音界面必须同步进入恢复状态，不能继续显示“在听”。
