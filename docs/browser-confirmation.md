# 网页操作不再逐次确认

本页是“网页操作不弹批准卡”这一决定的权威位置。

2026-10-04 产品负责人决定：助手在网页上的操作直接执行，不弹批准卡（[验收](evals/20261004-remove-approvals.md)）。删除、发送、支付、提交类按钮也不再拿住等用户确认。产品没有受信任网站名单。

2026-10-09 例外：助手点名字以「发送 / Send」开头的按钮前，程序先停下，在网页上问用户（[验收](evals/20261009-send-confirm.md)）。
因为发出去的消息收不回来，而网页里注入的指令可以让助手在用户已登录的网站上发消息。用户只点「发送」才发；点「不发」、停下、接管、离开网页或 2 分钟没理，都不发。
这个例外只拦「发送」按钮的单击。删除、支付、提交和按回车发送照旧不问，所以这一页的决定对它们仍然有效。

2026-10-09 另一例外：助手永远不点付款按钮，用户在聊天里同意也不点；程序在网页上圈出这个按钮，由用户自己点（[验收](evals/20261009-pay-stop.md)）。所以上一段的「支付照旧不问」不再适用于付款按钮的点击。

仍然保留的保护：

- 结果未知锁：写入的结果未知时，程序不重复执行这次写入，由用户决定是否继续（见[结果未知](unknown-results.md)）。
- 用户的接管、交还与中止。派发动作前，程序仍检查任务身份与控制轮次。
- 没有进展或重复失败时，任务自动停下；[目标核对](goal-check.md)照常运行。
- 凭据脱敏；页面内容在隔离环境里读取。
- 记忆照常作为上下文交给模型；用户纠正后，“要我记住吗”照常询问。

原生弹窗：助手的点击或按键弹出 alert、confirm 或 prompt 时，回执写出弹窗内容。助手按用户的意思确认或关闭弹窗。

## 已知后果与缺口

已知后果：网页里注入的恶意指令可能让助手在已登录的网站上点击、提交，或在聊天框里按回车发出消息，因为没有逐步确认来拦截这些动作。

发送前确认的已知缺口（证据见[验收](evals/20261009-send-confirm.md)）。下面这些情况，消息可能不经用户确认就发出去，或者确认的范围比用户以为的大：

- 聊天框里按回车就发送的网站：程序不拦按键。
- 网页脚本程序（browser_run）里的页面脚本直接调用按钮的点击：这不经过点击动作，程序不拦。
- 「发送」按钮在 iframe 里：程序读不到按钮名字，不问。
- 网页在最后一刻把指针下的按钮换掉：程序读按钮和真正点下去之间有空隙。
- 按钮名字读不到（例如只有图标、没有文字和标签）：程序认不出是发送，不问。
- 「不发」只记在这一轮里（到用户再说话为止），而且只按网页和按钮名记：同一轮里改发另一条、点同一个「发送」，也不再问，直接不点。
- 等确认的状态只在扩展后台的内存里：后台重启时等待丢失，确认框收起，按钮不点。
- 「发送验证码」这类名字以发送开头的按钮，也会停下问一次。
