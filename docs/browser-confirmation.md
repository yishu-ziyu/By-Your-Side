# 网页操作不再逐次确认

本页是“网页操作不弹批准卡”这一决定的权威位置。

产品负责人决定：助手在网页上的操作直接执行，不弹批准卡。删除、提交类按钮也不拿住等用户确认。产品没有受信任网站名单。

两个例外：

- **发送。** 助手点名字以「发送 / Send」开头的按钮前，程序先停下，在网页上和侧栏里同时问用户（[侧栏确认卡](evals/20261015-panel-send-confirm.md)）。因为发出去的消息收不回来，而网页里注入的指令可以让助手在用户已登录的网站上发消息。用户只点「发送」才发；点「不发」、停下、接管、离开网页或久不理会，都不发。
- **付款。** 助手永远不点付款按钮，用户在聊天里同意也不点。程序在网页上圈出这个按钮，由用户自己点。

结果未知时，助手重读页面后可以重做（见[结果未知](unknown-results.md)）。「连续失败就停」也已去掉。

仍然保留的保护：

- 用户的接管、交还与中止。派发动作前，程序仍检查任务身份与控制轮次。
- 原地打转时，任务自动停下；[目标核对](goal-check.md)照常运行。
- 凭据脱敏；页面内容在隔离环境里读取。

## 已知后果与缺口

已知后果：网页里注入的恶意指令可能让助手在已登录的网站上点击、提交，或在聊天框里按回车发出消息，因为没有逐步确认来拦截这些动作。

发送前确认的已知缺口。下面这些情况，消息可能不经用户确认就发出去，或者确认的范围比用户以为的大：

- 聊天框里按回车就发送的网站：程序不拦按键。
- 页面脚本（js 工具、组合执行里的 browser.js）里直接点「发送」：脚本运行期间，程序在页面上拦下名字以发送开头的按钮的点击和表单提交，不点，并让助手改用点击动作（#290，验收 `scripts/acceptance/real-path/program-send-confirm.mts`）。仍有缺口：脚本用定时器在返回之后才点、或直接调用 form.submit()、fetch 发请求，程序拦不到。
- 「发送」按钮在 iframe 里：程序读不到按钮名字，不问。
- 网页在最后一刻把指针下的按钮换掉：程序读按钮和真正点下去之间有空隙。
- 按钮名字读不到（例如只有图标、没有文字和标签）：程序认不出是发送，不问。
- 「不发」只记在这一轮里（到用户再说话为止），而且只按网页和按钮名记：同一轮里改发另一条、点同一个「发送」，也不再问，直接不点。
- 等确认的状态只在扩展后台的内存里：后台重启时等待丢失，确认框收起，按钮不点。
- 「发送验证码」这类名字以发送开头的按钮，也会停下问一次。
