# 架构

[文档导航](README.md) · [当前状态](STATUS.md)

本页只写代码里看不出的理由和边界。

- 语音的明确填写由 Realtime 选工具，任务宿主调用同一个已注册工具，不增加 Pi 推理。所以「不保存/提交」要贯穿要求、工具选择与权限检查，不只靠一句提示词。
- 端到端耗时与各分支使用频率**待验证**，不按模块数估算。

## 职责与事实边界

- 请求结果只说明请求去向，不说明网页目标完成，见[语音架构与调度](voice-architecture.md#任务调度多要求与请求结果)。
- 中止、插话、改口、接管时，任务原要求、结果未知项和已接受未消费的插话都保留。停声与中止的区别见[语音架构](voice-architecture.md#任务调度多要求与请求结果)。
- 语音回答生成完成不等于播放完成。任务视图、摘要与侧栏缓存都是同一份事实的不同投影，所以不能因为状态同名就把它们合并删掉。
- 工具名、元素编号、原始 JSON、Chrome 错误码等原文只留在记录和模型上下文。用户看到的文字都翻成人话；翻不出时说笼统但真实的话，不回退原文。

## 新任务不让模型手工记账

执行条目由真实的工具结果自动登记。所以新任务不再给模型手工登记的工具，免得模型与自动登记同时维护同一条目。

## 少来回、每次快一点

用户一周的真实使用里，大部分时间在等模型想下一步，页面操作只占一小部分。所以要快，就要少来回几次、每次来回快一点。改法按这个顺序，前一项量过再做下一项：

1. 点击、填写、按键、选择之后，工具直接带回页面上新出现的东西，只带变化、限长。原因：真实任务里很多次来回只是为了再看一眼页面；打开新页直接带回页面后，总来回明显减少。
2. 填写像真人敲键盘，并能“填完直接回车”。先在本机复现“直接改值不生效”，再改。回车即发送的输入框，仍要停在发送确认。
3. 一次回复可以做好几步；跳页或焦点变了，就停下后面的。放在 1 之后，因为停不停要看 1 带回的变化。同类做法：Browser Use 一次最多 5 步，Ego lite 让模型把几步写进一段脚本。
4. 打开、点击、看一眼这类机械步骤改用快模型，要判断的步骤仍用主模型；思考档位“只升不降”的规则一起改。放在 1–3 之后，因为要先知道还剩多少次来回。
5. 加拖动，能在画板上画。

用户一次说了好几件事时，交回答前先对一遍清单，还有没做的就接着做，过程行写做到第几件；只说一件事的照旧先显示回答。原因：真实使用里常常先显示一个像做完的回答，过几十秒再更正。放弃的是“多件事也先出回答”的那几秒。
