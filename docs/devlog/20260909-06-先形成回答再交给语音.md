# 先形成回答，再交给语音

## 1. 用户换了一个参照

用户实际用过Grok Bot，觉得交流更舒服。他提供了一个非官方重建仓库，要求先看做法，再继续试。

我们暂停了局部话术修补。此前同一条测试路径有时通过，有时照搬Markdown或只说“这封邮件”。更多提示词没有形成稳定的交付边界。

## 2. 借鉴的是对人说话的通道

重建代码要求Agent通过SendMessage发出用户消息。内部工作文本和工具结果不自动成为正式回复。它还检查结果有没有交出去，开头的接收回应不能抵掉最后的结果。

transport本身只转交消息、记录身份。没有证据表明它用另一个模型统一润色输出。

本轮因此保留现有任务模型和语音模型。任务模型负责组织面向用户的内容，语音读取这份内容。任务事实继续单独保留，供追问核对来源。

## 3. 不让播放状态改写答案

交付有自己的身份。侧栏显示一次，语音播放一次，播放完成只更新状态。

首轮侧栏验收找到一个竞态：上一条播放完成晚到，语音区会从新回答跳回旧回答。修复后，已有消息的状态更新不再替换正文。旧历史仍可阅读，内部过程仍在正式答案上方的折叠区。

## 4. 验收从真实入口开始

本轮独立脚本从生产侧栏输入和点击发送开始，连接真实任务模型、页面工具、语音客户端、采音处理和播放器。麦克风输入使用受控合成音频，用户浏览器不参与测试。

先让旧代码跑通这条检查路径，再加入“正式交付、侧栏正文、语音正文必须对应”的条件。框架能跑不算新功能通过。

## 5. 当前结果

侧栏9项独立浏览器检查通过，历史不可改写的检查通过。完整对话又找到一个问题：追问已经说完，播放状态却没有记到新回答上。原因是回执仍带着交付前的旧记录。两条独立测试先失败，修复后通过。

统一检查通过886项测试，类型检查和构建通过。真实模型完整对话31项检查通过，服务过载与测试页面被导航覆盖的失败记录均保留。

但本轮任务模型没有主动调用交付工具。两个任务依靠有限补写，三次追问也单独组织正文，共增加五次现有任务模型调用。三次追问到首段音频约12、19、22秒。

结果是：正文和播放状态能对齐，交流仍有明显等待。下一步由用户判断这份稳定性是否值得当前延迟，再决定是否优化交付时机。自然听感仍须实际试用。
