# 从 ChatGPT 归档失败看就地拦截与健壮性

日期：2026-09-05

## 1. 现场

后台日志里记录了一次真实 ChatGPT 会话归档任务。

任务最终未能顺利完成。后台日志出现了两条：

```
[sideagent] tool click session=main err 6ms Cannot read properties of null (reading 'x')
[sideagent] tool click session=main err 5ms Cannot read properties of null (reading 'x')
```

随后模型调用了一次 `mark` 工具，并向用户声称：光标已停留在归档按钮上，名牌上已展示确认按钮，等待用户确认。

但在真实屏幕上，光标依然停留在初始的角落原位。名牌没有双键，也没有就地拿住目标。

用户指出了这一点：失败案例非常有价值，应当用来反思、排查和迭代。

## 2. 根因剖析

排查发现了四个彼此咬合的隐蔽问题。

### 2.1 Chrome MV3 executeScript 吞错陷阱

在 Chrome Extension Manifest V3 中，`chrome.scripting.executeScript` 注入的函数如果在页面上下文抛出未捕获异常，Chrome 不会向外 reject Promise。

它会把错误吞掉，并返回 `[{ frameId: 0, result: null }]`。

原先的 `callDom` 直接提取 `results[0].result` 赋值给 `targetRect`。一旦页面查找元素抛错，`targetRect` 就变成了 `null`。紧接着代码访问 `targetRect.x`，就直接裸抛了 `Cannot read properties of null (reading 'x')`。

真正的 DOM 错误被掩盖了，调用方只能拿到一个莫名其妙的空指针崩溃。

### 2.2 危险操作词表缺失「归档」

此前系统的不可逆操作词表只包含：删除、清空、支付、发送。

对 ChatGPT 等生产工具而言，「归档」也是重要的会话隐藏与变更操作。

因为不在词表中，底层执行层没有把对归档按钮的点击识别为危险动作，也就没有触发底层的自动拿住拦截。

### 2.3 模型的幻觉与语义缺口

由于底层没有自动拦截，模型尝试用 `mark` 工具做视觉提示。

但模型在调用 `mark` 时，并未传入 `actions` 参数，只传入了标注文字「待归档」。

在原实现中，只有携带 `actions` 的 `mark` 才会激活虚拟手光标的拿住态（`holding`）。普通的 `mark` 只是在页面上画一个静态边框，光标根本不会飞过去。

模型产生了幻觉：它以为自己调用了 `mark`，屏幕上的光标就已经停在按钮上了。实际上光标根本没动。

### 2.4 AX ref 重布局丢失光标

系统支持两套快照：CDP AX 树快照与 DOM 快照。

AX 树快照使用 `backendNodeId`，不进入 DOM 对象的缓存表。

在拿住态发生页面滚动或重布局时，光标会尝试寻找 `liveAnchor`。由于 AX 树生成的 ref 无法反解成 liveAnchor，原代码直接给光标追加了 `.hidden` 类名。

这导致即使拿住了元素，页面只要发生轻微滚动或重排，光标就会在用户眼前瞬间隐身。

## 3. 修复

针对上述四个环节，进行了成套收口：

1. **信封包装**：在 `callDom` 注入页面的执行体内部，统一包裹 `try / catch`，以 `{ ok: true, rect }` 或 `{ ok: false, error }` 信封结构向外通信。如果页面出错，向外透传具体的 DOM 异常信息，并在外层做非空校验，绝不裸抛 `reading 'x'`。
2. **词表扩充**：`DESTRUCTIVE_ZH` 与 `DESTRUCTIVE_EN` 补入「归档」与「archive」，并将确认词映射为「归档」。点击归档按钮将直接进入就地确认拦截。
3. **语义兜底**：实现 `resolveImplicitMarkActions`。调用 `mark` 时若未提供 `actions`，但标签以「待」开头（如「待归档」「待删除」）或命中危险词，系统自动推导 `confirm` 与 `cancel` 双键，并让虚拟手飞过去就地拿住。
4. **锚点容错**：在重布局逻辑中，若拿住的目标无法反解为 liveAnchor，光标不再被隐藏，而是保持在当前记录的中心坐标 `hold.point`。
