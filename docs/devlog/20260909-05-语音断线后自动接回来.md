# 语音断线后自动接回来

## 1. 用户指出了三件事

上一轮语音比之前自然，但接任务仍反复说“任务已收到”。窄侧栏的底栏按钮跑出了边界。长聊后连接断开，用户需要自己重试。

用户给这次体验打了70分。这是一次个人体验反馈，不是稳定性统计。

## 2. 接收回应要知道接了什么

单个任务被应用接受后，语音根据这句委托生成一句确认。暂停、终止、失败和结果未知仍遵循事实回执。

第一版只在没有计划对象时生效。真实分发器总会附计划，因此自测通过，真实入口仍说固定文案。Boss用真实分发路径复现后退回修改。现在明确的单步任务可进入，复合任务仍按逐步回执回答。

真实语音样本：“收到，这就去帮你整理这篇文章的主要观点，先不发布。”这句话只确认将做什么。

## 3. 断线分成传输和恢复

Native传输原来把输入和输出都限制成1MiB。Chrome允许输入64MiB、输出1MiB。1.2MB截图型消息能够复现进程断开。现在按方向设置上限，真实子进程可连续处理大帧与后续小帧。

这证明了一条故障路径。旧日志没有该次消息大小，不能断言用户截图中的断连只有这一个原因。

语音开启后遇到可恢复断线，侧栏保留麦克风流，换连接代次自动续接。重试最多三次、总预算30秒。用户主动结束会取消恢复。旧音频和网页指令不重放。

Boss独立测试又发现三处遗漏：静默超时没有守住预算，重复连接通知耗尽次数，复用麦克风后拔掉设备没有报错。修复后原失败检查转绿。

## 4. 底栏只修容纳关系

长模型名允许省略，固定操作保留可点击宽度。没有重做配色、粒子球或界面层级。

五种宽度、三种状态、语音开关共30种组合通过几何检查。模型、附件、语音、接管和停止发送继续由真实按钮事件验证。

## 5. 下一步

验收结果与最新构建状态以两份eval为准。自动检查使用隔离浏览器与合成语音，真人麦克风听感和连续使用仍由用户裁决。本轮不代用户重载，不提交或推送。
