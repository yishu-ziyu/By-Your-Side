# 会话独立运行与同页协作

## 1. 新会话不打断旧任务

用户明确了一个行为：新建 B 后，A 应继续运行。

切换会话改变用户正在看的内容。任务仍属于原会话。

## 2. 两种页面关系

ego-lite 用任务空间管理页面。Kimi WebBridge 用 session 和标签组管理页面。

浏览器插件可以采用后者。不同会话访问同一 URL 时，各用自己的标签页。

但未保存的简历是同一份页面状态。开两个标签不能代替共同编辑；服务端自动保存也可能产生覆盖。

## 3. 多光标需要配合输入调度

两个子 Agent 可以同时准备各自内容，也可以有不同颜色的光标。

我的判断是：普通网页中的聚焦、输入、验证需要按短段协调。只给单次点击排队，仍可能把文字输入另一人的字段。

研究依据与实验建议见 [研究文档](../research/20260908-session-spaces-and-shared-tab.md)。本轮 0 个产品代码改动，0 次浏览器并发实验。下一步先验证同页分工是否串字段，以及跨会话控制是否相互影响。


## 4. 先确认使用方式

用户授权开发后，补充了一个顺序要求：先看临时 HTML 的前后对照，满意后再推进产品。开发中若交互变化，也先更新对照。

因此本轮没有改产品。独立校验先锁定标准，再做两条可点击路径：新建会话时旧任务继续；同一份简历由两位 Agent 分工，接管后都停下。

原型保留现有侧栏风格。当前会话名称常显，历史按需展开，另一会话的运行状态仍可看见。

2 条模拟路径已检查，产品代码改动仍为 0。下一步由用户确认使用方式。


## 5. 分工由 Agent 判断

第一版示例让用户提出“请两位 Agent”。用户指出，这把调度工作推给了人。

修订后，用户只说“完善简历”。Agent 判断两部分是否可以同时准备，再主动说明分工。简单任务仍可以由一位完成。

原型只改用户目标与 Agent 的解释，没有把人数选择做成新入口。下一步检验实际运行时是否能作出合适的分工决定。

## 6. 从原型进入实现

用户确认后，会话拥有独立的运行时、历史、草稿和页面集合。切换只换侧栏正在展示的内容。页面首次使用时才进入会话的标签组。

同页协作采用完整填写事务。定位、核对旧值、输入、读回在一段操作内完成。用户接管后，排队中的旧写入失效。

## 7. 实测推翻了两个假设

有派工工具和原则提示，不代表模型就会主动分工。M3 首次完整填写了两段简历，但全部由 Lead 执行，这项验收失败。

进一步测试发现，重载后旧测试页被列入未归属页面。新会话读到了上轮草稿，任务变成局部修订。页面查询因此收紧为只列当前会话拥有的标签。

从空白页复测后，M3 主动派出一名成员，却只让它交草稿。共享页的完整材料读取也受到原有快照截断和脚本保护的限制。下一步补齐受页归属约束的只读读取，并让字段负责人完成填写和核对。

## 8. 当前证据

会话与共享页底层浏览器检查 15 项通过。M3 的会话隔离、切换和草稿恢复 5 项通过。伴随进程重启后，M3 正确回答旧会话保存的代号。

类型检查和 533 项测试通过。主动同页填写仍未通过，不能把正确的最终表单当成有效协作的证据。

## 9. M3 正反例跑通

把分工判断移到提示最前，并给协作者完整读取材料的方法后，连续两次同页分工跑通。两个成员各自完成填写、读回，再由 Lead 核对。页面没有提交。

最后一轮耗时 59 秒。单字段反例耗时 8.2 秒，没有派工，其余字段保持空白。

这证明了协作可以正确完成，还不能证明它更快。早期由 Lead 独自填写同一短样本约 24 秒。模型分工还要付出启动、重复阅读和汇总的成本。后续应验证什么任务规模能覆盖这部分成本。

用户要求总耗时控制在两小时内。本轮停止新增实现，进入最终验收和汇报。真实分工文案仍有工具名、字段选择器等技术表达，留在人评中判断。

## 10. 最后收尾

存活的 M3 协作者完成了接管补验。两名成员能读取完整正文和两个长字段，六次写入尝试全部被阻断，页面值、焦点和滚动位置不变。

原生截图暴露了一个回放显示错误：历史任务被显示为回放处理耗时。现在新事件保存原始时间，旧记录缺时间则不显示耗时。M3 实测首次显示 1.9 秒，关闭重开仍为 1.9 秒；旧记录不再显示错误数字。

最终为 61 个测试文件、550 项测试通过，类型检查与构建通过。原始截图和模型轨迹留在本地。界面观感、分工文案及实际效率仍交给用户判断。
