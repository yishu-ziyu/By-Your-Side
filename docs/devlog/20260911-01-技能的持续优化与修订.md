# 技能的持续优化：证据累积，而不是自我进化

2026-09-11。用户提出：技能列表会持续优化，技能本身也会更新，架构要提前想清楚。
用户已确认半自动的默认档位：**只读技能跑之前先问一句「要不要按上次那样跑」**。

## 方向

技能不是一条写完就冻住的脚本，也不是一个会自己变聪明的黑盒。它是**用户教会的一件事**，
之后靠**证据**决定三件事：还敢不敢自己跑、要不要改、要不要报废。

所以设计取舍只有一句：**技能只在有证据的时刻变，而且变化对用户可解释。**

## 一、什么算证据

| 来源 | 记什么 | 会怎样 |
| --- | --- | --- |
| 每次运行 | 时间、耗时、结果、失败停在哪一步、当时页面的指纹 | 决定提示语气与是否继续问 |
| 用户当场纠正 | 「不对，是下面那个」这类话 + 当时那一步 | 生成修订建议（要用户确认） |
| 运行后反馈 | 「这次少了两个」 | 生成修订建议（要用户确认） |
| 重新示范 | 同一页再做一遍 | 直接产出新版本，旧版本保留 |

**不产生版本变化的**：跑得次数多、跑得快、模型觉得"可以更好"。跑 100 次也不自己做主。

## 二、版本规则

- 一个技能 = **一条版本线**，不做分支、不做合并。多分支会立刻变成用户看不懂的东西。
- 抬版本只发生在两种时刻：**用户确认的修订**，或**重新示范**。
- 旧版本保留最近 5 份，随时可回退；回退本身也记一笔（谁把它退回来的）。
- 修订默认由用户确认后落盘：技能是用户教的东西，静默改会让"今天它为什么这么做"无法回答。

## 三、连续失败怎么办（这是"持续优化"最容易被做歪的地方）

- 单次失败**不重写脚本**。失败原因分两类：页面变了（对象找不到）、还是流程本身变了（多了一步）。
- 同一个技能**连续 3 次**因"对象找不到"停下 → 标记**可能过期**：下次只提示、不直接跑，
  并把选择权交回用户（重新示范 / 忽略 / 删除）。阈值是可调旋钮，不是教条。
- 因流程本身失败 → 不标记过期，直接建议修订（因为证据指向"做法要改"）。
- 任何自动降级都**留痕**：卡片上写清"为什么它现在不肯直接跑"。

## 四、触发靠页面签名，不靠感觉

- 示范时顺带记下**页面签名**：hostname + 那一页的类型特征（例如"有列表、有筛选按钮、标题含 XX"）。
- 匹配在**扩展侧**做（只有它知道当前页面长什么样），不在伴随进程里猜。
- 匹配到多个候选 → 列出来让用户选，不自己挑一个跑。
- 拿不准就不触发。**沉默是允许的产品行为**（路线图第 5 节）。

## 五、存储形态（最小）

```
~/.sideagent/skills/<id>.json          技能本体（version / steps / inputs / check / program）
~/.sideagent/skills/<id>.history.jsonl 版本历史（含修订来源与理由，回退用）
~/.sideagent/skills/<id>.runs.jsonl    运行记录（append-only，一次一行）
```

沿用现有 `SkillStore` 的原子写（临时文件 + rename）与 hostname 作用域；不引入数据库。

## 六、用户看得见的四件事

1. 卡片上一行事实：**跑过 7 次 · 上次 3 秒 · 2 次因为页面变了停下**。
2. 「回到上一版」。
3. 「这次不太对」——当场生成修订建议，确认才抬版本。
4. 「忘掉它」——删掉后不再被检索与触发（已有）。

不说"AI 会自己变聪明"。用户看到的是次数、结果、失败原因和版本。

## 七、边界（明确不做）

- 不做自动优化循环（无人监督地改自己的脚本）。
- 不做跨站迁移。
- 不做分支/合并/依赖的技能图。
- 不把偏好文字塞进技能（偏好归记忆；技能只存可执行的东西——否则技能退化成一个更长的提示词）。
- 不需要用户确认就不执行写入类技能，这条永久不变。

## 八、落地顺序

1. **运行记录 + 技能列表**（跑了几次、上次结果、上次失败停在哪）。没有这个，谈"持续优化"是空的。
2. **一键「照上次那样跑」**：零模型调用，跑前问一句（用户已确认这个档位）。
3. **修订入口**：跑的过程中纠正 / 跑完点「不太对」→ 修订建议 → 用户确认 → 抬版本。
4. **回退到上一版**。
5. **连续失败 → 标记可能过期**。

## 追加（2026-09-11 04:30）：候选从哪来 —— 观察取代"要用户主动教"

用户提出：不该总让用户"教它编脚本"，Agent 应该**观察用户自己的浏览器行为**，从中整理出可复用的做法，再问用户能不能用。已认可。

保留的判断：**观察改变候选的来源，不改变执行形态。** 候选仍然编译成同一套技能结构（步骤 / 可变输入 / 完成凭证 / 折叠脚本），因为脚本给的是确定性（跑一次 1.4 秒、零模型调用）、可核对、可回退。若改成"从行为总结成一段提示词"，就退回成更长的提示词：慢、不可核对。

关键问题不是"示范 vs 观察"，而是**什么算一次任务**。示范自带意图；观察只有行为流，意图只能从**重复**里推出来——同一站点、同一串动作、做过多次，才是"这是常做的事"的证据。做过一次的是路过，不是任务。

### 最小切片

1. **行为骨架日志（本地）**：站点 + 语义锚点序列 + 时间 + 次数。**不记输入值**（沿用现有脱敏：密码/卡号/验证码永不落），沿用字节预算。
2. **重复检测 → 候选卡**：同一站点、同一串动作、**≥3 次且跨 ≥2 天** → 面板问「你在这个站这样做过 3 次，要不要我以后替你跑？」→ **用户点头才生成技能**；生成走现有 `compileSkill` 与校验，落地仍是零模型一键跑。

### 边界（底线，不是懒）

- 不录屏、不采 DOM 全文、不做跨站关联；
- 只在 `http/https`；**敏感站点清单**（银行/支付/邮箱/后台）不采；密码与验证码永不采；
- 观察开关**默认关**，用户打开才开始记；
- **不问就不跑**：学到的权限 ≠ 获准执行的权限。


## 追加（2026-09-11 04:45）：技能／观察的 UI 需要一次设计优化（用户指出）

功能先够用，UI 是 v0。现状问题：

1. **入口形态不统一**：记忆是抽屉，技能是被塞在消息区上方的一条 strip，同一类东西两套形态。
2. **三种信息挤在一条窄栏**：观察开关、候选卡、技能行，层级全靠字号和边框；侧栏窄时按钮折行。
3. **按钮主次不分**：技能行平铺五个（照跑／重新示范／不太对／回退／忘掉），看不出哪个是常走的。
4. **默认暴露太多**：事实行、凭证、版本、步骤全在默认视野，没有"只露摘要、细节收进折叠"的分层。
5. **候选卡没有展开**：只给一行长文案，看不到它到底记下了哪几步。
6. **观察开关的位置与解释**：它是长期开关，却和一次性操作挤在一起；也没有"在哪一页生效／哪些站点不采"的说明入口。
7. **空态是命令式口吻**（"点顶栏那只会看的手"），不是产品口吻。

动手前先定三件事：

- **A. 归属**：技能与观察并入「记忆」抽屉，做成统一的"知识"抽屉（记忆／技能两个分区）？还是保留独立入口？
- **B. 信息分层**：技能卡默认只露「名字 + 事实行 + 一个主按钮」，其余（凭证／步骤／脚本／回退／忘掉）收进展开？
- **C. 观察开关放哪**：技能面板内（顺手）还是设置里（它是长期开关）？

素材来源按既有前端协议清单（beautifului.dev / beui.dev / rareui.com / transitions.dev / ui.shadcn.com / ui-skills.com / coss.com/ui / designsystemchecklist.com / reui.io/components / emilkowal.ski/ui）：检查→挑选→集成定制，不凭空发明。若有方向分歧，先出 1–3 个预览让人选，认可后再实现。

**只记不做**：用户 2026-09-11 明确"门槛倒不用调低，但 UI 设计要记得优化"。


### 结果（2026-09-11 05:05）：采用方案一

用户选定**方案一（摘要 + 展开）**，观察开关留在技能面板（A、C 两项已定）：

- **A**：记忆与技能合成一个入口「知识」，抽屉里分段切换；不再有第二个抽屉。
- **B**：技能行默认只露「名字 + 事实行 + 一个主按钮」；凭证／步骤／脚本／重新示范／不太对／回退／忘掉收进一次展开（方案二的「⋯」菜单未采用：低频动作不值得加一层）。
- **C**：观察开关在分段行右侧，打开时才显示「已记 N 段」。
- 两处按我此前的建议改掉：观察行压小；过期技能事实行标「过期」、主按钮保持「照跑」，点下去**就地确认**（不用 `window.prompt` —— 原生对话框会把面板整个卡住，真机踩过）。
- 空态区分两种：没连上伴随进程 vs 这一页还没有技能。
