# 20260907-01 模型能力标签退回中性

稳定化首轮（标准 `docs/evals/20260907-stability-foundation.md`）的第一个修复，对应 issue #2。

## 1. 问题：能力声明没有输入

9 月 5–6 日做的模型思考档位体系，UI 标签的来源是 `modelReasoningMeta(provider, modelId)` 一个纯函数。它没有任何能力输入：`ModelOption` 协议只有 id/provider/modelId/name 四个字段，`ClientMessage` 也没有思考档位设置消息。

于是能力全部靠猜：openai/openai-codex 一律「支持档位调节」，名字含 thinking 算「内置深度思考」，其余默认「极速直接响应」。未知模型不是未知，而是被断言为「极速」。

我当时把这套映射称为「与真实后端严格对齐」。本轮校验指出：这是无证据推断。我接受这个判断。

## 2. 判断：没有证据时，沉默优于错误的肯定

标签的价值在于可信。一个可能错的「极速直接响应」比没有标签更糟——用户会据此选模型、预期行为。原则改成：**能力标签的唯一合法证据来源是已验证的 runtime/SDK/适配器元数据；元数据不存在，就不显示。**

由此推论：「支持档位调节」在产品接通调档链路之前也不该出现——它同时捏造了模型能力和产品能力。

## 3. 做法

- `modelReasoningMeta` 删掉全部猜测分支，恒返回 `{ tier: "unknown", tag: null }`。函数签名保留，等协议真带能力元数据时调用方不用动。
- 菜单项与芯片两处渲染都加了守卫：`tag` 为 null 就不产出元素、芯片隐藏。
- 测试先写反例（12 条：未知供应商、同供应商未见模型、代理别名、名称关键字、冲突混杂、空字段），旧代码 12 条全失败，修复后全过。这不是删断言，是把「断言猜测正确」纠正为「断言无证据即中性」。
- `tag-native/effort/direct` 样式类保留，供真实元数据接入后复用。

## 4. 证据

- 修复前：`extension/dist/sidepanel.js` 里「支持档位调节」「内置深度思考」「极速直接响应」各出现于猜测函数；修复后 rebuild 三个文案 0 次。
- 真机：生产侧栏（用户 Chrome，扩展 fnbjglh…）当前模型 MiniMax-M3——旧实现必显示「内置深度思考」——修复后芯片标签 hidden，全页无可见能力标签。
- 全量 vitest 394 通过（基线 385，净增 9 条反例），typecheck/build 绿，accept:browser 复跑通过。

## 5. 下一步

- 能力标签要回来，正路是协议携带真实元数据，不是扩充名称表。
- 稳定化矩阵其余条目（连接错误、控制权、生命周期、危险确认、选中即问）按 issue #1 继续逐项排查。
