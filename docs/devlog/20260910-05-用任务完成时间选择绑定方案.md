# 用任务完成时间选择绑定方案

## 1. 要解决的问题

简单浏览器任务会花多轮登记和重新绑定目标。本轮比较两种减少往返的方法：执行时自动绑定唯一待办，或让动作携带原待办编号。当前完整工作区作为基线。

Codex规划和评审。DeepSeek实现候选与测量脚本。子执行环境无法联网和使用本地端口，用户确认后由Codex在宿主启动脚本，DeepSeek继续分析。

## 2. 判定用一个指标

用户要求取消多维权衡，改用六次固定任务全部正确完成的平均耗时。任一次真实失败就不达标。全部通过者中，耗时最低者胜出。

页面状态和事件计数检查任务结果。登记轮次、token与首动作时间用于查原因，不再决定选型。

## 3. 测量先修自己的错误

隔离副本没有.git，旧证据采集在启动时失败。改用记录的基线版本和真实源码hash标识快照，新增批前预检。

内部登记不发浏览器RPC，不能从RPC列表数登记次数。工具开始尝试也不等于页面发生动作。测量分别记录内部工具事件、实际下发和页面事件时间。

首批失败保留。有效批次不删慢样本，不重跑刷掉真实失败。

## 4. 结果

A六次全部成功，平均83.701秒。B与C各五次成功、一次失败。按指标保留A，不把两个候选接入产品。

有效对照18次，真实失败2次，源码漂移0。依据与原始结果见[选型结论](../tasks/20260910-binding-ab/decision.md)。下一步若继续优化，需先修复失败路径，再按同一指标测试新候选。
