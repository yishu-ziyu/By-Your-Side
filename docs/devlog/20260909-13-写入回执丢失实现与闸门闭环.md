# 写入回执丢失实现与闸门闭环

## 1. 为什么不能把失败当成未执行

在网络不可靠或长耗时操作中，请求发出与收到回执是两个时刻。

如果页面已经产生了新增、提交或修改，但回执在网络途中丢失，调用方只知道自己没拿到结果，不能推断页面没有执行。过去系统将超时统一处理为普通失败，允许再次登记并自动重放，导致隔离浏览器与服务端实际新增了两条记录。

## 2. 做了什么改动

本次打通了调用链中执行状态的传递与守门：

1. **区分三种事实**：引入 `not_executed`、`unknown` 与 `executed`。未发送前或执行器动作前明确拒绝为 `not_executed`；发送后超时或断连为 `unknown`；明确成功为 `executed`。
2. **保守保留未知**：写入工具在缺少明确未执行证据时，失败必须保留为 `unknown`。只读工具失败依然为 `blocked`，读取错误不锁死写入。
3. **拦截重复写入**：任务账本拒绝通过重新登记将 `unknown` 洗成 `pending`。执行闸门检测到当前任务存在未决写入时，拦截所有后续写操作（包括更换目标别名、新登记 id 或通用页面 JS），仅放行只读核查工具。
4. **晚到回执核销**：RPC 保留已分发记录。迟到的成功回执在严格核对所属调用编号与任务编号后，可将原未知项收敛为已完成。
