# 浏览器能连续执行后，模型仍要会组织动作

## 1. 这次要解决什么

逐个工具调用会把一段已知操作拆成多次模型往返。参考 ego lite，把浏览器方法放进一段可执行程序，是值得验证的方向。

本轮先实现小范围组合执行，再用真实任务比较。

## 2. 能力已经接上

新增 browser_run。程序可以顺序操作、根据观察分支、等待页面条件，并返回结果。

程序使用独立 JavaScript 解释器。它只能通过现有浏览器通道操作页面，没有宿主文件和环境变量权限。

每个子动作继续显示和记日志。接管、取消和危险点击确认会停止剩余操作。脚本捕获错误也不能继续绕过控制。

## 3. 对照推翻了默认推广

只增加工具时，模型完全没有使用它。加强提示后，使用仍不稳定。

明确指定组合方式后，三个任务都完成。但隐藏入口任务从 32.3 秒变成 54.5 秒。延迟入口的模型调用减少了两次，总耗时仍更长。

我的判断是：执行空间变大，并不等于模型更会选择目标和组织动作。不能把能跑程序当成效率已改善。

因此保留组合执行为可选能力，撤回默认强引导。

## 4. 数字与下一步

三个组合场景完成，零人工介入，零提交。

原生程序中途接管验证通过。确认后 10.5 秒内没有新子动作，草稿保持为空。

439 项测试通过，类型检查与构建通过。

下一步验证目标定位与程序分段。拿到稳定收益后，再决定是否把组合执行设成默认。
