# 全队接管与交还

日期：2026-09-05

## 1. 目标

接管不再只管 Lead。

用户点一次，Lead 和所有活跃 worker 一起停手。交还一次，每个人回到自己的页面，从用户留下的新状态继续。

## 2. 状态模型

这次增加了一个明确的接管组。

组里冻结接管发生时的成员。每名成员保留 session、工作标签、活动类型和页面信息。

交还时按成员分别取 snapshot。关闭标签的 worker 留在暂停态，不拖住其他人，也不擅自补开页面。

中止仍是另一条路。它结束整张任务图，不能被包装成交还。

## 3. 真机发现的问题

第一轮真机验收失败了。

Lead 能读到用户的新值。worker 只是继续原来的循环，没有处理交还边界。

原因不是页面路由，而是时序。接管调用 SDK abort 后，没有等待它真正结束。立即交还时，边界消息被 steer 进了正在中止的旧流。

测试原来没有覆盖这段时间窗。

## 4. 修复

现在会保存同一次 stop Promise。

交还先等旧流 idle，再在同一个 AgentSession 启动一次新的续跑 prompt。它不重建会话，也不再把 handback steer 进旧流。

control epoch 会取消重复接管或中止前排队的旧续跑。迟到的旧 agent_start 也会被停掉。

新增五条竞态测试，覆盖立即交还、重复接管、中止、等待消息和空闲会话。

## 5. 结果

修复后从头跑了两条 ChromeMain 真机路径。

正常路径里，Lead 和 worker 分别读回 `PASS-LEAD-20260905` 与 `PASS-WORKER-20260905`。两边 sessionId、tabId 和 native Agent 进程不变，并继续原任务。

异常路径里，关闭 worker 标签后，Lead 读回 `PARTIAL-LEAD-20260905` 并恢复；worker 显示“绑定页已关闭，未续跑”，没有新开标签。随后单独中止，界面显示“已中止”，页面没有可见控制条或光标。

机器检查是 35 个文件、331 个测试全绿。真实扩展验收连续三轮，每轮 10 项全绿。

证据在 `docs/evidence/20260905-team-takeover-v2/`。展示页是 `docs/evals/20260905-team-takeover-v2-showcase.html`。

## 6. 边界

完整退出并重启 Chrome 后，仍不承诺恢复同一任务图。

## 7. 恢复状态的第二次收口

独立复核又发现一个时序问题。

续跑只是排队，界面就会显示“已恢复”。旧流还在停止、prompt 尚未启动或启动失败时，这个结论都不成立。

现在每名成员只在同一 control epoch 的 `agent_start` 真正出现后才标记恢复。一人已启动、另一人未启动时，界面会显示“1 个已恢复 · 1 个仍暂停”。

最终真机用真实 `MiniMax-M3` 重跑。Lead 读回 `FINAL-LEAD-20260905`，worker 回传 `FINAL-WORKER-20260905`；两边各自续跑并完成 12 次循环。交还过程真实出现了部分恢复中间态，最后才显示“全队已恢复”。
