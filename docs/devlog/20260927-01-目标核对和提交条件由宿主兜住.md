# 目标核对和提交条件由宿主兜住，不靠主模型自觉

2026-09-27。[验收](../evals/20260927-memory-proactive-task.md)

## 方向

用户在日常试用里遇到三件事：
- 它不记得邮箱；
- 订阅提交后让用户自己去 Gmail 点确认；
- 用户补一句话，又被当成新任务。

用户选择三件一起做，并要求用户用的每家模型都要有像样的效果。

## 被实测推翻的做法

最初只在系统提示里加「下一步在别的网站就自己去」。智谱主模型提交订阅后照样回「去邮箱点一下确认链接就完成了」，Kimi 也一样。提示词在这类事上管不住。

## 定下的做法

1. **目标核对（`goal-check.ts`）。** 动过页面、或最后在向用户要东西的一轮结束时，宿主用快速模型判断目标达成没有：
   - 自己能做就接着做，最多 2 次；
   - 在等用户就把任务留作「等你 / 还差」；
   - 做完了才写「已完成」。

   最后在问用户时，一律等用户，这条由程序定，不交给模型。原因是实测快速模型把「要我现在点 SIGN UP 吗？」判成助手能自己做。
2. **用户设的提交条件由扩展执行。** 原话要求「提交前让我确认」时，宿主给这一任务的点击带 `confirmSubmit`，提交类按钮像删除一样先拿住。实测智谱主模型曾在一段程序里「填邮箱 + 点 SIGN UP」一口气做完，没理会这个条件。
3. **侧栏回「确认 / 可以，提交吧」直接补上拿住的点击。** 旧做法只是放行下一次点击，但那次点击在账本里是「结果未知」，模型不能重做，结果连错三次卡住。这是旧漏洞，这次才暴露。
4. **任务跨轮。** 没做完的任务，下一句由快速模型判断是否接着做；是就作为原任务的修订继续，目标不变。
5. **服务商「忙」要重试。** Kimi 同账号同时请求超限时回 403，旧重试不认，接续的一轮空着结束。主循环和快速模型短调用都改成等一下再试。
6. **始终思考的模型要给足输出额度。** 阶跃的核对和接续判断原来只给 40–200 个字，思考完之前就被截断。

## 结果

三家同一条路径的通过情况见验收文件。判断都放在宿主，主模型只管做事，换哪家模型判断标准都一样。
