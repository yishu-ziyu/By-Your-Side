# 让正式回答逐段说出来

## 1. 正常回答被长度限制丢弃

真人两次无声的正文一致性检查其实通过了。158字音频超过20秒，被整段缓存上限拒绝。用户试听纯TTS样本后，批准正式接入。

## 2. 正式正文直接交给语音合成

输入识别保留。正式正文按形成顺序送入同音色纯TTS，收到音频即交给播放器。工具与内部文字不进入这个出口。普通插话先停声，网页停止仍按已有控制处理。

实际模型的参数可能先发正文、后发类型。等待类型会错失增量；任务身份的工厂绑定也要覆盖新增出口。这两处由真实路径发现并修正。

## 3. 区分不等待全文与实际首音时刻

真实例子的正文在172毫秒内生成完毕，首音在首段文字后859毫秒返回，音频共63秒。因此这个例子证明长音频和播放器路径，不证明首音早于全文结束。受控分段检查单独验证未结束正文即可返回音频。

最终复测出现9段正文，首音比最终正文早912毫秒，音频73.5秒。1020项测试、类型检查、构建通过。正式扩展已重载。下一步是用户实际听长回答并插话；最终听感仍未验收。原始标准与证据见[验收文档](../evals/20260910-streaming-voice-product.md)。本轮原因已由代码、测试和验收说明覆盖，不重复新增经验或规则提案。
