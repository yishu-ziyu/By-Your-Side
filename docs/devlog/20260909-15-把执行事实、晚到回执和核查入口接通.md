# 把执行事实、晚到回执和核查入口接通

## 1. 问题不是判断错，而是编号没对上

上一轮修了超时和断连，独立验收却退回。原因不是判断逻辑不够细，是 RPC 用传输 UUID 记账，模型事件用 Pi 的 toolCallId 查询，两个编号从来没有映射。事实没丢，是取不到。

这次先修身份：一次调用在 RPC 里只存一条记录，传输 id 和 SDK id 都指向它；`browser_run` 的内部步骤用 `父id/序号` 单独登记。执行前默认“未执行”，发出去超时或断连是“未知”，收到成功回执才是“已执行”。错误文案里的“未执行”“元素未找到”不再参与判断——那些词既可能是动作前拒绝，也可能是动作后失败，猜错一次就多写一次。

## 2. 未知需要出口，不能只有入口

原来系统只会进未知，没有出路。晚到回执在 RPC 里被识别，但没人把它接回任务账本；页面核查也没有生产入口。结果就是一次回执丢失，后续写入永久停住。

两处接线：

- Lead 会话向共享 RPC 注册监听，把晚到回执变成 `tool_late_result` 事件，沿生产事件流进入任务进度，只认同一个 run 的未决项。重复回执、旧 run、其他会话都匹配不上。
- 新增窄工具 `resolve_unknown_result`。模型不能说“我核查过了”，只能给结果 id、读取目标和一段证据文本；宿主自己重新读页面，读数里真的有这段文字、且读数晚于原操作，才解除未知。读不到就保持未知，并要求如实告诉用户“结果无法确认，没有重复执行”。

## 3. 去重要绑在操作身份上

执行器原来只在操作在途时记一笔，结束就删。同一个操作 id 再来一次，照做。现在按 `session::操作id` 记住完成结果：重复投递回传原结果或原错误，不再执行；并发重复等待原操作。完成记录进控制快照，SW 重启后仍认得出重复投递。

跨进程有个边界要说清：重启后只能证明“执行过”，拿不到当时的结果。所以重放一律报“未知”，绝不能报“未执行”——后者会让模型以为可以安全重试。

## 4. worker 不再绕开

Lead 有执行约束，worker 没有，等于留了后门。现在 worker 创建时传自己的 `memberId`，用与 Lead 同一套执行参数，并共享同一份会话进度。worker 只受一条约束：同一任务里有未决写入时不能写，读照常。它不需要替 Lead 登记结果，也不做 Lead 的目标绑定校验。
