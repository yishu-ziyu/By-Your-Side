## 2. 视频明确讲了什么

| 实际时间 | 内容 | 对理解全双工的作用 |

| [0:00–0:33](https://www.youtube.com/watch?v=YGgErBnx6po&t=0s) | 口头要求搜索桌子、播放音乐、换曲、30 分钟后停止 | 请求可以落到网页和工具；最后一项只展示口头应答，未展示计时到期执行 |

视频强调的是交互循环。它没有证明所有输入都应立刻引发操作，也没有证明采用某个框架就会自然得到这种体验。

单独的文字转语音只负责说；语音识别、现有 Agent、流式语音合成经过合适编排也可能做出可打断的体验。不能从视频对 TTS 的简化对比，直接推导出必须换成原生实时多模态模型。

## 3. 额外核对的一手技术事实

2026-09-08 查阅 Google 官方文档：

- [Live API 工具调用](https://ai.google.dev/gemini-api/docs/live-api/tools)：默认工具调用按顺序等待结果。当前表格中 Gemini 3.1 Flash Live Preview 仅支持同步调用；2.5 Flash Live Preview 支持同步及异步调用。异步结果还可以选择立即插入、空闲再说或静默更新。因此，“接入 Live API”本身不足以证明长工具执行期间仍能对话。
- [Live API 打断处理](https://ai.google.dev/gemini-api/docs/live-api/capabilities#voice-activity-detection-vad)：检测到插话后会取消当前生成，客户端仍须停止播放并清空待播队列。应用必须另外处理已经执行的外部动作，不能把模型取消事件理解成网页操作已经撤销。

这些事实只用于识别实验条件，未据此选择供应商或模型。

## 5. 初步产品判断

建议把第一条讨论路径设为：**它操作网页时，我能随时开口纠正；它按新的意思继续，任务背景仍在。**

把三种话先说清楚，避免同一个“打断”混入不同动作：

| 用户说什么 | 期待发生什么 | 不能算成功的替代 |
| --- | --- | --- |
| “先别讲了” | 停止当前播报，继续听；已有任务是否继续按当下明确约定处理 | 仅停止模型生成，队列里的声音仍播完 |
| “改成一千以内，只看下面那个” | 理解新条件，核对所指对象，使未执行的相关步骤服从新约束 | 留下一段转写，执行仍沿用旧条件 |
| “别点了，我来” | 阻止后续相关网页写入，确认停手后把控制权交给用户 | 口头说“好的”，后台仍继续点击 |

普通附和、思考停顿、明确纠正、明确叫停需要不同处理。尚未定案：无修饰的“停一下”默认停到哪一层、误识别时如何恢复、用户接管期间能问到什么。

共同注意也要具体：用户说“这个”时，系统需要当时的页面、选区或指向依据。连续传全屏并不能自动解决指代；发生跳页、滚动或切会话后，要重新核对对象。

## 6. 下次讨论的最小场景

1. 用户在商品列表说：“帮我找一张书桌，预算一千五。”
2. Agent 开始查看和筛选；用户中途说：“改成一千以内。”
3. 在页面仍加载时，用户问：“现在卡在哪？”Agent 根据真实任务状态回答。
4. Agent 正在解释候选项时，用户说：“先别讲，下面那个为什么没选？”它停下旧播报，核对对象并回答。
5. 用户说：“别点了，我来。”页面确实停止后续写入；用户自己展开一个选项。
6. 用户说：“你接着来。”Agent 重新查看用户改后的页面，保留任务条件继续。

这是一条候选验收场景，尚未冻结为实施标准。若用户更重视“我自己浏览，它随时陪我理解”，接管期间继续问答会成为首要路径，优先级应随之调整。

需要分别记录的量：开口到旧声音停止、意图说清到应答、明确叫停到真实停止写入、工具忙时仍能响应、误打断和丢失纠正。数值门槛尚未定，不从演示视频里推算。

选型前最有价值的实验是在同一条路径比较“流式语音识别→现有 Agent→流式合成”和“实时语音会话→现有任务执行”。先确认中文接话、工具等待时交流、控制权可靠性，再判断是否值得增加编排复杂度。
