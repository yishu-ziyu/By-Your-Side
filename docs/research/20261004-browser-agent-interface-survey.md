# 浏览器 Agent 接口调研：理解、对照本项目与采用决定

来源：用户 10-04 提供的两份调研，逐字原文见 [report-1](20261004-browser-agent-interface-survey/report-1.md)、[report-2](20261004-browser-agent-interface-survey/report-2.md)（资料访问日 2026-10-04，本项目未运行文中工具）。本文是理解与对照，不代表已实现。代码对照为 10-04 只读核对（未运行），文件行号以当日 main 为准。

修订：10-04 初版只压缩到原文约 8%，漏掉实验设计差异、取消语义、增量观察与核验配套、Browser Harness、各建议的不适用条件；并把续接确认作废误写成“绑定旧 runId”的例子（实际根因是边缘光晚一帧点亮，见[验收](../evals/20261004-resume-consent-race.md)）。本版重写。

## 核心论点

1. **工具数量与质量没有单调关系。** 能力缺失时加接口提高上限；覆盖后质量取决于一条链：看对页面 → 认准目标 → 动作真的执行 → 知道执行到哪 → 核对结果成立 → 失败不重复副作用。（工程判断，无对照实验证明）
2. **质量主要产生在模型与浏览器之间的执行层。** 同一个 CDP 可以包成脆弱的 `click(x,y)`，也可以包成带页面身份、可操作检查、引用生命周期、回执与后置核验的 `click(target)`。本扩展同时承担执行层与产品安全层。
3. **没有“总冠军”。** 公开评测没有同时固定模型、任务、登录态、权限与成功判据；EGO“最强 Snapshot”“快 2.5×”为厂商自测（4 个任务）。
4. **暂无证据要求换掉 Chrome 扩展。** `chrome.debugger` 已提供 DOM、DOMSnapshot、AX、Input、Network、Page、Runtime、Target 等原料；EGO 依赖定制浏览器的只有 Snapshot 内核与 Space 隔离，后者与“在用户当前 Chrome 里工作”冲突。

## 三项建议对照本项目（10-04 代码核对）

| 建议 | 本项目现状 | 缺口 | 不适用条件（原文） |
|---|---|---|---|
| **D1 目标身份＋动作前检查** | 部分有：ref 是 backendNodeId，按标签页登记，跨标签页即“未执行”；点击/填写前核对 documentId；导航清空登记；节点被替换时失败而非改点别处（`extension/src/background/axstate.ts`、`exec/input.ts`）。点击有零尺寸与命中测试，按下前再测一次 | ref 不带 frame 与“角色+名称”指纹；无“可用/不在动”检查；`fill` 不查禁用/只读；`force` 跳过命中测试 | 多数任务只读一次、页面不变时收益小 |
| **D2 结果核验** | 部分有：三态回执（已执行/未执行/不确定）完整，“不确定”上锁防重复；点击后有 DOM 变化、新标签页、弹窗检测；下载以完成为准 | 点击效果不关联网络请求与同页导航；`fill` 不回读值（回读只给语音路径）；下载不核内容；“恰好一次”只靠上锁 | 纯读取、滚动、搜索不需要重核验 |
| **D3 批量分段＋取消逐项报告** | 部分有：`browser_run` 每个子动作走同一权限与确认；出错、超时、被拿住即停 | 成功导航/提交/发送后不强制停下重看；取消时排队动作不报“未执行”，模型只收到一句“已中止” | 每步都强烈改变页面时逐步做更简单 |
| 增量观察 | 有视口范围、只列可操作控件、分页游标、24k 字上限 | 无 delta、无“画面不变不重发” | canvas、地图、富文本等结构化 diff 弱的页面 |
| 能力闭合（原文“任意 JS”审计） | 严格：原始 CDP 只放 10 个只读方法；页面 `js` 每次需批准；沙箱无 fetch/DOM | 批准后的 `js` 拥有完整页面能力；只读 JS 实验未通过（[实验](20261003-readonly-js.md)） | — |
| 跨域 iframe | 基本没有：自动挂接代码已写（`debugger.ts` `ensureChildFrameSessions`）但无调用方 | 嵌入式支付框、表单、企业后台看不见 | — |
| 标签页钉住 | 部分：任务上下文钉住 tabId，用户切页不影响 | 钉住的页被关只得到原始错误；未钉住时默认拿用户当前页 | — |
| 用户/Agent 交接 | 有：控制权归属、接管先收尾在途写入再拒绝迟到写入 | — | — |

## 对本项目的含义

- **今天的实例印证了原文。** 原文指出 `DOMSnapshot.captureSnapshot` 会展平 Shadow DOM；本项目确认绑定用它采页面状态，扩展画在封闭 shadow 里的边缘光被当成页面变化，导致续接确认误作废（10-04 已修）。“看对页面”需要分清自家呈现与网页本身。
- **对写操作，逐次确认是一道人工身份核对**：用户在卡片上看到目标，能拦下多数点错。所以 D1 对写操作的收益小于原文估计；D2（重复提交、谎报完成）伤害最大，优先。
- **可扩展性瓶颈在工程结构而非底座**：新增一个模型可用工具要改约 11 处（协议、模型说明、执行器、权限分类、侧栏文字、语音清单等），只有执行器表由编译器检查；9 个文件 1400–5100 行。
- **体验瓶颈**：读页面也逐次确认（安全设计）会让连贯任务被打断；`browser_run` 内的等待轮询是否也逐次确认未实测。

## 采用决定（10-04）

1. 先量现状再改：重复提交与谎报完成的基线（Linear YIS-21）。
2. 北极星场景“一句话跨网站办完一件事”（[验收](../evals/20261004-north-star-cross-site.md)）：用同一组练习站同时测底座、确认次数与结果核对。
3. 原文 E 的对照实验（A 现状 / B 可靠优先 / C 速度优先，每组 ≥30 次、配对比较、确定性判定、预先写推翻条件）作为后续评估方法，先在脚本模型上做。

## 预先写下的推翻条件（原文 E）

- B 在节点替换、导航、iframe 替换下没减少错目标与不安全恢复，且明显更慢更复杂 → 不做复杂身份账本，改用“页面变了就重读”。
- 速度优先组在注入超时、取消、部分失败、非幂等提交下仍零重复零错操作，且稳定省时省 token → 屏障过保守，放宽批量。
- delta 常漏关键变化、频繁退回完整读页且不省 token → 保持完整观察。

## 仍未知且会改变选择的事

EGO 闭源 Snapshot 改了什么；同 Profile 不同 Space 的存储隔离；各方案在同一真实登录 Chrome、同模型下的成功率；复杂 iframe/closed Shadow DOM 的实际失败率；压缩策略省多少、丢多少；用户同时操作同一 Chrome 时的竞争（本项目钉住标签页已有，被关后的报错待补）。
