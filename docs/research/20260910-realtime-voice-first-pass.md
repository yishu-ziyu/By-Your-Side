# 实时语音：本轮只确认可借鉴的公开机制

用户确认参考对象为ChatGPT连续实时语音。当前只授权调研，以及给现有播报拒绝分支增加原因日志并重载复现；没有批准更换模型、移除检查或重写语音链路。

## 官方公开的做法

- [Voice agents](https://developers.openai.com/api/docs/guides/voice-agents)：低延迟自然对话可用直接语音输入/输出；扩展已有文字Agent也可用识别→原Agent→语音合成的组合。两种架构都可成立，不能只因喜欢ChatGPT体验就推导必须换掉Pi。
- [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)：支持工具调用；用户插话时取消生成、停止播放，并从对话里移除未播放内容。声音是否被听到与生成是否完成要分清。
- [Voice activity detection](https://developers.openai.com/api/docs/guides/realtime-vad)：既可按静音分句，也可按语义判断用户是否讲完；犹豫、拖尾时不宜抢话。支持情况需按所选模型和服务核对。

这些是公开API能力，不是对ChatGPT内部完整实现的证明；不承诺接入同一个API就得到完全相同听感。本轮没有调用OpenAI模型或改变provider。

## 与本产品的直接关系

现有固定播报先缓存整段声音，等生成完成后检查，再播放；最多重试两次。它会增加首声等待，且拒绝后可能只剩文字。当前先定位用户本次无声的具体原因，不能直接取消防止播报改写事实的约束。

更自然的方向是减少说话前串行等待、让声音及时输出、打断及时停播，并让网页任务仍走Pi及原操作权限。是否采用直接实时语音或正文流式合成，需要结合当前Step服务实测后另行对齐。

## 本轮诊断准备

`voice-session.ts`只增加拒绝元数据：生成结束状态、音频是否存在/字节数/时长、是否超限、文字是否一致及两端字数。没有记录录音或原文，没有修改放行条件/重试次数。原42项语音测试通过，4种拒绝原因的单次事件探针可区分。已按用户授权重载插件，等待真人再次询问标题以获得本次原因；这不是修复通过。
