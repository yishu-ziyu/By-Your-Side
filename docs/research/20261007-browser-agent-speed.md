# 浏览器 Agent 提速调研：结论、对照本项目与实验建议

来源：ChatGPT Deep Research 2026-10-07 的报告，逐字原文见 [report.md](20261007-browser-agent-speed/report.md)，提示词见 [prompt.md](20261007-browser-agent-speed/prompt.md)。本文是理解与交接，不代表已实现。本项目未运行文中任何工具。

读者：负责实现的工程团队。本文给方向、候选方案和每个方案的验证方法；实现细节由工程团队定。

## 目标（10-07 与用户对齐）

- 速度分三种：整件事更快、每一步更快、感觉更快。三种都查，按收益和代价排先后。
- 准确不设固定底线。每个提速方案列出准确代价，由用户裁决。
- 交付：方向 + 候选方案 + 实验计划。

## 核心结论

1. **慢主要在“每一步都等一次模型”，浏览器本身不慢。** 本项目在用户本机 Chrome 里经 CDP 操作，没有云端浏览器的往返损耗；优化点击本身收益小（Stagehand v4 作者对本机场景的说法）。
2. **有效的提速做法都是同一个结构：先试一条便宜的捷径 → 核对前提还成立 → 成立就省掉模型 → 不成立就回到正常的 Agent 流程。** 捷径挂在可靠路径前面，不替代它。
3. **页面信息不是越少越准。** 强模型拿到更完整的页面时定位更准；弱模型相反。省的应该是“重复发送的信息”，不是“可能有用的信息”。
4. **各家产品（Claude in Chrome、ChatGPT Agent、Comet、Gemini/Mariner）都没有公开提速对照数据。** 它们只能作为产品方向的参考，不能作为性能证据。

## 三条路与候选方案

| 路 | 方案 | 公开数据（性质） | 准确代价 | 本项目现状（10-07 只读核对） |
|---|---|---|---|---|
| 少走几步 | **成功路线重放**：成功一次后把路线存成带意图、前提和变量的步骤；下次同类任务先重放，对不上就从当前进度交回 Agent | Skyvern 279 秒 → 120 秒（厂商自测，样本未披露）；Agent JIT 比 Browser-Use 快 10.4×（论文，37 个任务，测试站点） | 页面变了以后，旧路线点到语义不同的元素 | 已有批量动作工具，可当执行器；没有路线存储 |
| 少走几步 | **只读捷径**：问答、查询、下载时直接拼目标网址，或读页面已用过的只读接口；结果先校验，不对再走界面 | Skim 中位耗时 −33.4%，准确不降（论文，三种 Agent） | 网址规则变了，拿到错数据还被当真 | 无 |
| 每步更快 | **只发变化**：第一次发完整页面，之后只发变化的部分；跳转或大改时重发全页；模型可主动要全页或局部 | 论文认为差分是省 token 的折中，没有耗时数字 | 漏掉没变但关键的上下文 | 10-04 调研已记为缺口：“无 delta、无画面不变不重发”（[10-04](20261004-browser-agent-interface-survey.md)） |
| 每步更快 | **只读预备**：模型思考时，预取可能的下一页、提前解析候选元素；模型确认后才用，猜错丢弃 | 最多 −20%（ICLR 2026 论文） | 只做读就不影响准确；一旦提前点击就失去保证 | 无 |
| 每步更快 | 小模型执行、卡住再升级 | 最多 −45.8%（论文 StepWise） | 升级判断漏掉难步骤，就会降成功率 | **报告不推荐先做**：用户可能只配了一个模型，后台用第二个模型涉及成本和隐私 |
| 感觉更快 | **本地即时进度**：由扩展按真实事件显示进度，不等模型首字，不让模型写旁白 | 未找到对照数据 | 进度和实际动作不同步会伤信任 | 已有动作卡与光标旁白（#43、#47）；缺口要先核对，不重做 |
| 感觉更快 | **先给已确认的部分结果** | 未找到对照数据 | 临时结果被当成最终结果 | 未核对 |

不建议做或要限制的：

- **无条件并行**：Agent JIT 的一组实验里，全并行 148.5 秒，反而比串行 129.6 秒慢。只并行互不影响的只读子任务。用户的 Chrome 共用登录状态、购物车和当前标签页，同时写同一个对象不安全。
- **写操作走捷径**：提交、付款、删除、发送不走接口捷径，也不做预备执行。
- **省掉模型的同时省掉安全判断**：原来每轮 Agent 推理里隐含的安全检查，在重放和捷径里要变成明确的运行规则。

## 建议顺序

**第 0 步：拆开时间。** 先给主任务循环加计时，每一轮记录：模型等待（含首字）、读页、执行、等页面、核对、重试原因；再记录标签页数量、页面大小。

- 原因：26 秒的复制任务，可能是 3 次 4 秒的模型等待，也可能是网页自己加载了 10 秒。两种情况对应的方案完全不同。
- 现状（只读 grep，未运行）：批量动作的每个子步骤有耗时（`agent/src/browser-program.ts`），主任务循环没有看到按上述分类的计时。
- 这一步不改变用户能看到的行为，代价最小，结果决定后面先做哪条路。

之后按数据决定。没有数据时的默认顺序：

1. 只发变化：便宜，不依赖模型厂商，又是已知缺口。
2. 只读捷径：先覆盖页面问答（约 10 秒）和下载。
3. 成功路线重放：收益最大，也最难；先拿复制类任务（约 26 秒）试。
4. 本地即时进度：和上面并行做。先核对现有动作卡还缺什么，例如整页翻译时“主模型先想约 8 秒，页面不动”（[STATUS](../STATUS.md)）。

划词解释（约 2 秒出首字）的瓶颈是模型首字延迟，上面 1–3 帮不上；只能换更快的模型或靠第 4 项改善等待感。

## 实验与判负条件

每个方案的完整设计（改什么、对照组、样本量、指标）见原文“推荐做法的小实验设计”一节。共同规则：

- 同一任务、同一模型、同一初始页面，成对比较；每个任务至少跑 3 次；看 p50 和 p90，不只看平均。
- 测试集保留一部分正在变化的真实网站，不只用固定页面；否则重放和缓存的效果会被高估。
- 按模型分开看结果：GLM、MiniMax、Kimi、DeepSeek、OpenAI 的最佳页面表示可能不同。

报告给出的判负条件（任一成立即不值得做）：

| 方案 | 不值得做的信号 |
|---|---|
| 成功路线重放 | 命中任务 p50 降幅 < 20%；全体 p50 降幅 < 15%；成功率降 > 1 个百分点；出现任何由重放导致的不可逆错误；回退率 > 25% |
| 只读捷径 | 全体 p50 提升 < 15%；命中率 < 25%；出现任何一次错误结果被校验放过；回退任务 p90 比对照慢 > 20% |
| 只发变化 | 模型输入降幅 < 25%；每步耗时降幅 < 10%；成功率降 > 1 个百分点；定位重试增加 > 10% |
| 只读预备 | 猜中率 < 30%；p50 降幅 < 10%；额外请求 > 1.5 倍；出现任何未经模型确认的写操作（设计失败） |
| 本地即时进度 | 首个可见反馈时间降幅 < 50%；进度倒退或与实际不符；用户把“正在执行”误认为危险动作已完成 |
| 先给部分结果 | 部分结果后来被改正的比例 > 2%；首个有用结果提前 < 30%；总时长增加 > 5% |

这些阈值是报告的建议，不是用户已确认的完成标准。开工前应写进 `docs/evals/` 的验收文件，并由用户确认。

## 核查与未知

已核对（2026-10-07，对照原始摘要或原网页）：

- Agent JIT：10.4×、准确率 +28%；调度器比 OpenAI CUA 快 2.4×（arXiv 2605.21470）。
- Skim：中位耗时 −33.4%、成本降 1.9 倍、准确不降（arXiv 2605.16565）。
- Read More, Think More：紧凑表示适合弱模型，HTML 适合强模型，差分是省 token 的折中（arXiv 2604.01535）。
- Speculative Actions：下一动作猜中率最高 55%，耗时最多 −20%（arXiv 2510.04371）。
- Skyvern：平均 278.95 秒 → 119.92 秒（官方博客）。

未核对或不确定：

- “Browser-Use 约 73% 的时间在等模型”不在 Agent JIT 摘要里，正文未核对。
- Agent JIT 的 10.4× 来自 37 个任务和自建测试站点，不能当成本项目的目标值。
- Stagehand 缓存“最高约 80%”、EGO 2.4× 与 3.45×，都是厂商自测，样本很小或没有披露。
- 国内模型（GLM、MiniMax、Kimi、DeepSeek）的首字延迟和提示词缓存没有找到公开对照数据。
