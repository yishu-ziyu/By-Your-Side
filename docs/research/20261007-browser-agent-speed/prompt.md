请做一次深度调研：浏览器 Agent 怎样在"更快"的同时"不变得更不准"。

## 我们是谁、现在什么样
- 产品：Chrome MV3 扩展形态的浏览器助手，在用户自己正在用的 Chrome 里工作（不另开浏览器、不用云端浏览器）。底层通过 chrome.debugger 调 CDP；页面观察以无障碍树（AX tree）为主，只列可操作控件、限视口、单次上限约 24k 字，必要时截图。Agent 循环为自研（基于 Pi 框架），约 30 个工具，已有一个可批量执行多个子动作的工具。
- 模型：用户自选，包括 GLM、MiniMax M3.1、Kimi、DeepSeek，以及经 ChatGPT 登录的 OpenAI 模型。所以方案不能只依赖某一家的专属能力（例如只有某家才有的 computer-use 模型）。
- 现有实测（我们自己测的，供你估算量级）：页面问答中位约 10 秒；"复制类"多步任务中位约 26 秒；下载 PDF 2 步 8 秒；划词解释约 2 秒出首字（瓶颈是模型首字延迟）。
- 我们已经调研过"执行层质量"（目标身份、动作前可操作检查、结果核验、批量分段），这次不用重复，除非它直接影响速度。

## 要回答的问题
"速度"拆成三条路，请每条都查清楚：
1. 少走几步：减少 Agent 循环的往返次数。例如一次规划多步、批量动作、宏/技能复用、缓存成功路径、直接调网站接口而不是点界面。
2. 每步更快：缩短单步耗时。例如更精简的页面表示（增量快照、只发变化）、更小/更快的模型分工（大模型规划、小模型执行）、投机执行、并行、预取、首字延迟优化、提示词缓存。
3. 感觉更快：总时长不变时，让用户不觉得在干等。例如流式旁白、先给部分结果、进度可见。

每条路都要回答：有哪些具体做法；谁在用（产品或开源项目）；实测能快多少；对准确率有什么代价或风险；什么情况下不适用。
